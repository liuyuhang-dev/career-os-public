# MR 审查与合并规则

适用于向 `main` 提交、审查、解决冲突和合并 MR。提交流程见 `.agents/skills/axiom-git-commit-skill/SKILL.md`。本文规定合并门槛，不授予额外的合并权限；已有人工评审与业务冲突拍板要求继续适用。

## 1. 记录审查对象

- 记录 MR、关联 issue、源分支 SHA、目标分支 SHA、被测提交与实际测试环境。不得用浮动分支名代替 SHA。
- 创建 MR 前先 fetch 最新主干并同步；开始同步前保存双方基线及共同祖先，不能仅保存任务分支的 HEAD：

```bash
git fetch origin main --prune
PRE_SOURCE=$(git rev-parse HEAD)
REVIEW_TARGET=$(git rev-parse origin/main)
REVIEW_BASE=$(git merge-base "$PRE_SOURCE" "$REVIEW_TARGET")
```

- 工作区有他人改动时先保护，不为审查擅自切分支、重置或覆盖。基线与原始输出放本地 `reports/<日期>-<主题>/`；MR 只写必要结论、SHA、代码定位及可复核的验证摘要，不提交过程文件。

## 2. 合并前查清双方改动

查看共同祖先以来双方各自改了什么，找出双方同时修改的文件、函数及行为：

```bash
git diff --name-status "$REVIEW_BASE" "$PRE_SOURCE"
git diff --name-status "$REVIEW_BASE" "$REVIEW_TARGET"
git log --oneline "$REVIEW_BASE..$REVIEW_TARGET" -- <双方同时修改的文件>
```

- 对重叠范围追查主干相关 MR/issue 的修复目的、验收条件和测试。日期不限于本次分支创建之后；必要时继续追溯旧修复，不能只按提交标题猜测。
- 普通 MR diff 往往基于共同祖先，不能完整展示这条分支将如何影响后来合入主干的修复；`can_be_merged` 只说明 Git 能合并，不代表行为兼容。
- 同功能的在途 MR 必须核对重叠、依赖和最终实现归属。禁止把两个互相覆盖的修复分别判为通过，再直接批量合并。

## 3. 冲突必须按语义解决

- 冲突发生时立即保存 `git diff --name-only --diff-filter=U` 清单；解决后 Git 不再列出冲突，不能事后当成“无冲突”。
- 每个冲突说明双方意图、保护的旧修复、共存方案和行为差异，按提交 skill 请求人工逐项拍板。禁止未经确认整文件选边或使用 `-X ours/theirs`、`--ours/theirs`、`-s ours` 覆盖业务代码。
- 人工同意某侧文件不等于同意撤销其中所有旧修复。若方案会丢失已有行为保护，必须明确列出受影响 issue 和行为，单独确认。
- 暂不同步只能 abort 并保留本地工作；不得把冲突或落后分支作为已通过评审的交付，也不得绕过同步门槛创建/合并 MR。

## 4. 合并后双向检查（推送与合并的前置门槛）

同步及冲突处理完成后记录 `RESULT=$(git rev-parse HEAD)`，必须同时审查：

```bash
# 主干在分叉后增加了哪些修复：作为保护清单的输入
git diff "$REVIEW_BASE" "$REVIEW_TARGET" -- <重叠文件>
# 合并结果对已审主干的真实影响：检查是否删除/改坏主干已有修复
git diff "$REVIEW_TARGET" "$RESULT" -- <重叠文件>
# 合并结果对任务分支的影响：检查任务自己的实现是否丢失
git diff "$PRE_SOURCE" "$RESULT" -- <重叠文件>
# 最终完整净改动仍须审查，不能只看重叠文件
git diff --stat "$REVIEW_TARGET" "$RESULT"
git diff "$REVIEW_TARGET" "$RESULT"
```

检查全部冲突文件、双方同时修改但自动合并的文件，以及它们调用的接口、生成物、配置和资源。逐项填写保护记录：

|原 MR / issue|必须保留的行为、触发条件|主干实现位置|合并后实现位置或经确认的替代方案|回归用例与结果|
|---|---|---|---|---|
|填写实际编号|例如订单配方排序优先，允许非订单开工并不取消排序优先|文件/函数|文件/函数及语义说明|被测 SHA、场景、结果|

- 方法名还在、代码行数接近、编译成功都不能证明修复保留；必须核对条件、排序优先级、缓存失效、事件载荷、异步门控和异常兜底等实际行为。
- 删除、替换旧逻辑可以是合理改规，但必须有明确业务依据与确认，并验证替代实现。**任何未解释的主干修复损失、影响范围不明或回归失败，均停止推送/批准/合并。**
- 修复同一处代码时，同时回归此前修过的场景和新需求。示例：放开非订单制作后，仍需验证订单配方优先、订单换序后的缓存更新及非订单配方可用。
- 无文本冲突不豁免语义检查。无重叠文件可注明依据并缩小保护清单，但仍须审查完整净改动及跨层契约。

## 5. 测试与交付范围

- 源码变更须完成对应编译及受影响行为的回归；在解决冲突后的最终代码上重跑相关用例。源码、生成协议、配置、wasm/原生产物、Prefab/字体/图标依赖分别核对；不要求无关平台全量重测。
- `skipped`、`manual` 未执行、CI 不存在、编译通过或仅静态核对均不能写成“业务测试通过”。CI 未覆盖时须补实际命令/环境/被测 SHA/结果；关键验收未执行则保持待验，不批准合并。
- 仅需求/知识库文档 MR 应明确“无实现”，只做适用的文档检查；不得自动关闭仍缺代码、资源或验证的 BUG。拆分交付需列出各 MR 和依赖。
- 分支测试结果只覆盖被测提交。合并到当前主干后的代码发生变化时，先重验受影响场景；合并完成后记录实际主干提交并做相关冒烟，通过后才按修复完成关闭 issue。
- issue 关闭须区分：修复并验证、重复/转单（链接实际跟踪单）、按确认口径非缺陷、业务决定暂不处理。后三者不能描述为修复通过。

## 6. 批准与执行合并

- 评审结论写明源 SHA、目标 SHA、结果 SHA（如已生成）、保护清单、冲突拍板和测试结论。尚有未解释删除、未完成关键验证或未确认业务冲突时，结论必须是“阻止合并”。
- 执行合并前重新 fetch 并读取 MR 最新源 SHA。任一 SHA 与评审记录不符，旧批准失效：重新审查新增差异，更新保护清单并重跑受影响检查；主干已前进时先同步再复核。
- 不并发批准并合入会互相覆盖的 MR。每合入一个，再以新的主干作为后续 MR 基线。
- 调 GitLab 合并 API 时携带已审源 `sha`（或 CLI 对应的 SHA 匹配参数）；这只能防源分支变化，不能替代目标 SHA 重验。服务端拒绝、目标前进或 SHA 不匹配时停止，不自动放宽条件重试。
- 规则文件和 MR 模板提供流程约束，不等于已启用 GitLab 服务端强制门禁。不得声称仅编辑本文就能技术上阻止所有违规合并。
