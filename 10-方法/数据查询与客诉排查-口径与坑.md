# 数据查询与客诉排查：口径与坑

> 从数数（ThinkingData）取数和海外客服客诉排查里，能跨项目复用的部分。
> 具体项目 ID、内网地址、Token 不写在这里。

## 一、取数的四个口径

### 1. 收入用订单流水，不用客户端购买事件

- 服务端订单流水（`trackrevenue` 一类）是主数：`sum(usdprice) / 100`。
- 客户端购买事件（`purchase`）经常只是子集，实测会漏掉大部分订单；用它算 ROI 会显著偏低。
- 结论：**对账以服务端流水为准，客户端事件只用来定位行为。**

### 2. IAA 单独算，不要混进 IAP

- 广告收入看变现平台的 impression-level 报表，量级通常远小于 IAP。
- 广告报表里的 eCPM 字段不一定是真 eCPM，先验证单位再用。

### 3. 成本口径要写清楚覆盖范围

- 投放成本按广告平台 × 国家 × 天的粒度汇总。
- 很多项目只接了 Meta，Google/TikTok/AppLovin 不在同一张表里；报告里必须写"按 Meta 这一份花费算"，不能写成全渠道。

### 4. 留存看分母

- 买量成本按安装付，所以留存优先按设备算；账号口径只用于对比形状。
- 专门上报的 `d1_time` / `d7_time` 事件不能直接当留存：它们的分子分母可能对不上，用安装队列算。

## 二、时间与时区

- 分区字段（`$part_date`）是**项目时区**的自然日，查询必须带分区条件，否则服务端会拒绝。
- 事件时间（`#event_time`）是**玩家设备本地时间**，等于 UTC + 设备时区偏移；玩家自报"几点出错"通常对得上它。
- 当天数据是部分数据，结论只用到昨天；没到的留存写"未到"，不要写 0%。

## 三、字段与类型

- 账号 ID、玩家 ID 在不同项目里可能是数值或字符串，比较前统一 `cast(... as varchar)`。
- 带 `$` / `#` 的字段名要加引号。
- 有些字段名看起来该有 `#` 前缀，实际是自定义属性（没有前缀）；查不到先看事件属性清单。
- 价格字段可能是当地货币，跨币种直接求和会得到假数；用美元定价字段。

## 四、查询失败怎么判断

- **查询接口返回成功但内部报错**：业务层返回码可能仍是 0，要看 `isSuccess` / `errorMsg`。
- **Token 过期**：任何查询都立刻断开连接，换一个假 Token 也是同样报错——不要先怀疑 SQL。
  - 重新登录控制台，取新的 Token（值外面可能带一层 JSON 引号，要去掉）。
  - 写回本地凭证文件后，用 `select 1` 验证能出 1 行。
- **分区缺失**：报错会明确提示 where 条件要带日期分区字段。

## 五、客诉排查的顺序

1. **先对 ID**：玩家给的多半是游戏内 ID；先用它查，查不到再试账号 ID。
2. **再看崩溃/失败事件**：确认是客户端崩、服务端拒绝，还是网络问题。
3. **再看进度有没有在存**：对比最近几天的等级、金币、关卡，判断是"没存上"还是"存档被覆盖"。
4. **最后看是不是只有他**：同一错误在全项目的发生率，决定是个案还是版本问题。
5. **回复三段**：英文正文 + 中文翻译 + 内部处理要点；内部要点明确标注"不用发给玩家"。

### ID 对不上时

玩家手抄的 ID 常少一位。可以逐字缩短前缀做模糊匹配，命中后把正确的 ID 写回给玩家；不要直接回"查不到"。

## 六、报数规矩

- 每个数带日期范围、口径、分母样本量。
- ROI 低于/高于 1 时，把分子分母都列出来。
- 成本覆盖不全时，明确说覆盖了哪些渠道。
- 不用"大概""可能"掩盖口径问题；口径不清就先问清楚再报。
