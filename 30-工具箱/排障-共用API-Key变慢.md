# 「团队共用一个 DeepSeek key，感觉比个人单 key 慢」——诊断与处置（可转发版）

> 依据：DeepSeek 官方文档（api-docs.deepseek.com，限流页 / 错误码页 / 定价页）现行口径。
> 配套脚本：`deepseek-bench.py`（同目录）。

## 一、先说结论

> 本文档已根据 2026-10-08 的本机实测更新：**实测定位到自建中转的转发写出路径（初测吞吐仅约官方的 42–55%），经当天多版迭代后已达标：v4 吞吐比 102%（经中转 152 vs 官方 149 tok/s）、块间隔 p90 18ms、长任务持平或更快**。详见「四、本机实测结果与结论」与「五、处置」。

1. **官方限制是"按账号"的并发数，与用哪个 API Key 无关。**
   原文：*"Concurrency limits are calculated at the account level, regardless of which API Key is used."*
   限额：`deepseek-flash` 2500 并发，`deepseek-v4-pro` 500 并发；一个请求从发出到响应完成占用 1 个并发位。
   → **所以"再发几个 key"完全没有用**；同理，官方机制里不存在"共用就降速"，除非撞上限（429）。
2. **"共用导致慢"的说法站不住，但"确实变慢"的体感通常是真的。** 按概率排序：
   1. **时段混淆（最大嫌疑）**：官方高峰时段 = UTC 01:00–04:00、06:00–10:00 工作日 = **北京时间 9:00–12:00、14:00–18:00**，恰好是工作时段；其余时间（含整个周末、节假日）是低峰，价格还是高峰的一半。个人 key 的"快"多半发生在晚上/周末，团队吐槽的"慢"发生在高峰——两边根本不是同一条基准。
   2. **客户端重试/超时**：429/503 时各种 IDE 插件会静默指数退避重试，表现为"卡住不动"；有些客户端默认 60s 超时，而官方排队最长可到 10 分钟（期间以 SSE keep-alive 保活），于是"排队中被客户端掐断→重试→再排队"恶性循环。
   3. **工作负载差异**：agent/IDE 客户端上下文大、输出长（模型支持 1M 上下文 / 384K 输出）、常带长思考；同一 prompt 冷启动（缓存未命中）与命中缓存的 prefill 速度差很多。个人自测往往是短对话，天然更快。
   4. **中间层瓶颈**：若 key 是经网关/中转站（one-api、LiteLLM、第三方中转）分发的，瓶颈多半在那一层：并发上限、超时、无流式、同步写日志、甚至超售。
   5. **账号真撞并发上限或 key 泄漏**：出现 429 才是账号级证据；泄漏被外部刷也会让账号长期贴着上限。
3. 真要处理，正确杠杆是：**错峰 + 扩并发（免费）+ user_id 按人隔离 + 客户端参数**，不是换 key。

## 二、30 分钟验证（照做即可，结论以数据为准）

用 `deepseek-bench.py`，**同一台机器、同一时段、同一参数**分别测团队 key 和个人 key：

```bash
pip install requests
python deepseek-bench.py --key sk-团队xx --label 团队key --concurrency 1,4,16 --prompt-tokens 8000 --fresh
python deepseek-bench.py --key sk-个人xx --label 个人key --concurrency 1,4,16 --prompt-tokens 8000 --fresh
# 建议至少跑两轮：高峰一轮（10:00 或 14:00）、低峰一轮（12:30 或 20:00）
# --fresh = 注入随机编号强制缓存未命中，两个 key 都从冷启动开始，对比才公平
```

读结果（脚本末尾也会打印）：
| 现象 | 指向 | 处置 |
|---|---|---|
| TTFT 高但 tok/s 正常 | 排队：高峰拥堵 / 撞并发上限的重试 | 错峰；查 429 计数；扩容 |
| tok/s 明显低 | 服务端繁忙 / 输出长 / 长思考模型 | 错峰；换 flash；缩短输出 |
| 出现 429 | 账号级并发超限（与用哪个 key 无关） | 申请扩容 + user_id 隔离 |
| 出现 503 | 服务端过载（官方建议稍后重试） | 错峰；客户端退避要温和 |
| 冷启动慢、重复请求快 | 缓存命中差异 | 固定前缀、复用会话 |

另外三项人工检查：
- 抓各人客户端日志：**429 / 503 / 超时 / 重试次数**，以及客户端超时设置（建议 ≥300s，重试 ≤3 次带抖动）。
- 若经网关/中转：**绕开直连官方再测同一 key**，对比一轮。
- 用量面板：有没有明显不属于本团队的调用量（key 泄漏嫌疑）。

## 二·补充：确认「没有 429、只是体感慢」之后的排查顺序

没有 429 ⇒ 排除"账号并发撞顶"；但**不能**排除 503（服务端过载）和客户端超时重试——这两种都不报 429。按信息量从大到小查：

**检查 A（1 分钟，最先做）——两边是不是打在同一个接入点？**
看各自客户端配置里的 `base_url`：是官方 `https://api.deepseek.com`，还是中转/网关域名（如自建 one-api、第三方中转）。这是整条排查路径的分叉点：
- 团队走中转、个人走官方 → 进入「三、自建中转（子 key 分发）专项排查」——排队、转发、缓冲、超售都在这一层。
- 两边都是官方 → 进入检查 B。

**检查 B（10 分钟）——同机同时段双 key A/B，把体感变成数字。**
```bash
python deepseek-bench.py --key sk-团队xx --label 团队key --concurrency 1,4 --prompt-tokens 8000 --fresh
python deepseek-bench.py --key sk-个人xx --label 个人key --concurrency 1,4 --prompt-tokens 8000 --fresh
```
间隔尽量短（<5 分钟），各跑 3 批取中位数，比 TTFT 和 tok/s。结论：
- 团队 key 明显慢 → 进检查 C、D 继续定位；
- 两个 key 基本一样快 → "体感慢"是场景差异（时段/上下文/客户端），进检查 D 对照当时场景。

**检查 C——同一个团队 key，换个"组内负载"时刻再测一轮。**
午休（12:30）或晚上测一次 vs 全员开工（10:00/14:00）测一次：
- 无人使用时段也慢 → 服务端高峰拥堵（与共用无关，错峰即可）；
- 组内都开工时才慢 → 组内并发互相挤占，先给每人配 `user_id`（扩容账号下才隔离）或网关按人限流。

**检查 D——查客户端与工作负载（不需要写代码）。**
- 客户端日志里 429/503/超时/重试各多少次？（没有 429 也要看 503）
- 客户端超时设置多少？<300s 的调到 300–600s，重试 ≤3 次。
- 是否流式输出？非流式的长请求全程无输出，最像"卡死"。
- 同一任务的输入上下文多大、用的哪个模型？和"个人 key 用着快"时的场景是否可比。

## 三、自建中转（子 key 分发）专项排查

已确认团队路径：**成员客户端 →（自建中转，分发子 key）→ 上游**；个人路径：官方直连。嫌疑面收窄到"中转这一跳"，但先证明、再修。

**第 0 步：看中转的上游配置——上游到底是官方还是又一层中转？**
查中转的渠道配置里上游 `base_url`：若是官方 `api.deepseek.com`，往下走；若还是另一个中转/转售方，慢的根源可能在上游那层，先把这个问清楚。

**第一步：定位慢在哪一段（三分测法，脚本支持 `--base-url`）**

```bash
# ① 成员机器 → 经中转（用分配到的子 key）。同机先测一段网络时延：
curl -s -o /dev/null -w "dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s\n" \
  https://<中转域名>/v1/models -H "Authorization: Bearer <子key>"

python deepseek-bench.py --key <子key>  --base-url https://<中转域名>/v1 --label 经中转   --prompt-tokens 8000 --fresh
# ② 同一台机器、同一时段 → 官方直连（借一把官方 key 做对照）
python deepseek-bench.py --key <官方key> --label 官方直连 --prompt-tokens 8000 --fresh
# ③ 中转服务器本机 → 官方直连（在中转机上跑，测上游与时段）
python deepseek-bench.py --key <上游官方key> --label 中转机直连官方 --prompt-tokens 8000 --fresh
```

判读：
| ①成员→中转 | ③中转→官方 | 结论 |
|---|---|---|
| 慢 | 快 | 问题在中转这一跳：线路 / 服务器 / 代理配置 / 限流 |
| 慢 | 慢 | 上游高峰拥堵，与中转无关（错峰即可） |
| 快 | 慢 | 上游慢但被中转缓冲掩盖，仍按上游处理 |

再看形态：① 的 TTFT 高但 tok/s 正常 → 排队类（子 key 限流 / 渠道限流 / 反代缓冲）；tok/s 低 → 带宽或服务器资源不足。

**第二步：中转侧五处必查（自建的，都查得到）**

1. **反代的流式缓冲（头号嫌疑）**：若成员→中转经 nginx，SSE 必须 `proxy_buffering off; proxy_cache off; proxy_read_timeout 600s;`。症状：流式本来"一个字一个字蹦"，经中转变成"一段一段蹦"，或首字明显变慢。
2. **子 key 自身的限速**：one-api / new-api 支持令牌级 RPM / 并发上限。如果给每人配了低限额（比如并发 1–2、60 RPM），单人在 agent 里发并行请求就会排队——表现是"每个请求都要等"，全组人人如此。这是自建中转体感慢最常见的原因。
3. **渠道限流与上游配置**：渠道是否设了并发 / RPM 上限；上游是几把 key、是否混了多渠道（混渠道会忽快忽慢）；上游超时值是否 <300s（会让长请求被掐断重发）。
4. **服务器资源与连接复用**：CPU / 内存 / 负载 / **带宽**（小 VPS 多人并发流式 → 带宽和 CPU 双瓶颈）；是否与 MySQL / Redis 同机；日志是否同步写库（SQLite 高并发写会阻塞）；中转→上游是否 keep-alive 长连接。
5. **部署位置与前置层**：中转机在哪个地域（成员 ping / curl 的 RTT 大不大）；是否套了 Cloudflare / CDN（会增加首字时延，免费版还可能被限速）；成员到中转这段是否走公司网络 / VPN。

**第三步：修（按第二步发现做，通常收益最大的三刀）**
- 反代关缓冲（若是）；
- 放宽或重设子 key / 渠道限流（按人给合理值，而不是一刀切低限额）；
- 升级中转机带宽 / 规格或换更近的地域；上游改多 key 负载。

## 四、本机实测结果与结论（2026-10-08）

对照条件：同一台机器、同一时段、同一参数（deepseek-flash、关闭思考、冷启动 `--fresh`）。

| 路径 | TTFT p50 | 输出吞吐 p50（长输出 1200+ tok） | 并发表现 | 429/503 |
|---|---|---|---|---|
| 官方直连 api.deepseek.com | 0.54–0.79s | **150 tok/s**（3 次：152/150/150） | 16 并发：TTFT 1.79s、150 tok/s | 无 |
| 经自建中转（内网） | 0.58–0.82s | **83 tok/s**（3 次：84/84/83） | 64 并发：TTFT 1.42s、123 tok/s，全部 200 | 无 |

辅助证据：
- **一周真实请求日志**（ZCode 经中转）：484 次请求，仅 2 次重试、4 次失败、**零 429**；真实耗时与输出长度成正比——最慢一条 265 秒 = 1.9 万 token 的长思考输出（73 tok/s，速度本身正常）。
- **分块到达模式**：两条路径的 SSE 块数（1278 vs 1327）和平均块大小（5.0 vs 5.1 字符）几乎一致，说明中转是逐块透传、未重新编码；但块间隔 p90 为 **46ms（中转）vs 18ms（官方）**——流在转发环节被"攒批—释放"式拉长了。
- 本机到中转是内网直连（connect 1.4ms），排除"网络距离"因素。
- **账户归属验证（扣费追踪，回答"两条路径是不是同一账号"）**：证实都记在同一个官方账户下——① 10-03 凌晨 01:00–02:30 的 303 次经中转请求（ZCode 配置自 09-20 起即指向中转），账户余额在同一窗口精确下降 **¥3.55**（与低峰半价费率吻合），其后 21 小时余额零变动；② 今天经中转灌入 80 个已知大小的请求（预估 ¥0.91），数分钟后从余额扣出（该接口扣费有几分钟延迟，30 分钟粒度看是台阶式下降）。→ "经中转 vs 官方直连"是严格的**同账号对照**，账号不是变量。
- **版本更新记录（每次更新后用 `relay-check.py` 复测）**：v1 53% → v2（带更新重启）42% → v3 75%（块间隔 45→30ms、停顿占比 80%→64%）→ **v4 ✅ 达标：吞吐比 102%（经中转 152 vs 官方 149 tok/s）、块间隔 p90 18ms、TTFT 0.80 vs 0.87s**。长任务验收：8192 token 长输出经中转 **47.6s**（172 tok/s）、官方直连 53.3s；并发 1/4/16 全部 200、无 429。**遗留小项**：① 流内停顿节拍仍可见（占比 55%、30ms 桶仍在），但总时长已与官方持平，属可接受余量；② `/v1/models` 仍返回 400（所有 `/v1/*` 走 chat 处理器），若其他工具依赖 list models 会报错，建议顺手修；③ 部署后首批请求出现过一次 15s TTFT 瞬态，数分钟后不可复现（疑冷启动/上游瞬态），留意后续是否复现。
- **停顿指纹（初测，2026-10-08）**：经中转的流 **80% 的时间在停顿**（>20ms 的停顿 316 次/15 秒，单次集中在 30–40ms）；官方直连只有 29%（52 次，多为公网正常抖动）。关键：**剔除停顿后经中转的"有效吞吐"是 358 tok/s，反而高于官方直连的 222 tok/s**——数据早已到达中转、是它按 ~30–40ms 的节奏一批批放出来的。⇒ **瓶颈在转发"写出"路径（flush 定时/攒批、Nagle、或读上游的轮询循环），不是出网带宽/线路**。**带更新的重启后复测（最新代码）吞吐比 45%→42%，仍无改善，且服务行为无变化**（`/v1/models` 仍 400 路由到 chat 处理器；流式响应头仍 `Connection: close`、无 keep-alive）——排除"运行久了积累状态"类原因；**单纯重启不改变结果，判断每次更新是否真的改到流式写出路径，只看 `relay-check.py` 的吞吐比是否 ≥90%**。

**结论**
1. 中转**没有**排队、没有并发限制、没有 429，首 token 速度与官方直连一致；
2. 唯一实锤差异：**流式输出吞吐只有官方直连的 ~55%**——短问答无感，但 agent 长输出（几千到 2 万 token）时长接近翻倍，这正是"体感慢很多"的来源；
3. 根因在中转这一跳的转发环节（缓冲 / Nagle / 出网链路），**不是 DeepSeek 侧，也不是账号共用**——两条路径同为同一账号（扣费追踪已证实），同账号直连即满速。

**在中转服务器本机跑一条命令，即可区分是哪一种：**

```bash
python deepseek-bench.py --key <中转的上游官方key> --base-url https://api.deepseek.com \
  --label 中转机直连官方 --concurrency 1 --repeats 3 --max-tokens 1500 --fresh --no-thinking \
  --prompt-text "Write a detailed 900-word essay about the history of the Great Wall of China. Write the full essay."
```

- 结果 **≥140 tok/s** → 服务器出网正常，问题在转发实现：检查代理代码/反代是否逐块即时 Flush、是否禁用 Nagle（TCP_NODELAY）、nginx 是否 `proxy_buffering off`；
- 结果 **≈83 tok/s** → 服务器到上游的链路或使用的上游渠道本身慢：换线路 / 换上游渠道 / 迁机。

## 五、处置（按成本从低到高）

**第一优先级：修中转（本次实锤的唯一瓶颈，改完约 2 倍提速）**

先用第四节那条命令在中转服务器本机直连官方定位方向：结果 ≥140 tok/s → 问题在**转发实现**；≈83 tok/s → 问题在**服务器出网/上游渠道**。

转发实现排查清单（按嫌疑排序）：
1. **转发循环里的 ~30–40ms 定时/攒批（头号嫌疑）**：实测停顿单次集中在 30–40ms、占流式时间的 80%，而剔除停顿的有效吞吐高达 358 tok/s（数据早已在中转手里）——典型"攒一批、按定时放一批"。改成每收到一块立即写出并 Flush（Go `http.Flusher.Flush()`、Python `await resp.write()` + `drain()`）；
2. 两端 socket 都设 `TCP_NODELAY`（Nagle + 延迟 ACK 同样会造出 40ms 级停顿）；读上游不要用带 timeout 的小缓冲轮询循环；
3. 转发路径不做 JSON 解析/重组、不重新编码；
4. 若前面挂 nginx：`proxy_buffering off; proxy_cache off; proxy_read_timeout 600s;` + `X-Accel-Buffering: no`；
5. 中转→上游用 keep-alive 长连接，避免每请求重握手。

出网/渠道问题的处理：实测中转机到 api.deepseek.com 的延迟与丢包，换机房地域或换成官方直签渠道。

**验收标准（可判定）**
- `relay-check.py` 吞吐比 ≥ 90%（经中转 ≥135 tok/s）、块间隔 p90 回到 15–20ms；
- 一条 1.9 万 token 的长输出从 ~265 秒降到 ~130–140 秒；
- 全程无 429/503、零重试。

**第二优先级：使用习惯（当天可做）**
- 客户端：开流式；超时调 300–600s；重试封顶 2–3 次（指数退避 + 抖动）；简单任务用 `deepseek-flash` + 关思考，长任务才开思考。
- 重活排低峰：北京时间 12–14 点、18:00 后、周末——又快又半价（**已实证**：10-03 凌晨 303 次请求按低峰费率计费）。
- 提高缓存命中：系统提示、长文档固定放前缀、会话别频繁重建。
- 每个客户端自限并发 2–4 个。

**本场景已排除、不必再做的**
- **多发 key**：官方并发按账号计、与 key 数量无关；**申请扩容**：解决的是并发上限→429，你们零 429，不是速度解药；
- 排查客户端重试 / 网络距离：一周 484 条日志仅 2 次重试；本机到中转是内网 1.4ms；
- 多供应商池等架构改造：等中转修好、体检通过后再评估。

## 六、可直接发群里/发给 QA 的话术
