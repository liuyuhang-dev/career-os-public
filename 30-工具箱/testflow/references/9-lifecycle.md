# 9 · 全流程与缺口清单

从需求到上线、到线上玩家探索的完整地图,以及每个阶段需要什么、现在缺什么。

这份文档用来做两件事:**跟团队对齐能承诺什么**、**排优先级**。

---

## 一、能做 / 不能做

### A 档:完全确定,能进 CI

不需要视觉、不依赖平台配合,判定结果稳定可复现。

| 能力 | 依赖 | 今天可用 |
|---|---|---|
| 需求覆盖率 / 期望覆盖率 / 复核状态 三道闸门 | 无 | 是 |
| 数值与货币不变量(不变负、不超上限) | 客户端状态上报 | 否 |
| 结算精确性(界面显示 vs 实际存储) | 客户端状态上报 | 否 |
| 存档一致性、跨端一致 | 客户端状态上报 | 否 |
| 断线重连状态收敛、重复上报幂等 | 客户端状态上报 + 网络可注入 | 否 |
| 背包无重复条目、道具不超上限 | 客户端状态上报 | 否 |
| 崩溃 / ANR 检测 | adb logcat | 装 adb 后可用 |
| 启动耗时 | adb | 装 adb 后可用 |
| 固定随机种子下的数值复算 | 客户端提供种子开关 | 否 |

### B 档:视觉封闭断言,可复现性中等

固定区域 + 固定是/否问题,判定结果基本可复现。**这是显示层正确性的主要手段,也是人审的标准。**

| 能力 | 例子 |
|---|---|
| 元素是否出现 | 「屏幕底部是否出现带『立即结算』字样的按钮?」 |
| 文案是否正确 | 「屏幕中央是否出现包含『金币不足』字样的提示?」 |
| 数值显示是否合法 | 「顶部金币数值是否显示为不含『-』号的整数?」 |
| 布局是否错乱 | 「底部三个按钮是否互不重叠?」 |
| 画面是否健康 | 白屏、黑屏、花屏、贴图缺失 |
| 关键路径是否走通 | 登录 → 开局 → 单局 → 结算 → 返回 |

### C 档:探索发现,不要求复现

只要求发现率,不判通过与否。产出 bug 候选。

- 像玩家一样看画面操作,发现流程断裂、死路、异常弹窗
- 随机/压力操作撞崩溃与卡死
- 长时间连续游玩找长尾缺陷
- **适合慢节奏、回合制、卡牌、模拟经营;快节奏动作类只能做随机压力测试,做不到能力型探索**

### D 档:回放回归,可复现性高

把 C 档跑通的轨迹固化成脚本,之后回归靠回放,不再依赖模型重现决策。

### E 档:只能人工

- 手感、打击感、动效流畅度
- 难度曲线、趣味性、新手引导的体验
- 真实弱网体感(能测数值收敛,测不了"卡不卡")
- 美术质量、品牌一致性

### 不能做(硬限制,不是方案缺陷)

| 做不到 | 原因 |
|---|---|
| 帧级时序操作(闪避、连招、格挡) | VLM 推理是秒级,游戏是 60fps |
| 多指同时操作(双摇杆、边移动边瞄准、捏合) | `adb shell input` 只注入一对 down/up,无真正多点 |
| 真实支付链路 | 无沙箱自动支付路径 |
| 纯视觉判定游戏内部数值正确性 | 界面显示 100 不代表内部存了 100 |
| 抖音生产「高性能」渲染模式的功能自动化 | 该模式与调试器互斥(平台硬限制) |
| iOS 真机精确弱网 | Network Link Conditioner 只对模拟器生效 |
| 微信小游戏节点树自动化 | MiniGameTest 只接入 Cocos/Laya/Egret,Unity 不在列表 |
| 抖音小游戏官方自动化 | 平台完全没有(CLI 只能 preview/upload) |
| 崩溃根因定位 | 能收集栈,定位到具体代码要研发 |
| 覆盖率百分比 | 业界没有可信公开基线,任何百分比都应视为营销数字 |

## 二、十二个阶段:从需求到线上

| # | 阶段 | 判定模式 | AI 做 | 人做 | 门禁 |
|---|---|---|---|---|---|
| 0 | 体验与理解 | — | 结构化遍历游戏,出理解文档 + bug 候选 | **复核理解文档** | 系统清单完整、入口路径正确 |
| 1 | 需求拆解 | — | 需求 → 带编号的可验收子句 | 确认歧义与冲突 | 无未决歧义 |
| 2 | 用例生成 | — | 按需求 + 通用不变量生成用例 | — | — |
| 3 | 断言转换 | — | 用例 → 机器可读断言 | — | — |
| 4 | 复核 | — | 出复核单 | **逐条批准/驳回** | `validate_cases.py` 退出 0 |
| 5 | 冒烟验证 | vision-closed | 跑纵向切片:启动→进游戏→一条路径→截图→开单 | 看结果 | 环境链路通 |
| 6 | 功能回归 | state-report + vision-closed | 执行 + 判定 + 提 bug | 看报告 | P0/P1 全绿 |
| 7 | 弱网专项 | state-report(收敛) | 造弱网 + 判定收敛 | — | 收敛断言全绿 |
| 8 | 探索测试 | explore | 像玩家一样玩,报异常 | **复核 bug 候选** | 误报率可接受 |
| 9 | 兼容与性能 | 采集类 | 跑机型矩阵、采 FPS/内存/启动耗时 | 定机型档位 | 无崩溃、无 P0 |
| 10 | **上线真机回归** | replay + state-report | 回放回归集 + 数值断言 | **放行决策** | 见下方专节 |
| 11 | **线上玩家探索** | explore + 反馈回流 | 模拟玩家长时游玩;归因线上反馈 | 定优先级 | 见下方专节 |

**阶段 4 是唯一需要"逐条过"的人工关卡。** 其他阶段的复核可以抽样,只有用例复核必须每条都看——因为 AI 同时写用例和断言,复核是唯一能拦住"把现有 bug 写成期望"的环节。

不过**人工并没有被移除**,只是分布在不同阶段:**阶段 4** 逐条批准用例、**阶段 10** 发版放行决策、**阶段 11** 线上缺陷归因与优先级。这三处不能自动化,也不该假装能。

## 三、上线真机回归(阶段 10)

### 目标

在**候选包**上确认没有退化,并且这个结论是可复现的。

### 回归集组成

| 来源 | 判定模式 | 覆盖 |
|---|---|---|
| 关键路径回放 | replay | 登录、进入、单局、结算、返回、商城、邮件 |
| 数值与结算断言 | state-report | 货币、结算、存档、等级 |
| 弱网收敛断言 | state-report | 断线重连、离线重放 |
| 冒烟视觉断言 | vision-closed | 关键界面元素与文案 |
| 崩溃与启动 | 采集 | 无新增崩溃、启动耗时不退化 |

### 门禁(建议阈值,需你们定)

- P0 / P1 用例全绿
- **实际执行率 ≥ 90%**(不是通过率——执行率才代表真覆盖)
- 无新增崩溃
- 启动耗时不超过基线 120%
- 所有 skipped/blocked 项有明确原因记录

### 需要提供

- 候选包的安装方式(adb 可安装的包,或微信开发版/体验版)
- 版本号与变更范围(用于判断哪些回归必须跑)
- 性能基线(首版需要人工采一次作为基线)
- 回归集的批准记录(哪些用例是"必须跑"的)

### 现在缺什么

- **回放引擎**(录制/回放未实现)
- 候选包安装与版本记录的自动化
- 回归集的**清单与缺口**已有工具(`regression_set.py`:已复核清单、最近结论与稳定性、
  smoke/regression 选择器、P0/P1 未复核或从未跑过的缺口);**缺的是按版本记录"这版该跑哪些"** ——
  那需要版本号与变更范围(见上一条)
- 性能基线采集(启动耗时 / FPS / 内存)
- CI 触发方式(定时 / 提交触发 / 手动)

## 四、线上玩家探索(阶段 11)

两种含义,都要做,是不同的东西。

### (a) AI 模拟玩家探索

上线后对**线上版本**做长时间探索,找长尾缺陷。

- 判定模式 `explore`,**不判通过/失败,只报异常**
- 手段:随机操作撞崩溃 + 目标驱动游玩走边角路径
- 指标是**发现率**与**误报率**,不是通过率
- 适合慢节奏玩法;快节奏动作类只能做压力测试

**缺什么**:长时间探索的调度与预算控制、异常聚类去重(同一根因的多次崩溃要合并)、探索时长与机型分配的排期。

### (b) 真实玩家反馈回流

**这是线上阶段价值最高、也最容易被漏掉的一环。** 闭环应该是:

```
线上崩溃/客服反馈/玩家视频/低分评论
  → 归因(是哪个系统、哪个状态)
  → 复现(能不能在真机上稳定重现)
  → 生成用例(写成 spec,标注 expect_source=requirement 或 invariant)
  → 进回归集(固化后下次发版必跑)
```

这样每一个线上缺陷都会变成一条永久回归用例,**缺陷库不会只增不减**。

**缺什么**:
- 崩溃上报与客服反馈的收集渠道(需要你们现有的埋点/客服系统对接)
- 归因流程(谁来看、看多久、怎么分派)
- 把反馈转成用例的责任人(否则这个闭环没人推)
- 用例回归集的版本管理(哪些用例对应哪个版本的线上问题)

### 与真机回归的关系

线上发现的缺陷 → 复现 → 生成用例 → **进入下一轮阶段 10 的回归集**。两个阶段是一个环,不是两条线。

## 六、建议的推进顺序

**第一步(不依赖任何外部条件,今天可做)**
把判定轮实现出来,并用现有 fixture 跑通"截图 + 封闭问题 → 判定结论 → 进报告"。这是让整条链闭环的最小一步。

**第二步(需要你)**
授权 computer-use + 接 Android 机 + 装 adb。然后跑阶段 5:启动微信 → 进游戏 → 走完一条关键路径 → 截图取证 → 提 bug 单。这一步会暴露入口自动化这个真问题,值得先撞一次。

**第三步**
实现崩溃/白屏/无响应检测,然后跑一轮探索测试,看发现率与误报率。**这一步决定了探索模式值不值得继续投入。**

**第四步(需要客户端)**
推状态上报,把 A 档能力打开,弱网收敛断言才有依据。

**第五步**
回放引擎 + 回归集 + CI,建立上线真机回归。

**第六步**
线上反馈回流闭环,让阶段 10 和 11 连成环。
