# 2 · 需求拆解(阶段 1)

## 目的

把需求原文拆成**带编号的可验收子句**,让下游的覆盖率校验有确定的对象。

需求覆盖率这道闸门校验的是"每条需求子句是否至少有一条用例",所以子句必须**先编号、再引用**。不先做这一步,覆盖率就是空话。

## 输入与输出

**输入**:`requirements/<feature>.md`(人提供;没有需求文档时跳过本阶段,直接走不变量路线,见 `3-cases.md`)

**输出**:`test-artifacts/<feature>/01-requirements.json`

```json
{
  "feature": "对局结算与货币",
  "source": "requirements/battle-reward.md",
  "clauses": [
    {
      "id": "R-3.2",
      "text": "单局结算后金币按击杀数 × 10 发放,上限 500",
      "source_ref": "requirements/battle-reward.md#L42",
      "kind": "functional",
      "notes": "上限值原文写的是『500』,与另一处『单局上限不超 500』一致"
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `id` | `R-<章>.<序>` 形式,文件内唯一。**这是覆盖率校验的键,不许重复、不许跳号复用** |
| `text` | 子句原文或最小改写。**改写要保义,不确定就抄原文** |
| `source_ref` | 指回需求文档的行/锚点,供人复核时对照 |
| `kind` | `functional` / `performance` / `compatibility` / `ui` / `data` |
| `notes` | 歧义、与别处冲突、疑似错误。**这一栏是给复核人看的重点** |

## 拆解纪律

1. **一条子句只讲一件事。** "结算后发放金币,且连续三局有额外奖励,且金币上限 500" 要拆成三条。混在一起的子句会导出一条用例验三件事,失败时无法定位归属。

2. **不许合并同义子句。** 原文在不同位置重复说了同一件事,保留两条并在 `notes` 里互相引用。合并会掩盖"两处要求不一致"这种真实缺陷。

3. **不许补充原文没有的要求。** 你觉得"显然应该有"的东西(例如"金币不能为负"),放到**不变量**里(阶段 2,`expect_source: "invariant"`),不要伪装成需求。伪装会让复核人以为那是客户要求的。

4. **需求里的实现细节要标出来。** "通过 Redis 计数实现锁定" —— 实现方式不是验收标准,它会在重构后失效。拆解时保留原文但标 `notes: "含实现细节,不可作为断言依据"`,让阶段 3 只取行为部分。

5. **歧义与冲突必须显式上报,不许自行裁决。**

## 无法拆解时的回报格式

不要静默产出残缺的子句表。停下来等澄清:

```
BLOCKED 需求拆解无法完成

需求: requirements/battle-reward.md
问题子句(原文 L42):「结算后按表现发放金币,表现好多发」
无法拆解的原因:
  - 「表现」未定义 —— 是击杀数、伤害值、还是评分?无法得出可判定的验收标准
  - 「多发」无量化 —— 缺具体数值或公式
建议: 补充 ①「表现」的度量定义 ② 各档位发放数量的具体数值或公式
```

同时要报告**冲突**:

```
CONFLICT 需求内部不一致

R-3.2 (L42): 单局金币上限 500
R-5.1 (L88): 单局金币上限 800

建议: 由需求方确认以哪条为准;在此之前这两条都不应生成用例
```

## 需求覆盖率怎么算

`validate_cases.py --requirements <01-requirements.json> --cases <03-cases/>` 做的事:

```
uncovered = {所有 clause.id} - {所有 case.req_refs 的并集}
```

`uncovered` 非空 → 报 `MISSING_REQUIREMENT_COVERAGE`,列出未覆盖的子句。

**注意**:不变量用例的 `req_refs` 为空,不参与需求覆盖率的分子。所以在没有需求文档的项目里这道闸门会整体跳过(校验器会提示 `no requirements provided`),而不是报一堆未覆盖。

## 复核聚焦点

复核人看 `01-requirements.json` 时只需关注三件事:

1. `notes` 里的歧义与冲突 —— 这是拆解的主要价值所在
2. 有没有被"补"出来的需求(标成需求但其实是你自己想的)
3. 有没有漏掉原文的章节(对照 `source_ref` 扫一遍文档结构)

**这一份复核通过后,需求才算冻结。** 之后新增需求要改子句表并重新跑覆盖率。
