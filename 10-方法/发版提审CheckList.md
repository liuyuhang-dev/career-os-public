# IAP 批量提审 CheckList

> 用途：每个批次按此清单打勾执行，避免遗漏导致提审卡住。

## 阶段 0 · 前置确认

> ⚠️ 这四项不确认就开工，会在最后一步才发现卡住。**开工第一天先过这一节**。

- [ ] API 密钥已获取，权限为 `App Manager` 或以上
- [ ] **付费 App 协议已签署且状态为「有效」**
- [ ] App Store 版本存在，状态为「准备提交」
- [ ] 该版本**已关联构建版本**（不是空的）
- [ ] App ID / Bundle ID 与目标一致

---

## 阶段 1 · 数据准备

### 1.1 源表统一

- [ ] 已确认**唯一权威源表**（多份表并存时明确指定哪份为准）
- [ ] 多份表之间做过**差异比对**，差异项已逐条确认
- [ ] ID 命名口径统一（**补零规则一致**，如 `_4` vs `_04` 二选一）
- [ ] 无重复 ID
- [ ] 无空 ID

### 1.2 CSV 生成

- [ ] `product_id` 唯一且非空
- [ ] `purchase_type` 合法（`CONSUMABLE` / `NON_CONSUMABLE` / `NON_RENEWING_SUBSCRIPTION`）
- [ ] **英文名 ≤30 字符**（超长项 = 0）
- [ ] **英文描述 ≤45 字符**（超长项 = 0）
- [ ] 价格按**美分整数**存储，无浮点
- [ ] 审核备注统一且 ≤4000 字符
- [ ] 名字/描述是规则生成的 → **已抽查**是否符合业务语义

### 1.3 素材准备

- [ ] 素材尺寸统一为 **2436×1125**（逐张校验过，不是抽样）
- [ ] 格式 PNG
- [ ] **素材上的价格与计费点定价一致**（不一致的已重绘）
- [ ] 「同素材类型 × 同价格」已聚合，共用图已确认
- [ ] 素材歧义项（多个可用版本）**已由业务方明确指定用哪张**
- [ ] 无素材缺图（缺图数 = 0）

### 1.4 素材归位

- [ ] 已建立「中文名 → `product_id`」映射表
- [ ] 一图多用的情况已**显式登记复用规则**
- [ ] 归位后文件数 = 可提交计费点数
- [ ] **多出/缺少的文件已逐一解释**（多余图、缺源图）

---

## 阶段 2 · 创建 IAP 本体

- [ ] 先跑 `--dry-run` 预演，确认无报错
- [ ] 已查过现存 productId，**只创建缺失的**（幂等）
- [ ] 创建端点使用 `POST /v2/inAppPurchases`（app 在 relationships）
- [ ] 查询使用**分批 `filter[productId]`**（每批 20 个），未拉全量列表
- [ ] 请求间隔 ≥0.3s，429 有退避重试
- [ ] 执行后**逐条回查确认**本体存在

### 僵尸 ID 处理

- [ ] 所有「查不到本体」的 ID 已**逐一探测确认**（含补零/去零变体）
- [ ] 确认真僵尸的已记录数量与清单
- [ ] 误判的已修正（重复 productId 场景下反查会失效）
- [ ] 真僵尸的处置方案已定（跳过 / 先创建本体）

> 检查点：**可提交数 = 总数 − 真僵尸数**，本项数字对得上才算过。

---

## 阶段 3 · 配置元数据

- [ ] 每个 IAP 都有 `version`（本地化挂载点）
- [ ] 每个 IAP 都有 **en-US 本地化**，且内容与 CSV 一致
- [ ] 每个 IAP 都有**价格时间表**（`priceSchedule` 已设）
- [ ] 定价地区基准正确（如 USA）
- [ ] 价格档位与源表**逐一对应**（不是近似匹配）
- [ ] 审核备注已写入

---

## 阶段 4 · 上传审核截图

> ⚠️ 最容易翻车的环节。**先冒烟 2～3 个，再全量**。

### 上传前

- [ ] 待上传图目录已最终校验：**数量 = 可提交数**，缺失 = 0，尺寸全合规
- [ ] 已用**真实成品图**（2436×1125），**没有误用 xlsx 内嵌缩略图**
- [ ] 图片文件名 = `product_id.png`
- [ ] **已体检过 version 状态**，识别出处于 `READY_FOR_REVIEW` 的项（这类媒体被锁，换不了图）

> 💡 上一项建议在**批次开始前**就跑：送审中的版本会锁死媒体资源，跑到最后才发现会白费功夫。

### 冒烟验证

- [ ] 先跑 **3 个**试用
- [ ] 冒烟结果终态为 `COMPLETE`（不是 `UPLOAD_COMPLETE`）
- [ ] 冒烟通过后才全量

### 全量上传

- [ ] commit 请求体 `type` = `inAppPurchaseAppStoreReviewScreenshots`（**注意 `Store`**）
- [ ] 换图场景已删旧图，并**等待异步删除落盘**（≥2.5s）
- [ ] 终态判定使用**轮询**（超时 300s、间隔 3s），非"查一次"
- [ ] 只认 `COMPLETE` / `FAILED` 为终态，中间态继续等
- [ ] 请求间隔 ≥0.5s
- [ ] 断点续跑生效（已成功的跳过，不重复传）

### 上传后

- [ ] 全量回查，统计 `COMPLETE` 数量
- [ ] **失败项已逐条看原因**（不是直接重跑）
- [ ] 失败项已重跑至归零，或已记录明确的遗留原因

---

## 阶段 5 · 配置供应地区

- [ ] 每个 IAP 都已配置供应地区（缺 = 无法提审）
- [ ] 地区范围符合业务要求（如「除中国外全部」= 174 个地区）
- [ ] 排除地区已确认（如排除 CHN）
- [ ] 幂等执行过（409 视为成功），无重复创建
- [ ] 未使用 `PATCH` 修改地区关系（会 403）

---

## 阶段 6 · 提审

- [ ] 提审前**跑一次全程体检**，确认无遗留缺失
- [ ] 体检结论：`ALL_OK` 数量 + 各缺失分类数量已记录
- [ ] 所有缺失项要么已修复，要么**已明确接受并说明原因**
- [ ] 版本页已把本批 IAP **挂进版本**
- [ ] 挂载数量与 CSV **核对一致**
- [ ] 审核备注 / 演示说明已填
- [ ] 点「添加以供审核」，处理完提交前校验拦截
- [ ] 提交成功，状态进入「等待审核」

---

## 阶段 7 · 提审后跟进

- [ ] 已记录提交时间
- [ ] 持续跟踪状态（24～48h 常规）
- [ ] 被拒项已逐条看拒绝原因并处理
- [ ] 被拒项修改后**重新挂版本提审**
- [ ] 全部批准后，确认各地区陆续生效（1～24h）
- [ ] 本批次执行记录已归档（含报告文件）

## 附录 A · 数量一致性检查

> 批量作业最容易"数字对不上"。以下每组数字必须自洽。

| 检查项 | 公式 | 本批次实际 |
|---|---|---|
| 可提交数 | = 总数 − 真僵尸数 | |
| 素材文件数 | = 可提交数（含复用规则） | |
| 归位后文件数 | = 可提交数 | |
| 待上传图数 | = 可提交数 | |
| 上传成功数 | = 上传目标数（失败为 0） | |
| 供应地区已配数 | = 可提交数 | |
| 挂进版本数 | = 本批提审数 | |

**任一项对不上，必须先解释清楚再继续。**

## 附录 B · 高频错误速查

| 看到这个 | 先查这里 |
|---|---|
| 「请为所选平台添加 App 版本」 | 阶段 0：有无「准备提交」的 App 版本 |
| 409 `ENTITY_ERROR.WRONG_TYPE` | 阶段 4：commit body 的 `type` 是否漏写 `Store` |
| 停在 `UPLOAD_COMPLETE` | 阶段 4：**这是中间态，不是失败**，继续轮询 |
| `IMAGE_INCORRECT_DIMENSIONS` | 阶段 1.3：是否误用了缩略图 |
| 403 `availableTerritories` | 阶段 5：是否用了 PATCH 改地区 |
| 429 `RATE_LIMIT_EXCEEDED` | 全局：请求间隔是否够 |
| 提示某 IAP 缺元数据 | 阶段 3/4/5：本地化/截图/定价/地区 缺哪项 |
| 计费点"本体不存在" | 阶段 2：源表 ID 与 ASC 实际 ID 是否一致（补零） |
| 删图报 `MEDIA_ASSET_DELETE_NOT_ALLOWED` | 阶段 4：version 是否已 `READY_FOR_REVIEW`（媒体被锁） |

## 附录 C · 留档要求

批次结束后，以下文件需归档：

| 文件 | 内容 |
|---|---|
| 本 CheckList | 已打勾的版本 |
| CSV 配置表 | 本批唯一事实源 |
| 体检报告 | ASC 真实状态快照 |
| 上传报告 | 截图上传结果（成功/失败清单） |
| 问题记录 | 本批遇到的坑（回填到 `../提审问题汇总_*.md`） |

> **留档目的**：下一次同类批次可直接参考，避免重复踩坑；出现争议时可回溯。
