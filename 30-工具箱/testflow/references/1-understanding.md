# 1 · 体验与理解(阶段 0)

这是流水线的第一步,也是**杠杆最高的一步**:理解文档错了,下游全部用例都错。

## 目的

第一次接触一个游戏时,先产出一份**游戏理解文档**。它回答"这个游戏有什么、长什么样、从哪进",不回答"它应该怎样"。

理解文档同时是后面三个阶段的前提:

- **给用例作者**:界面与系统的命名、导航路径、元素清单 → 用来写操作步骤
- **给 `vision-closed` 断言**:词汇原料(如"带『结算』字样的按钮") → 开放提问不可复现,封闭提问需要准确的名词
- **给人复核**:一份系统地图比五十条用例便宜得多,这是人工投入回报最高的一处

**它不提供期望。** 见规矩二。

## 执行方式:结构化系统遍历,不是自由游玩

目标是**逐个访问每个界面与系统入口并记录元素与状态**,不是打赢对局。

这么做的理由:
- 成本可控(不需要打到后期才能看到系统)
- 理解文档可靠(不依赖模型游戏水平)
- **不受"AI 打游戏行不行"影响** —— 对局 fumble 没关系,需要的是看清系统

### 遍历顺序

1. **启动与首屏** —— 冷启动耗时、加载页、公告弹窗、隐私协议、登录/授权
2. **新手引导** —— **免费的结构化导览**,会依次展示核心系统。全程截图并记录引导指向的每个界面
3. **主界面** —— 记录所有入口按钮及其位置(归一化坐标)、每个入口通向哪里
4. **逐个系统界面** —— 按主界面入口顺序访问;每个界面记录:关键元素、可点击项、展示的数值与货币、返回路径
5. **设置 / 帮助 / 教程 / 公告** —— **高质量理解来源**,文本里常有玩法规则、数值说明、活动规则原文
6. **边界入口** —— 商城、充值、(若有)排行榜、邮件、活动中心

### 记录纪律

- 每一步 **截图并落盘**,命名体现界面与状态(`01-launch.png`、`07-shop.png`)
- 坐标只记**归一化比例(0..1)**,不记像素
- 遇到异常(白屏、文字截断、元素重叠、无响应、报错弹窗)**当场记录并单独截图**,写进"已知异常",同时作为 bug 候选
- 不确定的推断要标 `(待确认)`,不要写成事实

## 理解文档格式

写到 `understanding/<game>.md`,用 `assets/understanding-template.md`。

**必须在文件顶部标记来源属性:**

```markdown
> **来源:观察所得。** 本文件由真机结构化遍历产出,描述"当前实际行为",可能包含实现缺陷。
> 它不包含期望,不可作为验收标准。期望只能来自需求文档或通用正确性不变量。
```

这个标记不是形式主义。没有它,下游很容易把"观察到的行为"当成"应该的行为"。

## 文档内容清单

| 章节 | 内容 | 下游用途 |
|---|---|---|
| 基本信息 | 宿主(微信/抖音)、包名/AppID、引擎、版本、测试机、测试账号 | 执行环境 |
| 核心循环 | 一局/一轮的完整流程与产出 | 关键路径用例 |
| 系统清单 | 每个系统一句话说明 + 是否可独立进入 | 覆盖率检查 |
| 界面地图 | 界面 → 入口路径 → 关键元素表(归一化坐标) | 操作步骤、视觉断言区域 |
| 状态机 | 主界面/对局中/结算/离线/断线重连等状态与迁移 | 弱网与异常用例 |
| 资源与经济 | 货币种类、来源与消耗、上限、是否显示为数值 | 不变量用例 |
| UI 元素词汇表 | **界面中实际出现的文案与按钮名**,逐字抄录 | `vision-closed` 断言的 `question` 与 `region` |
| 已知异常 | 遍历中观察到的异常 + 截图 | bug 候选 |

### UI 元素词汇表是最容易被低估的一节

视觉断言的质量完全取决于这里。开放提问("结算页面正常吗")不可复现;封闭提问需要**准确的文案**:

- 差:`确认按钮`
- 好:`带『立即结算』字样的按钮`(逐字抄录屏幕上的文字,不要改写、不要翻译、不要补标点)

抄录时注意:同名文案出现在多个界面时要标出界面;图标型按钮没有文字时,描述其图形特征与相对位置,并标注"仅图形,OCR 不可用"。

## 产出物

1. `understanding/<game>.md` —— 理解文档
2. `test-artifacts/<feature>/04-runs/evidence/understanding/` —— 遍历过程截图
3. bug 候选清单(直接写进理解文档的"已知异常",或单独列出)

## 复核

理解文档**必须由人复核后**才能进入阶段 2。复核聚焦三件事:

1. **系统清单是否完整** —— 有没有漏掉整个系统(漏了系统 = 漏了整片需求)
2. **界面地图的入口路径是否正确** —— 路径错了,所有导航类用例都会失败,而且会被误报成 bug
3. **已知异常的分类** —— 哪些确实是异常(→ bug 候选),哪些是设计如此(→ 从清单移除,否则会变成噪音)

复核通过后把 `understanding/<game>.md` 顶部的来源标记补上复核人与日期。

## 与探索测试的关系

**同一趟遍历的两种产出**:理解文档 + bug 候选。不需要跑两遍。

区别在判定模式:探索测试用 `judge: "explore"`,**不判通过/失败,只报异常**。它的产出是 bug 候选,进 `05-bugs/` 或理解文档的"已知异常"。

若某条探索路径值得长期跟踪,**把它固化成 `replay` 用例**(见 `4-conversion.md` 与 `5-execution.md`),这是把不可复现的发现变成可复现资产的机制。
