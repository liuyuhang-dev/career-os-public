# 14 · 模块分类与二级节点展开

上游解析只是第一步。**一条需求子句直接变成一行关注点,粒度太粗** ——
策划要的不是"R-3.1 测了吗",而是"**跟这条需求相关的正向、边界、异常、反向,你们都想到了吗**"。
所以中间必须有一步:**AI 把一级节点展开成二级节点**。

---

## 一、层级定义

| 层 | 是什么 | 从哪来 |
|---|---|---|
| **一级节点(父)** | **模块** —— 需求模块名 / 配置表名 / 代码模块 | 上游三源合并(见第二节) |
| **二级节点(子)** | **具体关注点** —— 一条一行,可判、可归因 | **AI 按展开规则生成**,人确认来源与优先级 |
| 判定项 | 一条关注点怎么验(判定模式 / 断言) | 用例(阶段 3),不在本层 |

登记册里就两列表达这个层级:`模块`(父) + `上游引用`(这条二级节点归因到哪个上游)。

## 二、模块分类:三源合并成一张模块台账

| 源 | 提供的模块名 | 冲突时 |
|---|---|---|
| 需求文档 | 需求里的功能模块(结算/支付/存档…) | **需求名优先** —— 策划与产品按这个说话 |
| 配置表(CSV/字段说明) | 表名(道具表/商店表/怪物表) | 找不到对应需求模块时,作为独立模块 |
| 代码模块 | 目录/文件名(ShopManager、OrderService) | **只用来定位"测哪里"**;模块名不当作对外口径 |

**合并规则**:需求模块为骨架 → 配置表挂到它服务的模块下(商店表 → 结算/商城模块)→
代码模块作为"实现归属"填在备注里。三源对不上时**由人裁定**(不许 AI 猜),
裁定的结果写进 `cli 命令 --feature` 或登记册的模块列。

## 三、AI 展开规则(按上游类型)

**展开的四条纪律**(违反任一条,展开出来的东西都不能进登记册):

1. **不推期望。** 代码只能告诉我们要测哪里,不能告诉我们"应该是什么"(见 `10-upstreams.md`)。
2. **每条必须可判。** 展开出的关注点要能被一条判定项或一次人工检查回答;写成开放问题不算。
3. **允许"不适用"。** 展开时发现某类确实不涉及(比如本项目没有内购),就写一条"不适用"并给原因,
   而不是留空 —— 留空会让人以为漏了。
4. **来源与优先级由人定。** AI 只展开"要关注什么",不替人决定这条多重要、该谁负责。

### 需求子句 → 四个方向(每个方向至少一条)

| 方向 | 展开提示 | 例子(需求 R-3.1:金币按击杀数 × 10 发放,单局上限 500) |
|---|---|---|
| 正向 | 按需求做到 | 结算后金币增量 = 击杀数 × 10(击杀 8 → +80) |
| 边界 | 上限/下限/金额/数量/时间 | 单局上限 500:击杀 60 时增量为 500(不是 600);击杀 0 时为 0 |
| 异常 | 失败/超时/重复/断线 | 结算请求超时:金币不增不扣(不出现一半入账) |
| 反向 | 需求明确不该发生的 | 重复点结算按钮不重复发放(幂等);金币不出现负数 |

### 配置表列 → 四个方向

| 方向 | 展开提示 |
|---|---|
| 静态自洽 | 引用/范围/枚举(先跑 `check_config.py`,它的检出直接变二级节点) |
| 运行时生效 | 游戏里真的按这条配置跑了吗(改配置 → 行为跟着变?) |
| 边界取值 | 配置的极值在游戏里的表现(0 / 上限 / 非法值) |
| 与需求一致 | 配置数值与需求写的是否一致(不一致就是缺陷) |

### 代码模块 → 四个方向

| 方向 | 展开提示 |
|---|---|
| 分支与边界 | 代码里的 `if` 边界有没有用例(只决定测哪里) |
| 状态机迁移 | 状态切换有没有漏(未确认订单、断线重连) |
| 异常路径 | 报错/重试/超时路径 |
| 幂等与重试 | 重复触发会不会出问题(`scan_idempotency.py` 的检出直接变二级节点) |

### 线上缺陷 → 两个方向

| 方向 | 展开提示 |
|---|---|
| 同根因的其它入口 | 这个缺陷类型在别处会不会也发生(重复支付 → 重复领奖) |
| 该路径的回归 | 修完之后加一条回归用例(进回归集) |

## 四、落地流程(三步,AI 干第二步)

```bash
# 1) 解析上游 → 展开工作单(一级节点 + 待展开提示)
python3 "$SKILL_DIR/scripts/concerns.py" \
  --intake requirements:test-artifacts/<f>/01-requirements.json --feature 结算与数值 \
  --intake config:configs/fields.json --intake code:src/ --intake bugs:test-artifacts/<f>/05-bugs/ \
  --expand-out test-artifacts/<f>/worklist.csv

# 2) AI 按上面的规则,把每个【待展开】行拆成 2-4 条具体关注点(补为什么担心与建议覆盖方式)
#    产出即登记册(同一套列,不用换格式)

# 3) 人确认:来源、优先级、"不适用"的裁定 —— 之后就能跑结论页与封板
python3 "$SKILL_DIR/scripts/concerns.py" --register test-artifacts/<f>/concerns.csv \
  --runs test-artifacts/<f>/04-runs --bugs test-artifacts/<f>/05-bugs \
  --out 置信度结论.md --brief-out 给你关心的事_答复.md
```

**展开一次的成本是一次阅读上游的时间**,之后每次版本回归只更新结论,不重展开。

## 五、真实例子

`examples/concerns-expanded-sample.csv` 是 R-3.1 这一条需求子句展开后的样子:
一条子句 → 6 条二级节点(正向 1、边界 2、异常 1、反向 1、与配置一致 1),
每条都带 `上游引用 R-3.1`。对照 `examples/concerns-sample.csv`(未展开的粗粒度版本)
就能看出这一步的价值:**"R-3.1 测了吗" 和 "上限截断、超时不下发、重复领取都测了吗" 不是一回事。**
