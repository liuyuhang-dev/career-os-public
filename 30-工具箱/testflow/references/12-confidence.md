# 12 · 置信度:怎么证明"他们担心的,我们覆盖到了"

这份文档只回答一个问题:**凭什么说质量是高的?** 答案不是"我们跑了多少用例",
而是"**产品/研发/策划担心的每一条,都能查到覆盖方式与结论;查不到的部分,明明白白写出来**"。

---

## 一、为什么"测试自己的用例清单"证明不了置信度

用例清单能证明"我测了我想测的",证明不了"**你担心的**我覆盖到了"。
产品提一句"金币会不会变成负数",他要的不是我们的用例编号,而是:

> 覆盖了 / 怎么覆盖的 / 结论是什么 / 依据在哪

所以需要一个**关注点登记册**:一条关注点一行,谁提的、怎么覆盖、结论、依据、卡在哪。
登记册的入口有两个:① 产品/研发/策划主动提;② 我们从需求、设计文档、代码、线上反馈里
**提取候选关注点**,再请他们确认(不替他们定义担心什么)。

## 二、五档结论(对外就这么说)

| 结论 | 含义 | 对外口径 |
|---|---|---|
| ✅ 已覆盖并验证 | 有判定项 + **依据核对通过** | 「这条没问题」(可承诺) |
| 🟠 已覆盖并发现缺陷 | 测了,判定失败,已开单 | 「测了,发现缺陷,见 BUG-xxx」 |
| 🟡 覆盖但结论待条件 | 用例与判定已就绪,卡在埋点 / 端点 / 真机 | 「准备好了,结论还没出」 |
| 🔴 未覆盖 | 没有对应用例或工具 | 「还没测,谁在补、什么时候」 |
| ⛔ 做不到 | 平台限制或主观体验 | 「测不了,原因是…」 |

**"做不到"不算缺口**——写清原因就是合格答案;**"未覆盖/待条件"必须写出谁在补、什么时候补**,
否则这个缺口等于没提。

**🟠 这一档是专门为"缺陷不能藏在 ✅ 里"加的**:判定失败过的关注点,不许写成"没问题"。

## 三、最关键的一条:**依据要核对,不接受自述**

说「已覆盖并验证」的,`concerns.py --runs <04-runs/>` 会拿着判定项引用**去运行结果里查**:

| 核对结果 | 含义 | 处理 |
|---|---|---|
| 判定项有 pass | 依据成立 | 通过(报告标「✅ 已核对」) |
| 判定项是 fail | 依据成立,但**有已知缺陷** | 报错:结论必须改成 🟠,并挂 bug 单 |
| 判定项是 blocked/pending/skipped | **说了已覆盖,其实没结论** | 报错:改 🟡 并写清卡在哪 |
| 判定项在运行结果里找不到 | 依据不成立 | 报错 |
| 依据没引用判定项、也没指向工具 | 只能算自述 | 提示:补一条可核对的依据 |

**实测效果**:我自己写的样例里,"金币会不会变负 = ✅ 已覆盖并验证"被这一步当场打回 ——
那条判定项其实停在 `pending_judgment`(没接判定端点,根本没结论)。
**假覆盖就是这么被抓住的**,而且它抓的不是别人,是写这份表的人自己。

## 四、四条规矩(机器校验,不靠自觉)

`scripts/concerns.py` 会对登记册逐条判:

1. **不许口头覆盖。** 写「已覆盖并验证」必须给判定强度 + 依据(哪条判定项/哪次运行/哪个工具输出);
   空依据直接判「证据不足」,整册退出码变 1。
2. **缺口必须有出口。** 「未覆盖 / 做不到 / 待条件」都必须写清卡点与补位。
3. **"做不到"必须写原因。** 平台限制、主观体验都行,不写不行。
4. **结论强度分级。** 代码判定 > 工具扫描 > 视觉判定 > 人工。报告里会算给你看:
   强证据几条、弱证据几条 —— **弱证据的结论要先人复核才敢对外说**。

## 五、两个"假信心"来源,机器专门盯着

**① 旧版本的结论冒充本版本的信心。** 上一版测过、这一版没重跑,但它还挂在 ✅ 里 ——
这是最隐蔽的假信心。加 `--since 2026-09-20`(通常填本次封板日),核对时会把
"时间早于这个日期"的依据判为过期,要求重跑或把结论降级成 🟡。

```bash
python3 "$SKILL_DIR/scripts/concerns.py" --register <concerns.csv> --runs <04-runs/>   --since 2026-09-20
# → [stale_evidence] 依据来自 2026-09-18(run-xxx),早于本版本要求的 2026-09-20 ——
#   上一版测过不代表这一版没问题,要么重跑,要么降级并把重跑排上
```

**② 没人想到的盲区。** "没人会主动写『我们没考虑支付』—— 因为没人想到"。
所以按风险类别机械问一遍:**资损(钱/道具/发货)、账号与登录、进度与存档、
崩溃与可用性、合规与隐私、性能** —— 每一类要么有登记(哪怕结论是"做不到"),
要么显式写一条"不适用"。没提到的类别会被点名:

```
[blind_spot] 风险类别「合规与隐私」 — 登记册里没有任何一条关注点提到
             ['隐私', '协议', '合规', '权限'] —— 如果本项目确实不涉及,加一条写清「不适用」
```

## 六、弱证据与过期缺口,也都要看得见

- **弱证据**:判定项有结论、但**没有证据文件**(截图/上报/日志)→ 这个 ✅ 只能算弱证据,
  报告里标出来(不拦,但列出来)。没证据不许判通过是本框架的底线,登记册这一层也不放过。
- **缺口过期**:期限写成日期(`2026-09-30`)而已经过去 → **报警**。缺口可以挂着,
  但不能**假挂着** —— "下个迭代补"写到第三个迭代,那就不叫计划了。
- **趋势**:每次出结论页会往登记册旁边的 `confidence-history.jsonl` 追一行;
  两次以上就有趋势表 —— 未覆盖是在收敛还是变多、放行是否从 ⛔ 变成 ✅。
  汇报时这一行比"通过率 92%"有意义得多。

## 七、给策划/产品的答复(`--brief` / `--brief-out`)

**策划不关心我们跑了多少用例,也不关心什么"信心指数"。他就问三件事:**

> ① 我关心的那条,测了没有? ② 结果是什么? ③ 有没有 bug(单号 + 严重级)?

所以答复就按这三件事组织,一条一行、不用任何内部术语:

```bash
python3 "$SKILL_DIR/scripts/concerns.py" --register <concerns.csv> --runs <04-runs/>   --bugs <05-bugs/> --brief-out 给你关心的事_答复.md
```

```
# 你关心的事:答复 · v1.4.4

**测了没问题 1 条 · 测了发现问题 2 条 · 还没测 2 条 · 结论没出 4 条 · 测不了 1 条**

## 测了,没问题
- [异常与体验] 崩溃后能不能还原现场

## 测了,发现问题(已开单)
- [支付与发货] 同一个订单会不会扣两次 —— 已开单 BUG-001(P0,open)

## 还没测(谁在补、什么时候)
- [热更与资源] 热更下到一半断网会怎样 —— 测试:补热更中断用例·本迭代内

## 结论还没出来(等什么条件)
- [结算与数值] 金币会不会变成负数 —— 卡在 你:给一个视觉端点

## 测不了(原因在册,不是遗漏)
- [核心循环] 手势玩法能不能测 —— 平台限制(adb 不支持多指)
```

**加了 `--bugs` 之后,机器会核对两件事**:说了"发现缺陷"却没写 bug 单号 → 报错;
写的单号在 bug 目录里找不到 → 报错并进放行判断的拒绝理由。
**"后续有没有 bug"要看得见、追得到 —— 这是策划对测试最基本的信任来源。**

## 八、封板:让"放行"成为留痕的动作

放行不该是一次口头结论。`--freeze <版本号>` 把封板做成一个动作:

```bash
python3 "$SKILL_DIR/scripts/concerns.py" --register <concerns.csv> --runs <04-runs/>   --freeze v1.4.4 --out 封板结论_v1.4.4.md
```

它出四件事:① 信心与放行判断 ② **与上次封板对比**(缺口 N→M、这版关了哪些、又开了哪些、
缺陷数变化)③ 归档快照文件(结论页整页附在后面)④ 记一条 `type=freeze` 进历史
(带缺口清单与快照路径)。**下次封板自动能对比上一版** —— "这版比上版更可靠了吗"
有据可查,不用凭记忆。

## 十、放行判断(把置信度变成"能不能发")

```bash
python3 "$SKILL_DIR/scripts/concerns.py" --register <concerns.csv> --runs <04-runs/> --gate-only
# → ✅ 可以放行 / ⛔ 不满足放行条件 + 具体卡在哪
```

三条硬条件:① 产品/研发/策划关心的点不许有「未覆盖」② 说「已覆盖并验证」的依据必须核对通过
③ 「做不到」必须写原因。**已确认的缺陷不阻塞放行**(它走 bug 流程),但会在放行判断里
**作为提示列出来** —— 放行决定必须知道它们。

## 十、关注点从哪来(不指望人想全)

```bash
# 从产物里自动生成候选:run 里的 fail / 没结论的判定项、异常扫描的发现、配置交叉的不一致
python3 "$SKILL_DIR/scripts/concerns.py" --register <concerns.csv> --runs <04-runs/>   --anomalies <anomalies.json> --config-check <config-check.json> --suggest --as-csv
```

输出是**能直接粘进登记册的 CSV 行**(结论与依据已按事实预填),人只需要确认来源与优先级。
**三个入口合起来**:① 产品/研发/策划主动提 ② 我们从需求/设计/代码/线上反馈提取候选 ③ 上面这种机器兜底。

## 十一、用法

```bash
# 登记册模板:assets/concern-register-template.csv(Excel 存 UTF-8 或 GBK 都能读)
python3 "$SKILL_DIR/scripts/concerns.py" --register test-artifacts/<f>/concerns.csv \
  --out test-artifacts/<f>/置信度结论.md
```

产出是**给人看的一页**:一句话结论 → 按来源分组(产品看自己那行)→ 关注点逐条(缺口在前)
→ 信心依据(强度分布)→ 口径。退出码 `0` 干净 / `1` 有未覆盖或证据不足 / `3` 只是卡在外部条件。

## 十二、这套东西跟「跑没跑出 bug」的关系

- **出了 bug ≠ 质量差**,而是"覆盖点被验证了":bug 单本身就是置信度的一部分(它证明判定有效)。
- **没出 bug ≠ 质量高**,除非能说清:覆盖了哪些关注点、依据是什么、哪些没覆盖、为什么。
- 所以汇报里**不要只报通过率**,要报:已覆盖并验证几条、卡在谁那里、未覆盖谁在补、做不到的原因。
  **缺口可见,才是置信度**;缺口不可见,"全绿"只是运气。
