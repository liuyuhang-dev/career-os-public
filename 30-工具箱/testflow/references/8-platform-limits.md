这份文档用来**在立项和汇报时把预期说清楚**。里面每一条都是"做不到",写下来的目的是避免承诺做不到的事。

## ⚠ 先看这里:未经查证的说法

下面几条**没有引用来源,不要作为决策依据**。查清之前必须当作未知。

**2026-09-18 查证一轮的结果:**

| 说法 | 状态 | 结论 |
|---|---|---|
| 「`adb shell svc wifi disable` / `svc data disable` 可直接用于故障注入」 | ✅ **已查证(AOSP 源码)** | **成立,且不需要 root。** AOSP master 里 `frameworks/base/cmds/svc/svc.sh` 就是一层向后兼容翻译:`svc wifi enable/disable` → `cmd wifi set-wifi-enabled enabled/disabled`,`svc data enable/disable` → `cmd phone data enable/disable`。原实现(`WifiCommand`)已在 2019-11-21 的提交 "Migrate WifiCommand to WifiShellCommand" 里移除,`Svc.java` 里直接写着注释 `// 'svc wifi' has been migrated to WifiShellCommand`。设置走的仍是 `WifiServiceImpl.setWifiEnabled()`,权限检查是 `CHANGE_WIFI_STATE`,以 `com.android.shell` 身份调用 —— AOSP 愿意维护这层 shim,说明这条路是官方支持给 shell 用的。**注意:国产 ROM 可能改掉,首次使用请在目标机型上实测。** 备选:`cmd connectivity airplane-mode enable` / `cmd wifi set-wifi-enabled disabled` |
| **「iOS 真机不能用 Network Link Conditioner,只能靠代理近似限速」** | ❌ **仍未查证** | Apple 的 Xcode 文档集里**没有** Network Link Conditioner 这一页(查过 Xcode 文档索引 + "Running your app on simulated or physical devices" + "Enabling Developer Mode on a Device",都不含 network/NLC 字样),所以既不能确认也不能否认。这条仍然是本文弱网能力表的支柱,继续按未知处理。**能一次定性的验证方式:拿一台 iPhone 连 Xcode 打开开发者模式,看「设置 → 开发者」里有没有「网络链路调节器」**(有 = 本文 iOS 弱网评估显著低估) |
| 「`glm-4.5v` 可作为独立判定模型」 | ❌ **仍未查证** | 智谱文档站是 JS 渲染的,静态抓取拿不到模型列表(抓 `open.bigmodel.cn/dev/api` 与 `docs.bigmodel.cn` 都是 0 命中);本次会话无可用的搜索引擎。**要确认就直接查 BigModel 控制台的模型列表与计费页,或拿密钥打一次 `/v1/chat/completions` 传图片试** |

**处理方式**:涉及未查证条目的结论,在报告与方案里都要标注为待验证。不要因为它们看起来合理就当作事实用 —— 本文件其他部分有官方文档链接支撑,这几条没有。

## 一、能力矩阵

| 能力 | Android 真机 (adb) | iOS 真机 (投屏) | 微信云测 | 抖音 |
|---|---|---|---|---|
| 截图 | 可编程落盘 | 需 computer-use 授权 | 云测报告内 | 无 |
| 坐标输入 | `input tap/swipe` | 需投屏可控 | 不适用(脚本模式除外) | 无 |
| 多指同时操作 | **不支持** | **不支持** | 不支持 | 无 |
| 结构化日志 | logcat | 无 | Console log(报告内) | 仅调试面板 |
| 崩溃日志 | 有 | 无 | 报告内 | 无 |
| 性能数据 | 可采(FPS/内存/启动) | 无 | 有(启动/运行/网络) | 仅手工性能工具 |
| 精确弱网 | `tc`/netem(需 root) | 仅代理/AP 限速 | 平台档位 | 无 |
| 节点树 / 元素定位 | 无(游戏是 canvas) | 无 | 仅 Cocos/Laya/Egret | 无 |
| 可编程注入 | 无 | 无 | 无 | 无 |
| 批量脚本化 | 可以 | 勉强 | 提交任务制 | 无 |
| 官方自动化框架 | 无 | 无 | MiniGameTest(Unity 不支持) | **完全没有** |

## 二、按平台的具体限制

### Android 真机

**能做**:启动宿主、进游戏、走关键路径、截图取证、logcat、崩溃收集、性能采样、`tc` 精确弱网、批量脚本化。**这是能力最完整的通道。**

**切网不用 root**:`adb shell svc wifi disable` / `svc data disable` 是 AOSP 官方维护的向后兼容路径(内部翻译成 `cmd wifi set-wifi-enabled disabled` / `cmd phone data disable`,见文首查证结果),可直接用于断网类故障注入。国产 ROM 首次使用需实测。

**做不到**:
- 多指同时操作(边移动边瞄准、双摇杆、捏合)
- 帧级时序精确的操作
- 压力值
- `input swipe` 的插值可能被手势识别器拒绝

**风险**:
- 注入事件与渲染线程竞态,"tap 成功"不等于游戏注册了输入
- 部分机型/系统版本对 `input` 有限制;国产 ROM 的后台管理可能杀进程

### iOS 真机

**能做**:若投屏可控,则可截图 + 像素点击,走关键路径。

**做不到**:多指、logcat(无此机制)、可编程截图落盘。
**待查证**:精确弱网。本文原先断言"Network Link Conditioner 只对模拟器生效",这条**没有来源**;2026-09-18 查了一轮:Apple 的 Xcode 文档集里没有这个功能的页面,所以既没证实也没证伪。**在真机上确认之前,不要把"iOS 侧弱网只能靠代理近似"当作结论** —— 若真机可用,这里的评估是显著低估。

**未验证**:爱思助手投屏**能否反控**。这决定 iOS 通道是否成立,实现前必须验证。

**备选**:WebDriverAgent(需签名配置,真机部署有维护成本,Xcode/iOS 升级会失效)。

### 微信小游戏

**官方自动化存在但 Unity 用不了**:MiniGameTest 的节点树只支持 Cocos Creator / Laya / Egret。

**真机调试能看不能编程**:Console/Sources 可手工调试,**无可编程注入 API,无截图**。真机调试 2.0 仅 iOS、需 Nightly 工具、单设备、需高性能模式、Mac 侧需 libimobiledevice。

**云测是唯一可用的官方真机路径**:智能探索测试(无脚本)+ 自定义测试(录制回放 / MiniGameTest 脚本)。有独立的「Unity」评测标准(偏性能)。云测环境内 `GameGlobal.isTest === true`。

**其他限制**:
- 需要体验版或开发版,每个小游戏只能有一个体验版
- 代码片段上限 1MB
- 系统组件(授权框等)不提供方法获取和操作,自动化前需手工授权
- **免费额度与定价官方未公开**,需开发者账号后台确认

### 抖音小游戏

**没有任何官方自动化能力。** CLI(`tmg`)只能 `login/open/preview/upload`,不执行测试;无本地执行能力,CI 只能构建上传。

**关键限制**:
- **「高性能 / 高性能+」渲染模式与真机调试互斥** → **生产渲染模式无法调试**。这是最影响测试覆盖的一条
- 真机调试 Profiles 仅 Android,iOS 不支持
- 无截图能力
- 权限门槛:设备需白名单;账号绑定**一次性且不可解绑**
- **无官方云测** → 只能第三方云手机(WeTest / Testin / 优测)
- 性能测试工具需人工点击运行、扫码、玩一局、再读报告,**不可脚本化**

**架构同源但工具链不通**:运行时与微信同为 JS VM(无 DOM/BOM,只有 `tt` API,`GameGlobal`,开放数据域),一份代码可同时导出两端。**但调试桥完全不同,不要指望同一个 harness 驱动两端。**

## 三、通用限制(所有平台)

- **canvas 游戏没有 DOM、没有可访问性树** → `uiautomator dump`、Appium 原生定位、XCUITest 元素查询**全部返回空**
- **真实支付无法自动化**(无沙箱自动支付路径)
- **帧级时序、多指手势、手感类用例无法自动化**
- **内部状态一致性缺陷无法靠视觉发现**(需 `state-report`,见 `7-instrumentation.md`)
- 第三方云手机跑微信/抖音需要账号登录,**新设备登录会触发风控**(短信验证、设备锁),这是云端批量的主要障碍

## 四、可承诺 vs 不可承诺

### 可以承诺

- 关键路径能否走通(登录 → 进入 → 单局 → 结算)
- 界面与文案是否符合需求
- 崩溃、卡死、白屏、无响应、无限转圈
- 通用不变量违例(货币变负、道具超上限、文字截断、重复条目)
- 弱网表现与断线重连的**界面层**行为
- 机型适配的粗粒度差异(需多机型)
- 性能基线(FPS/内存/启动耗时,Android 侧)

### 不可以承诺

- 帧级操作与手感
- 多指手势玩法
- 真实支付链路
- 纯视觉判定游戏数值正确性
- **抖音生产高性能渲染模式的功能自动化**
- iOS 侧精确弱网
- "覆盖率 X%"这类数字(业界没有可信的公开基线,任何百分比都应视为营销数字)

## 五、预期管理的说法

给非技术同事解释时用这三句:

1. **"能自动走通关键路径并截图取证,发现问题自动开单"** —— 而不是"能全自动测完游戏"
2. **"数值与结算这类精确判定需要客户端配合加一层状态上报,否则只能看到界面显示对不对"** —— 而不是"能看到游戏内部状态"
3. **"抖音侧平台完全不提供自动化能力,只能做到视觉冒烟 + 第三方云手机;微信侧有官方云测但 Unity 项目的功能自动化仍要自己做"** —— 而不是"两个平台都能全自动测"

## 六、投入产出参考

| 层 | 成本 | 覆盖 | 建议 |
|---|---|---|---|
| 通用不变量用例 + 视觉探索 | 低(今天可开始) | 崩溃、UI 异常、货币/背包不变量 | **先做,立即可用** |
| 关键路径回放回归 | 中(需录一次) | 主流程回归 | 第二优先 |
| 状态上报 + 弱网收敛断言 | 中高(需客户端改造) | 结算精确性、丢档、双倍结算 | 弱网游戏必做,但排第三 |
| iOS 通道 | 中(取决于投屏可控性) | 机型覆盖 | 验证后再投入 |
| 抖音侧 | 高(平台限制大) | 有限 | 最后评估,或只做视觉冒烟 |

## 七、复核提醒

平台文档会变。**这份文档每季度复核一次**,重点检查:

- 抖音是否推出官方自动化或云测
- 微信 MiniGameTest 是否接入 Unity
- 微信云测定价是否公开
- 爱思助手/投屏工具版本是否改变控制能力
