# 10 · 多源上游与交叉验证

这份文档记录一个重要的方向修正:**测试的上游不止需求文档,项目里的配置表、CSV、构建配置、源码都是上游。多源交叉能把测试从纯黑盒升级为三层验证,并补上最便宜、最高产的一层。**

---

## 一、为什么这是升级:原框架起点在最贵的一层

原框架是纯黑盒,只能做"运行时行为是否符合需求"。而项目里其实有三个可验证的层次:

| 层 | 验证什么 | 需要什么 | 成本 | 典型缺陷 |
|---|---|---|---|---|
| **L1 静态自洽** | 描述产品的各个源彼此是否一致 | 需求 / 配置 / 资源清单(**不需运行**) | 极低,可进 CI,可在出包前跑 | 漏配、错配、悬空引用、与需求不符、字段类型错误 |
| **L2 实现一致** | 代码是否按配置 / 需求实现 | 源码 | 中 | 硬编码覆盖配置、读错字段名、死配置、不可达分支 |
| **L3 运行时符合** | 真机行为是否符合这些源 | 设备 + 状态上报 | 高 | 配置未生效、运行时与配置不符、崩溃 |

**原框架只有 L3。** L1 是纯静态分析,零设备依赖,能在构建之前跑完。

而 L1 能发现的缺陷类别,黑盒测试的发现成本极高——要精确构造某个运行时条件才能暴露。**静态检查是零运行成本。这是整条线上投入产出比最高的一段。**

---

## 二、上游源清单

| 源 | 形态 | 能提供什么 | 可信度 |
|---|---|---|---|
| 需求文档 | prose | 应然(客户意图) | 高,但常缺失或模糊 |
| **配置表** | CSV / JSON / Excel | 应然(策划意图)+ 具体数值 | 高,但可能是从实现反推的 |
| 构建配置 | 分包表 / 资源清单 / 渠道配置 | 应然(打包规则) | 高 |
| 源码 | 各种语言 | **覆盖目标**(分支、边界、状态机) | **不提供期望** |
| 运行时数据 | 状态上报 / 日志 / 埋点 | 实然 | 只能当实然 |
| 游戏理解文档 | 观察所得 | 名词与地图 | 不含期望 |

## 三、交叉矩阵

六对源,每对对应一类独立的缺陷。这是多源思路的干货部分。

| 源对 | 能发现 | 检测方式 | 层 |
|---|---|---|---|
| **配置 × 配置** | 表间悬空引用、同一条目在两张表冲突、字段缺失 / 类型错误 / 超范围 | 纯静态,可全自动 | L1 |
| 需求 × 配置 | 需求要求的功能没配、配置数值与需求不符 | 语义比对,AI + 人复核 | L1 |
| 需求 × 代码 | 需求未实现、实现语义与需求不同 | AI 定位代码 | L2 |
| 配置 × 代码 | 硬编码覆盖配置、读错字段名、死配置(配了从不读)、不可达配置组合 | AI 定位代码 | L2 |
| 配置 × 运行时 | 配置未生效、实际行为与配置不符 | 真机 + 状态上报 | L3 |
| 需求/配置 × 运行时 | 功能缺失、行为错误 | 真机(原框架能力) | L3 |

### 「配置 × 配置」应该做成流水线的第一道检查

理由:纯静态、可全自动、零设备依赖、不需要模型判断,而且发现的都是真实缺陷。

具体检查项:

- **悬空引用**:道具表引用的图标不存在;关卡表引用的怪 id 不在怪物表;商店表引用的道具 id 不存在
- **主键重复**:同 id 两行
- **字段缺失 / 空值**:必填列为空
- **类型与范围**:数值列出现非数字、负数、超出字段说明的范围
- **枚举越界**:类型字段的值不在合法枚举内
- **表间一致性**:两张表对同一实体描述不同(道具表说品质=3,品质表里没有 3)
- **孤立行**:配置了但引用它的地方都没有(可能是废弃配置,也可能是漏接)

**这一类检查是确定性的,不需要 AI 判断,应该写成脚本而不是让模型看。**

## 四、必须写死的边界:代码只回答"测哪里",不回答"应该是什么"

这条不写死,整个体系会退化成"用实现验证实现"——这是最隐蔽也最致命的坑。

- 代码里有 `if kill > 5 then reward = kill * 10`
  → 只意味着「这里有个 >5 的边界值得覆盖」
  → **不意味着**「kill > 5 时应该发 kill × 10」
- 期望仍然只能来自:需求、配置、通用不变量、源间一致性
- 所以:**`expect_source` 的枚举里永远不能有 `code`。校验器必须硬编码这条。**

这就是规矩二(期望不能来自观察)在代码场景下的延伸。代码是"实现",不是"应然"。

### 代码的合法用途

| 用途 | 产出 |
|---|---|
| 提取分支与边界 | 等价类划分、边界值用例的**测试点** |
| 提取状态机 | 状态迁移覆盖的**测试点** |
| 提取异常处理路径 | 异常路径用例的**测试点** |
| 提取硬编码常量 | 与配置交叉的**输入**(配置 × 代码的入口) |
| 找出配置空间里不可达的组合 | 既省测试量,本身也可能是缺陷 |

---

## 五、期望来源重新定义

原来是三类,现在扩到四类,并明确禁止两类:

| 来源 | `expect_source` | 需要带 | 说明 |
|---|---|---|---|
| 需求文档 | `requirement` | `req_refs` | 客户意图 |
| **配置表** | `config` | `config_refs`(表 + 行) | **新增。** 策划意图 |
| 通用不变量 | `invariant` | — | 不需外部依据 |
| **源间一致性** | `consistency` | `consistency_refs`(源对) | **新增。** 期望是"两个源应当一致" |
| 源码实现 | —— | —— | **禁止** |
| 观察到的运行时行为 | —— | —— | **禁止** |

### 为什么 `config` 要单独成类,不并进 `requirement`

1. **可信度不同** —— 配置可能是从有 bug 的实现反推出来的,需求是独立表达的。复核时人要能分辨。
2. **失效模式不同** —— 配置改了,用例要跟着改;需求改了,配置可能要跟着改。两者影响面不同。
3. **复核关注点不同** —— 需求类要问"这是需求说的吗",配置类要问"这条配置本身对吗、它和需求一致吗"。

## 六、新增用例类别:一致性用例

它不是"验证功能",而是"验证多个源描述同一件事时是否自洽"。

```
用例: 道具表引用的图标资源必须存在
- ID: CONS-CFG-C01
- 来源: consistency
- 源对: configs/item.csv × assets/icons/
- 检查: item.csv 每行的 icon 字段都能在资源目录找到同名文件
- 期望: 无悬空引用
```

这类用例大多**可以完全机械化**,不需要模型判断,应该优先做成脚本而不是用例文件。

需要用 AI 判断的是语义层的一致性,例如:

```
用例: 结算金币上限与需求一致
- ID: CONS-REQ-C01
- 来源: consistency
- 源对: requirements/battle-reward.md (R-3.1) × configs/battle.csv (settle_coin_cap)
- 期望: 需求写 500,配置也是 500
```

## 七、三个坑

### 坑一:期望来源污染(最隐蔽)

一旦允许用代码推期望,用例就会开始"永远通过"——因为期望是从实现里读出来的。

**机制性防止**:校验器硬编码禁止 `expect_source: "code"`。同时新增检查:若某条用例的 `expect_source` 是 `requirement` 但 `req_refs` 指向的行内容与代码中的常量一致而需求文档里找不到依据,复核时标出来。

### 坑二:实现耦合

覆盖目标可以来自代码,但**用例的步骤与期望描述必须停在行为层**。

- 差:"调用 `ShopManager.BuyItem()` 后校验 `m_coin` 减 100"
- 好:"点击购买按钮后,顶部金币显示减少 100"

前者重构即失效。**代码只用来决定"测哪里",不用来写"怎么测"。**

### 坑三:代码规模与幻觉

- 项目几十万行,**读不完**。必须"由需求 / 配置定位代码"作为入口,而不是全量通读
- AI 读代码会声称"这里有个分支"但实际没有。所以代码分析产出的覆盖目标**必须能定位到文件与行号**,让人可以抽查
- 代码分析结果要标注为"待验证的覆盖目标",不能直接当事实进入用例

---

## 八、源的可信度优先级必须由人定

需求 vs 配置 vs 代码,冲突时谁说了算?

惯例是 **需求 > 配置 > 代码**,但实际项目里经常反过来(配置是活的,需求是死的,代码是既成事实)。

**这个优先级不能由 AI 猜。** 必须人确认后写进框架配置,否则源冲突时无法裁决,所有交叉都会产出"疑似缺陷"而无法定性。

建议配置项:

```json
{
  "source_precedence": ["requirement", "config", "code"],
  "precedence_notes": "冲突时以需求为准;需求缺失时以配置为准;代码只作实现参考。"
}
```

## 九、与现有流水线的关系

插入两个新阶段,流水线变成:

```
-1  上游编目     收集所有源、格式化、建立索引
 0  静态交叉     配置×配置、需求×配置 → 不一致清单(直接是缺陷候选)   ← 新增,出包前就能跑
 1  体验与理解   (原有)
 2  需求拆解     (原有)
 3  用例生成     期望来源扩展到 config / consistency
 4  断言转换     (原有)
 5  复核         (原有)
 6  执行         (原有)
 7  判定提 bug    新增「不一致类缺陷」的开单模板
```

**阶段 0 的产物——不一致清单——在出包之前就能拿到。** 这比等真机回归便宜两个数量级,而且不需要设备、不需要视觉、不需要判定轮。

## 十、需要什么材料

| 材料 | 用途 | 优先级 |
|---|---|---|
| **配置表(CSV/JSON/Excel)1-2 张** | 建立静态检查能力,立刻能出不一致清单 | **最高** |
| 配置表字段说明(类型 / 范围 / 外键关系) | 悬空引用与范围检查的依据 | 高 |
| 资源目录清单(图标 / 音效 / 预制体) | 悬空引用检测 | 高 |
| 需求文档节选 | 需求 × 配置交叉 | 高 |
| 源码目录结构 + 一个模块的代码 | 建立 L2 能力 | 中 |
| 构建配置(分包表 / 资源清单 / 渠道) | 出包相关检查 | 中 |
| 源可信度优先级(人的裁定) | 冲突裁决 | 中(但不给就无法定性) |

**其中配置表优先级最高**:两张 CSV 加一份字段说明,就足以搭出第一个真正有价值的静态检查器,而且完全不需要真机、不需要授权、不需要客户端配合。

## 十一、对原有结论的影响

| 原结论 | 是否改变 |
|---|---|
| 真机是最终目标 | **不变**。L3 仍需真机,只是不再是唯一手段 |
| 视觉判定只用于显示层 | 不变 |
| 期望不能来自观察 | **强化**:同样不能来自代码 |
| A 档能力依赖客户端状态上报 | **缓解**:L1/L2 的能力不依赖客户端,今天就能做 |
| 最大缺口是判定轮 | **改变**:最大缺口变成"上游编目 + 静态交叉",因为它更便宜更高产 |
| 先做真机切片 | **调整**:先做阶段 0 静态交叉,再上真机 |

**最重要的一条变化:L1/L2 完全不依赖设备、不依赖客户端改造、不依赖平台能力。** 在等授权、等设备、等客户端排期的这段时间里,这一段可以立刻创造价值。

## 十二、工具:`check_config.py`(阶段 0 已实现)

阶段 0 的静态交叉做成了脚本,**不需要模型判断,也不需要设备**。

```bash
# 1) 先生成字段说明模板(推断类型/必填/唯一/枚举候选;范围与外键必须人补)
python3 "$SKILL_DIR/scripts/check_config.py" --dump-spec-template configs/fields.json \
  --config configs/item.csv --config configs/shop.csv

# 2) 跑交叉检查
python3 "$SKILL_DIR/scripts/check_config.py" \
  --config configs/item.csv --config configs/shop.csv --spec configs/fields.json \
  --out test-artifacts/<f>/config-check.md --json test-artifacts/<f>/config-check.json
```

**输入**:CSV(`utf-8` / `utf-8-sig` 都行,Excel 导出的 BOM 已处理)或 JSON(数组或 `{"rows": [...]}`)。
**xlsx 请先导出 CSV** —— 本项目不允许第三方依赖,读 xlsx 要额外库。

**字段说明格式**(JSON;`min`/`max`/`ref`/`ref_dir` 是工具猜不出来的,必须人写):

```json
{
  "source_precedence": ["requirement", "config", "code"],
  "precedence_notes": "冲突时以需求为准;需求缺失时以配置为准",
  "tables": {
    "item": {
      "path": "configs/item.csv",
      "key": "id",
      "referenced_by": ["shop.item_id"],
      "columns": {
        "id":      {"type": "string", "required": true, "unique": true},
        "name":    {"type": "string", "required": true},
        "icon":    {"type": "string", "required": true,
                    "ref_dir": "assets/icons", "ext": [".png"]},
        "quality": {"type": "int", "min": 1, "max": 5},
        "kind":    {"type": "enum", "values": ["weapon", "armor", "consumable"]},
        "price":   {"type": "int", "min": 0}
      }
    },
    "shop": {
      "path": "configs/shop.csv",
      "key": "id",
      "columns": {
        "id":      {"type": "string", "required": true, "unique": true},
        "item_id": {"type": "string", "required": true, "ref": "item.id"},
        "count":   {"type": "int", "min": 1}
      }
    }
  }
}
```

**检查项与产出的缺陷类别:**

| 检查 | 缺陷类别 |
|---|---|
| `ref: <表>.<列>` 外键 | 表间悬空引用(商店里的道具 id 不存在) |
| `ref_dir` + `ext` | 资源悬空(图标/音效文件不存在) |
| `key` + `unique` | 主键重复(同 id 两行) |
| `required` | 必填列为空 |
| `type` / `min` / `max` | 类型错误、超范围(负数、越上限) |
| `type: enum` + `values` | 枚举越界(类型字段出现词汇表外的值) |
| `referenced_by` | 孤立行(配了但没人引用 —— 废弃配置或漏接,**提示级,要人判断**) |

**输出与退出码**:`0` = 没有确定性错误;`1` = 有(不一致清单里逐条列出表/行/列/值);`2` = 用法或字段说明错误;`3` = **只有未检查项**(字段说明缺失,不是"没问题")。

**三条边界,别越界使用:**

1. **未声明的列走"未检查",不是"通过"。** 报告里有独立一节列出未检查项 —— 字段说明不全时,报告会显得"干净",但退出码是 3,别把它读成"配置没问题"。
2. **它判不了"是否符合需求"。** 需求说 500、配置写 300 这类语义比对不在它范围内(那是"需求 × 配置",要 AI + 人复核)。它只判"配置自己是否自洽"。
3. **它不产出期望。** 产出的是一致性缺陷候选;期望的来源仍然只有需求/配置/不变量/源间一致性(第四节)。

**没有真实配置表时怎么用**:`--dump-spec-template` 就是为此准备的 —— 拿两张真表,先生成模板,再人工补范围与外键(通常十几分钟),就能立刻出一份不一致清单。出包前跑这一层,比等真机回归便宜两个数量级。
