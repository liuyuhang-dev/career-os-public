# 测试维度完备性矩阵：漏测不是靠「想」，是靠「乘」

> 一句话：把每条需求子句去乘一张维度表，得到的不是用例数量，而是**"哪里还没判断"的位置**。
> 这张表的用处不是证明测得全，是**逼你承认哪里没想过**。

## 问题：靠「想」一定漏

需求评审完，策划问"边界和异常你都考虑到了吗"，测试说"考虑到了"。
然后上线，漏了一个上限截断。

复盘时发现不是不用心，是**人的注意力是线性的**：你顺着需求的正常流程想下去，
想到哪算哪。而边界、重复、中断、时序这些，是**跟正常流程正交**的——不在你思路的延长线上。

所以问题不是"再仔细一点"，是**换一种生产方式**。

## 方法：需求子句 × 维度

```
每条需求子句  ×  每个维度  =  一个格子
```

一个 3 条子句的需求 × 12 个维度 = 36 个格子。
每个格子只有三种合法状态：

| 状态 | 要求 | 不满足的后果 |
|---|---|---|
| **适用** | 必须产出一条可判定的关注点（进登记册） | 相当于"知道要测但不测" |
| **不适用** | 必须写明**为什么**不适用 | 相当于"不知道测没测" |
| **未判断** | **不允许存在** | 这就是漏 |

第三条是整个方法的支点。它把"覆盖率"从形容词变成了**数得出来的空格子**。

> 策划可以数：36 格，适用 24，不适用 12，未判断 0。
> 这比"覆盖率 92%"可信得多——后者你永远不知道那 8% 是什么。

## 十二个基础维度

这十二条不是我发明的，是**把策划脑子里那几类问题结构化**。

| # | 维度 | 标准问法 |
|---|---|---|
| D1 | 正向 | 正常路径上真的做到了吗（界面/文案/数值与需求一致） |
| D2 | **数值边界** | 0 / 1 / 最小 / 最大 / 上限 / 超上限 分别什么表现？上限截断吗？会负数或小数吗 |
| D3 | 空与缺失 | 数据为空（没记录/没奖励/没订单）时界面与流程怎么表现 |
| D4 | **重复与幂等** | 重复点击、请求重试、回调重投、断线重放会不会重复生效 |
| D5 | **中断与恢复** | 做到一半断网/切后台/被杀进程/来电，恢复后不丢不重不回退吗 |
| D6 | 时序与竞态 | 快速连点、并发、响应乱序、超时重试会出问题吗 |
| D7 | 权限与合规 | 未授权/拒绝授权/权限被关/协议未同意时的表现 |
| D8 | 状态迁移 | 首次/已存在/已过期/已完成 各状态对不对？会不会卡中间态 |
| D9 | 跨端与跨设备 | 换设备、多端同登、低端机与不同分辨率下是否成立 |
| D10 | 资源与配置 | 配置缺失、配置与需求不一致、热更中断时的表现 |
| D11 | 时间与周期 | 跨天/跨周刷新瞬间、活动结束瞬间、服务器与本地时间不一致 |
| D12 | 数据一致性 | 本地缓存与服务器不一致、部分成功、回滚时用户看到哪一份 |

D2 / D4 / D5 是策划说"边界值和异常你都想过了"时，脑子里真正在指的那三类。

完整问法、触发关键词、示例见 [`30-工具箱/测试维度表.csv`](../30-工具箱/测试维度表.csv)——**维度是数据，加一行就多一维**，不用改代码。

### 项目里补上的五类（D13–D17）

基础 12 类偏功能，真跑起来不够。按「出一次事故补一维」的路径，实际补了：

| # | 维度 | 它抓的是什么 |
|---|---|---|
| D13 | 性能与稳定性 | 启动/切换/列表滚动/高负载下的 FPS、帧时间、内存；长稳后是否卡顿、ANR、崩溃、泄漏 |
| D14 | 网络与弱网 | 断网、弱网、高延迟、丢包、超时、重连、回调重投；是否重复扣费/重复发货/状态卡死 |
| D15 | 安全与反作弊 | 改本地存档/系统时间/客户端价格、重放请求、伪造回调、内存修改；服务端能否拒绝 |
| D16 | 兼容性与本地化 | 系统版本、分辨率/宽高比、安全区、字体、语言、RTL、输入法、emoji、键盘 |
| D17 | 文案与术语正确性 | 与需求/文案表逐字一致；错别字、标点、中英混排、占位符残留；是否走 i18n 而不是硬编码 |

**D17 是最后加的一条，也是最容易被忽略的一条**：它的判定口径必须是「期望串 vs 实际串」精确 diff，
不靠人眼"读起来对不对"——否则永远会漏掉形近字和术语不统一。

平台类被测对象还要叠一组维度（入口注册、深链恢复、启动就绪、数据源路径、空数据隔离、错误可诊断、
落盘完整性、并发多实例、权限边界、规模、外部降级、跨模块对账、布局输入、可测试性、注入）。
完整 17 + 15 条见 [`30-工具箱/测试设计规则.md`](../30-工具箱/测试设计规则.md)。


## 第二张表：需求没写、但必须成立的常识

第一张表是「按你写的展开」。还有一半是**你没写、但这是常识**：

> 金币不能为负、体力不能为负、道具不超上限、同一操作不重复生效、
> 存档不回退、显示不出 NaN、点击必有响应、倒计时不倒流、操作 ID 唯一、不崩不白不卡。

需求文档里往往不写这些——合成文档里就没写"体力不能为负"。
但策划心里有。**把它们单独列出来逐条给结论，才说明不是只会在需求里抄东西。**

21 条常识分四类：

| 类别 | 覆盖 |
|---|---|
| 数值与资产 | 不得为负 / 不超上限 / 概率与权重合法 |
| 数量与守恒 | 消耗产出对得上 / 物品不重复计入 / 标识符唯一 |
| 重复与中断 | 操作不重复生效 / 失败不留痕 / 存档不回退 / 表现层幂等 |
| 界面与体验 | 不出 NaN / 显示等于权威值 / 点击有响应 / 空态有表现 / 文案不超框 / 时间不倒流 / 长跑不退化 / 等待有超时 / 互斥禁用真挡住 / 不崩不白不卡 |

每条带建议断言写法与"为什么这是常识"，见 [`30-工具箱/常识不变量.json`](../30-工具箱/常识不变量.json)。

三条纪律：

1. **不硬塞**：需求里没出现的实体不会冒出来。
2. **也不静默丢掉**：没命中的照样成行，写「不适用 + 为什么」。
   否则表看起来很干净，实际是少了几行——**覆盖的形状必须完整**。
3. **匹配要看正文也要看备注**：玩家可见反馈（界面/动画/文案/空态）常常只写在备注里，
   只看正文会整类漏掉。

## 为什么这套东西能让人放心

1. **维度是他认得的。** 上限截断、重复领取、断线重连、跨天刷新——他自己就是这么想的。
   他看到的是"你把我想的每一类都列了"，不是"你凑了一堆用例"。
2. **不适用也要给理由。** 「D11 时间与周期：需求写的是单局上限，不涉及跨天」——
   **这条理由本身就是信任来源**：说明不是漏了，是判断过。
3. **格子数得出来。** 36 格、适用 24、不适用 12、未判断 0。策划可以数。
4. **跟结论连得上。** 有产出的格子 → 登记册 → 结论页 → 给他的答复（测了没 / 有没有 bug）。

## 完备性是相对的，而且会变强

**不要声称"穷尽了所有可能"**——那是吹。能声称的是：**"按这张维度表逐格过了，没有空格子"**。

维度表可以扩，而且扩的动作是机械的：

1. 线上出了新类型缺陷（比如"跨时区导致每日刷新错乱"）→ 回补一个维度（D13 时区）；
2. 重跑矩阵 → **新增的格子会被自动标出来**，那就是"以前没考虑到的"；
3. 逐格处理（适用给产出，不适用写原因）。

所以这张表**每出一次事故就变强一次**，而不是靠人的记忆力。
项目里从 12 类基础维度扩到 17 类（D13–D17），走的就是这个路径。

## 一个填好的例子

需求：结算后按击杀数发放金币，单局上限 500。

| 维度 | 结论 | 产出 / 不适用原因 |
|---|---|---|
| D1 正向 | 适用 | 金币增量 = 击杀数 × 10（击杀 8 → +80） |
| D2 数值边界 | 适用 | 上限 500：击杀 60 时是 500 不是 600；击杀 0 时增量为 0 |
| D3 空与缺失 | 不适用 | 单局结算不存在"没有数据"（击杀数必为 0 及以上） |
| D4 重复与幂等 | 适用 | 重复点结算不重复发放 |
| D5 中断与恢复 | 适用 | 结算超时/断线：金币不增不扣，重连后以服务端为准 |
| D6 时序与竞态 | 适用 | 结算动画中再点 / 立刻开下一局：奖励不串局 |
| D7 权限与合规 | 不适用 | 结算不涉及授权与隐私 |
| D8 状态迁移 | 适用 | 未结束/已结束/已结算 三态下结算入口的表现 |
| D9 跨端 | 不适用 | 单局结算与设备无关（跨端一致性由存档类需求覆盖） |
| D10 资源与配置 | 适用 | 上限值与配置表一致；配置缺失时的行为 |
| D11 时间与周期 | 不适用 | 需求写的是单局上限，不涉及跨天刷新 |
| D12 数据一致性 | 适用 | 上报增量与界面显示一致（界面 80、入账 40 = 缺陷） |

展开前这里只有「D1 正向」一条。展开后策划看到的是：
上限截断、击杀 0、重复点击、结算中断、竞态串局、状态三态、配置一致、上报一致。

**这就是"你都考虑到了"的样子；而它是乘出来的，不是想出来的。**
