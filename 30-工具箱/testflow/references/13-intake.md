# 13 · 上游解析:关注点从哪来

这份文档回答一个问题:**"关注的每个点,是从哪儿来的?"** 凭空想的关注点不可信,
从上游解析出来的才可信 —— 而且**结论要能归因回上游**:
不是"我们觉得没问题",而是"需求 R-3.1 要求 X,我们验证了 X"。

---

## 一、关注点的三个入口

| 入口 | 谁做 | 覆盖什么 |
|---|---|---|
| ① 人主动提 | 产品/研发/策划 | 他们脑子里的顾虑(需求文档写不下的那些) |
| ② 从上游解析 | `concerns.py --intake`(机械) | 需求子句、用例期望、配置列、代码模块、已开缺陷 |
| ③ 机器兜底 | `concerns.py --suggest`(机械) | run 里 fail/没结论的判定项、异常扫描、配置不一致 |

**入口 ②③ 是这份文档的重点**:人想不全,机器兜住;人只做"确认与裁决"。

## 二、五条上游,各自怎么解析

```bash
python3 "$SKILL_DIR/scripts/concerns.py" \
  --intake requirements:test-artifacts/<f>/01-requirements.json \
  --intake specs:specs/ \
  --intake config:configs/fields.json \
  --intake code:src/ \
  --intake bugs:test-artifacts/<f>/05-bugs/ \
  --feature <特性名> --intake-out test-artifacts/<f>/concerns-candidates.csv
```

| 上游 | 解析成什么 | 每条候选带的"上游引用" |
|---|---|---|
| `requirements:<01-requirements.json>` | **每条需求子句一条候选**("需求 R-3.1 是否满足:…") | 子句号 `R-3.1` |
| `specs:<自然语言用例目录>` | **每条 `E-N` 期望一条候选** | `<用例ID>/E2` |
| `config:<字段说明.json>` | **每张表一条 + 每个引用/范围列一条** | `表名` / `表名.列名` |
| `code:<源码目录>` | **每个模块文件一条**("异常路径与副作用是否覆盖") | 文件路径 |
| `bugs:<05-bugs/>` | **每张缺陷单一条**("曾经的缺陷会不会回归") | `BUG-001` |

候选的**结论是照事实预填**的:需求/配置/模块 → "未覆盖"(还没测);
用例期望/缺陷回归 → "覆盖但结论待条件"(用例在,等跑)。
人审一遍(定来源与优先级、删掉不适用的、把结论改到实际状态),它就是正式登记册。

**代码这条特别说明**:源码只用来决定"测哪里",**不用来推期望**(见 `10-upstreams.md` 第四节)。
所以从代码解析出来的候选,期望一律留空,只写"这个模块的异常路径覆盖了吗"。

## 三、父节点:归纳那一层

关注点是**叶子**(一条一行),但人看的时候先看**父节点**。
登记册里用两列表达这个层级:

- **`模块`** = 父节点(需求模块名 / 配置表名 / 代码模块 / 用例 ID / 缺陷模块)
- **`上游引用`** = 这条结论归因到哪个上游(子句号 / 用例判定项 / 表.列 / 文件 / 缺陷单号)

结论页与给人看的一页都会**先按模块归纳一行**:

```
| 模块 / 主题 | 关注点 | ✅ | 🟠缺陷 | 🟡待条件 | 🔴未覆盖 | ⛔做不到 | 一句话结论 |
| 结算与数值  | 3 | 0 | 1 | 2 | 0 | 0 | 2 条结论待出 |
| 热更与资源  | 1 | 0 | 0 | 0 | 1 | 0 | 还有 1 条没测 |
```

**父节点回答"这个模块整体怎么样",子节点回答"具体哪条、卡在哪"** ——
汇报时先给父节点那张表,追细节再往下看叶子。

## 四、结论怎么归因(为什么这比"通过率"可信)

每条 ✅ 都能回答三个问题:上游是谁要求的?用哪条判定项验的?哪一轮跑的、证据在哪?

登记册里就是这三个字段:`上游引用` + `覆盖方式` + `依据`;
`concerns.py --runs <04-runs/>` 会把 `覆盖方式` 里的判定项**拿去核对**(见 `12-confidence.md` 第三节),
核对不过就打回。**上游 → 关注点 → 覆盖方式 → 依据 → 核对**,这条链完整了,"没问题"三个字才有分量。
