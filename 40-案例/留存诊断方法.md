# 留存诊断：把「留存低」拆成可以动手的几件事

> 一句话：留存分析的价值不在于算出 D7 是多少，而在于指出**明天该改哪一关、停哪个渠道、核查哪个地区**。

## 问题

一款出海休闲游戏，D1 约三成、D7 一成出头、D30 不足 5%。团队知道"留存低"，但不知道问题在哪：
是买量质量差？是某地区不行？是新版本回退？还是新手引导劝退？

这四个判断对应完全不同的动作，猜错就是白花钱。

## 方法：五步，每步都要先定口径

### 第 1 步：清洗，并把清洗过程写成瀑布

留存分析最常见的错误不是算错，是**分母里混了不该有的人**。按顺序剔除，每一步都记录剩余人数：

```
全部安装
  → 剔除混入的其他包（按 bundle_id）
  → 剔除测试账号（用户表 is_test）
  → 剔除特定地区（投放/运营策略导致，不具代表性）
  → 剔除未完成首次 loading 的（安装事件在了，游戏没进去）
  → 剔除无安装事件的（只有启动没有安装，数据异常）
  → 剔除异常等级账号
= 分析口径
```

写成瀑布的好处：任何人对结果有疑问，可以直接指出"你第 3 步不该剔"，而不是推翻整份报告。

### 第 2 步：定义清楚两个词

| 词 | 定义 | 为什么重要 |
|---|---|---|
| 安装日 | 首次 `app_install` 的时间 | 用注册日/首启日算，分母会漂 |
| 留存 | 安装后第 n 天有 `app_start` | 用"在线时长 > 0"算，会把挂机算成活人 |

**分母只含安装满 n 天的人。** 这一条不遵守，最近的批次会系统性拉低 D7。

### 第 3 步：先看整体，再看周趋势

整体曲线回答"现在多差"，周趋势回答"在变好还是变坏"。**没有周趋势的留存报告不能用来判断版本效果**，因为版本和安装批次高度绑定。

### 第 4 步：分维度，但每个维度都要"同周对比"

这是整份分析里最关键的一条方法：

> **当版本/渠道/平台与安装批次强绑定时，整体对比会得出相反结论。必须固定同一周再比。**

实际遇到的例子：

- **平台**：整体看 iOS 明显好于 Android。但按周拆开后，iOS 的优势只存在于早期批次，后期已经打平甚至更低。→ 结论从"iOS 用户质量更好"改成"不能认定平台差异"。
- **版本**：新版本整体留存更高，但新版本恰好赶上了投放质量更好的批次。同周对比后，提升仍然存在但幅度收窄。
- **地区**：某个市场每周都低 3–6 个百分点，是**稳定的结构性短板**，不是批次噪声。这类才值得单独核查素材与本地化。

### 第 5 步：用分层找"漏在哪"

三个分层最有解释力：

| 分层 | 它回答什么 | 当时的发现 |
|---|---|---|
| 首周活跃天数 | 留存是"广度问题"还是"深度问题" | 一半用户首周只来 1 天；真正撑住长期留存的是不到一成的核心层。**长尾极长，头部极小** |
| 首日关卡深度 | 新手引导在哪一步劝退 | 存在明显断崖：首日只过 1–3 关的用户，次日留存低于"一关没过"的用户 |
| 付费 | 留存是不是付费驱动的 | 付费率低、付费用户留存高，属选择关系，不能当因果 |

**首日关卡深度那条最有行动价值**：它把"新手引导有问题"从感受变成了一个具体位置——前 3 关。

### 一个容易漏的口径细节

"0 关"其实包含两种人：

- 启动了关卡但**没打完一局**；
- 首日**完全没有开始任何关卡**。

后者次日留存反而很高（只启动、不打关，不是有效留存），把两者混在一起会把"卡在加载"的问题掩盖掉。**分组前先想清楚每一组到底代表什么行为。**

## 结论怎么写成动作

差的结论：「留存偏低，建议优化新手引导。」
好的结论：

| 发现 | 动作 | 责任方 |
|---|---|---|
| 前 3 关是断崖 | 逐关看流失点，优先改第 1–3 关的引导与难度 | 策划 + 关卡 |
| 某地区每周稳定低 3–6pp，且浅层用户占比最高 | 单独核查该地区的素材、定向与本地化 | 投放 + 本地化 |
| 某小渠道样本极小但质量显著差 | 停投或单独核查，不参与整体判断 | 投放 |
| 核心层不到一成却贡献大部分长期留存 | 运营资源向 4–5 天层倾斜（可争取的中间层） | 运营 |

## 诚实的边界

- **关卡深度、付费与留存都是相关关系，不是因果。** "提高关卡数就能提高留存"是错的推论——深度是投入度的代理，不是原因。
- 小样本（几百人）的渠道差异不下结论。
- 最近两周的 D7/D14 分母不完整，只作趋势参考。
- "首日无 level_start" 的用户是否卡在加载，需要客户端日志确认，数据本身答不了。

## 可复用件

这套流程与行业无关，换任何产品都能用：

1. **清洗瀑布**先立口径，让结论可被质疑；
2. **周趋势**判断变化，**同周对比**判断差异；
3. **分层**定位漏点，**代理变量**解释原因；
4. 结论必须落到"谁、改什么"，否则只是描述。

工具是 SQL + 数数（ThinkingData）的查询接口，但方法本身与工具无关。
