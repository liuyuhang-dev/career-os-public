# 多智能体协同：用 Issue 和 Label 撑起一条 AI 研发流水线

> 完整框架、角色定义、流程文档和运行时代码见 [`merge-ai工作流框架/`](merge-ai工作流框架/README.md)。
> 一句话：把 GitLab issue 当成任务数据库，用 6 个常驻 agent 把「需求 → 实现 → 测试 → 通知」串成闭环，人只在两个地方签字。

## 背景与约束

| 项 | 内容 |
|---|---|
| 当时的状态 | 10 名贡献者并行开发，issue 与 MR 数量大。派发、催办、验收、同步状态靠人喊；AI 生成代码变快之后，**没人验收**成了新瓶颈 |
| 规模 | 4 个 agent 工作区 + 2 个调度机器人；1200+ 知识节点、735 个甘特节点 |
| 硬约束 | ① AI 不可控，不能让它直接改计划 ② 多个 agent 并行，工作区必须隔离 ③ 网络与宿主不稳定，进程会挂 ④ 团队已习惯 GitLab issue，不能换工具 |
| 我的角色 | 流程与规则设计、状态机定义、验收标准、调度策略；具体平台能力是团队共同实现 |

## 设计

```
              ┌──────────── GitLab Issue（唯一的任务真相） ────────────┐
              │  labels: 待处理 / BUG / PR / 审核通过 / 已完成          │
              │          / 人工 / 测试通过 / 测试未通过                │
              └───────┬──────────────────────────┬────────────────────┘
                      │ 每 2 分钟轮询             │
              ┌───────▼────────┐         ┌───────▼────────┐
              │ PR 机器人       │         │ BUG 机器人     │
              │ 需求分析/派发   │         │ 问题分析/派发  │
              └───┬────────┬───┘         └───┬────────┬───┘
                  │        │                 │        │
        ┌─────────▼──┐ ┌───▼─────────┐ ┌─────▼──────┐ │
        │ LL 逻辑开发 │ │ PL 表现开发 │ │ LL-TEST    │ │
        │ （可写代码）│ │ （可写代码）│ │ （只读+反馈）│ │
        └─────────┬──┘ └───┬─────────┘ └─────┬──────┘ │
                  └────────┴─────────────────┴────────┘
                                   │
                         钉钉群通知（简短文案）
```

六条设计原则：

1. **Issue 当数据库，Label 当状态机。** 不引入新系统。任务状态就是 label 的组合，人和 agent 看的是同一个东西。
2. **轮询 + 幂等去重。** 每 2 分钟扫一次 open issue，用 `(issueId, 最后评论时间)` 做去重键。重复触发不会重复干活。
3. **职责分离。** 开发 agent 可以提交代码；测试 agent **不许提交任何代码**，只能在 issue 里写结论和建议。防止"自己出题自己判卷"。
4. **人工闸门。** 任何标签为「人工」的 issue，调度器一律不派发，必须等人在评论里确认完成。AI 只提议，不越权。
5. **失败自愈。** 每 2 分钟用外部接口探活；不在线就 `update 到 main`（丢弃本地改动）后重启。宁可丢一次未提交的改动，不可让流水线停摆。
6. **工作区隔离。** 每个角色一个工作区、一个分支，不共享、不建额外 worktree，避免互相踩文件。

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 触发机制 | 2 分钟轮询 | Webhook | 内网与宿主不稳定，webhook 丢一次就静默卡死；轮询最坏只慢 2 分钟 |
| 状态存储 | Issue label | 独立数据库 | 数据库会和人的认知分叉；label 人和 agent 都看得见 |
| 去重键 | issueId + 评论时间 | issueId 单键 | 单键会导致"同一个 issue 的第二轮反馈被吞" |
| 测试权限 | 只读 + 反馈 | 允许测试 agent 修 bug | 测试一旦能改代码，判定就不再独立 |
| 掉线处理 | 回滚 main 后重启 | 保留现场人工排查 | 无人值守场景下，可用性优先于现场保留 |

## 落地过程

1. **先跑通单角色**：一个开发 agent + 一个 issue，确认「读 issue → 改代码 → 提交 → 回评 → 打标签」这条链能闭合。
2. **再加测试角色**：这里第一次暴露出"测试 agent 会不会顺手把代码改了"的风险，于是定了硬规矩：测试工作区禁止提交。
3. **加调度器**：PR / BUG 两个机器人负责分诊。分诊的价值不是"自动"，是**让每个 issue 都有明确的下一个负责人**。
4. **加自愈**：agent 挂掉是常态。探活 + 回滚 + 重启之后，流水线才真正能无人值守。
5. **踩的坑**：早期没有「人工」闸门，agent 遇到模糊需求也会硬往下推，产生大量无效改动。加上闸门后，宁可停下等人，也不猜。

## 结果

- `issue → 分支 → 实现 → 测试 → 通知` 全链路闭环，不再需要人工催办。
- 132 个节点已完成、87 个逾期可逐条核对，负责人、优先级、计划日期都挂在节点上。
- 测试结论回到 issue 而不是散在聊天里，可追溯。
- 提测前通过静态走查输出 18 项已知问题，减少提测后返工。

## 如果重来

- **「人工」闸门应该第一天就有。** 它不是一个功能，是这套系统的伦理边界。没有它，agent 会把不确定性静默地转成代码。
- **探活只看端口不够**，早期误判过"进程活着但 agent 卡死"。后来改成调外部接口做真实探活。健康检查必须检查**能力**，不是**进程**。
- **通知太啰嗦**。第一版把完整上下文都推到群里，没人看。改成一句话 + issue 链接后才有用。

## 可复用件

「**Issue as DB + Label as state + Polling as trigger + Human gate**」这套组合不依赖任何特定平台。任何有 issue 系统和标签功能的地方（GitLab / GitHub / Jira / 禅道）都能复刻。真正的难点不在编排，在**定义什么情况下必须停下来找人**。
