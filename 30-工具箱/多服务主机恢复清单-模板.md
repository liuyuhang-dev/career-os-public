# 多服务主机恢复清单（模板）

> 适用：一台长期运行的打包/工单/看板主机（macOS 或 Linux），断电、重启、换机后按顺序恢复。
> 目的：把"哪些服务会自动起来、哪些必须手动拉、怎么验证"写成可照着执行的清单，避免每次重启靠回忆。

## 〇、先决条件（缺一步后面全白搭）

1. **登录桌面**：如果机器没有自动登录，停在登录窗口时，所有用户级服务都不会加载。
2. **挂载外置盘**：确认数据盘已挂载，且当前用户有读写权限。
   - macOS：`diskutil list` 找到盘，再 `diskutil mount diskXsY`
   - Linux：`lsblk` / `mount`
3. **验证关键路径可读**：随便读一个数据盘上的配置或数据库文件，确认不是只有目录存在。

> 这三步不做，后面的服务会"启动成功但读不到数据"，看起来像服务坏了。

## 一、登录后自动恢复的（不用管，但要会验证）

| 服务 | 端口 | 自启方式 | 验证方法 |
|---|---|---|---|
| 反向代理 / 文件共享 | 80 / 自定义 | 系统服务管理器 | `curl -I http://127.0.0.1/` |
| CI / 构建服务 | 自定义 | 系统服务管理器 | 浏览器打开，或 `curl -I` |
| 定时任务执行器 | — | 系统服务管理器 | 看最近一次执行时间 |
| 状态监控 | — | 系统级守护进程 | 看监控页或日志最后一行 |

验证命令示例：

```bash
# macOS launchd
launchctl list | grep -i <关键字>
# Linux systemd
systemctl list-units --type=service --state=running
# 端口
lsof -iTCP -sTCP:LISTEN -P -n | grep <端口>
```

## 二、必须手动拉起的（断电后重点）

按依赖顺序启动：先数据库/存储，再业务服务，最后对外入口。

| 顺序 | 服务角色 | 端口 | 启动方式 | 备注 |
|---|---|---|---|---|
| 1 | 数据库 | 自定义 | 系统服务或容器 | 先确认能连上再起业务 |
| 2 | 工单/交付主站 | 自定义 | 项目内启动脚本，后台运行 | 一次只起一个实例 |
| 3 | 报表/看板站 | 自定义 | 静态服务或应用服务 | 依赖主站数据 |
| 4 | 机器人/消息服务 | — | 应用内 `serve` 模式 | 确认长连接已建立 |
| 5 | 登录态守护 | — | 独立进程或定时任务 | 扫码登录类服务需要 |

启动后逐个验证：

```bash
curl -I http://127.0.0.1:<端口>/
ps aux | grep <进程名> | grep -v grep
```

## 三、定时任务（不占端口，但最容易静默失败）

| 任务 | 频率 | 调度方式 | 失败表现 |
|---|---|---|---|
| 超期检查 | 每天固定时间 | 系统定时器 / crontab | 没有提醒，但数据不更新 |
| 日报/汇总 | 每天固定时间 | 系统定时器 / crontab | 群里没有消息 |
| 数据同步 | 每 N 分钟 | 系统定时器 / crontab | 看板停在旧数据 |
| 登录态兜底 | 每 N 分钟 | 系统定时器 / crontab | 需要扫码的服务掉线 |

检查方法：

```bash
# macOS
launchctl list | grep -i <关键字>
# Linux
crontab -l
systemctl list-timers --all
```

## 四、恢复后的验收（不要只看"进程在"）

1. **端口在听**：`lsof` / `ss` 能看到。
2. **页面能开**：`curl -I` 返回 200。
3. **数据能读**：打开一个列表页，能看到最新一条记录。
4. **写链路能通**：提交一条测试数据，确认能落库。
5. **定时任务能跑**：手动触发一次，看日志有产出。

## 五、常见坑

- **外置盘没挂**：服务起来了但读不到数据，日志报"文件不存在"。
- **权限问题**：后台进程（launchd/systemd）拿不到桌面用户的文件权限，需要改成经 `ssh localhost` 或显式授权。
- **重复启动**：启动脚本不幂等，重复执行会端口冲突；启动前先查端口。
- **只验证了进程**：进程在、端口在，但数据库连接失败，页面照样打不开。
- **定时任务静默失败**：没有告警，只能靠"数据是否更新"发现；关键任务要加失败通知。
