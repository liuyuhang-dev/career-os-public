# 3 · 用例生成(阶段 2)

用例**由 AI 生成,人只复核**。因此这一阶段的核心不是"怎么写",而是**怎么保证生成出来的用例值得复核**——尤其是怎么防止 AI 写出自证型用例。

## 头号风险:自证型用例

AI 同时写用例、写断言、还参与判定,天然的倾向是写出**容易通过的**用例。三种典型形态:

| 形态 | 表现 | 后果 |
|---|---|---|
| 以现有行为为期望 | 看过游戏后写"期望:扣 50 金币" | **把现有 bug 烤进期望,从此永远测不出来** |
| 以实现为验收标准 | "期望:调用了 Redis 计数接口" | 重构即失效,且不验证任何用户可见行为 |
| 绕开硬需求 | 只给"登录成功"写用例,不给"锁定与解锁"写 | 最难的需求恰好没人测 |

对应三条硬约束(见下)。

## 硬约束

**约束一:用例只能从需求子句或不变量派生,不能从观察实现派生。**
生成用例时只拿到 `01-requirements.json` 和 `understanding/<game>.md`(它给名词和地图),**不拿运行中的游戏**。屏幕上的实际数值不是期望的来源。

**约束二:期望必须可观测、可判定、自包含。**

- 反例:"系统应该保护账号安全" → 这是需求意图,不是可判定的结果
- 正例:"结算页金币增量等于击杀数 × 10,上限 500"
- 反例:"提示信息友好" → 改为"结算页出现包含『结算成功』字样的提示"

**校验器会在规格层面就提醒**(不用等到用例生成阶段发现期望写不出断言):

- `SPEC_VAGUE_EXPECTATION`:期望里出现"正常/流畅/良好/合理"这类模糊词**且没有数值** ——
  它转不成是/否问题,大概率会变成一条判不了的判定项
- `SPEC_SUBJECTIVE_EXPECTATION`:期望里出现"手感/打击感/观感"这类主观词 —— 真机自动化
  判不了,应写成 `type=manual` 的用例并给出 `reason`(为什么必须人工),
  而不是留在需求用例里等判定轮猜

**约束三:一条期望里既有可机械判定的部分又有主观部分,必须拆成两条。**
"返回 423 且文案清晰" → 拆成 `E_a`(状态码/数值)+ `E_b`(文案判断,标 `judgment`)。混在一条里,转换器只能二选一:要么漏掉主观部分,要么把客观部分降级成主观判断。

## 期望来源

每条用例必须声明 `expect_source`,校验器强制:

| 来源 | `expect_source` | 前置要求 | 可信度 |
|---|---|---|---|
| 需求文档 | `requirement` | **必须带 `req_refs`** 指向需求子句 | 最高 |
| 配置表 | `config` | **必须带 `config_refs`**(表 + 行) | 高 |
| 通用正确性不变量 | `invariant` | 无 | 中高 |
| 源间一致性 | `consistency` | **必须带 `consistency_refs`**(要比对的源对) | 高 |
| 源码实现 | —— | **校验器直接报错** | —— |
| 观察到的现有行为 | —— | **校验器直接报错** | —— |

**两条红线,不是一条:**

- 观察到的现有行为是**实然**,不是应然判断 → 禁止
- 源码实现也只回答「测哪里」(有哪些分支与边界值得覆盖),**不回答「应该是什么」** → 禁止

第二条更容易犯,因为代码看起来比截图"更权威"。一旦用实现推期望,用例就会永远通过。
详见 `references/10-upstreams.md`(多源上游)与 `references/11-idempotency.md`(幂等类缺陷)。

### 通用不变量目录(游戏向,尤其针对弱网)

不变量是"任何游戏都成立"的性质,不需要需求文档。**这是没有需求文档时也能产出有价值用例集的依据。**

| 类别 | 不变量 |
|---|---|
| 货币与数值 | 货币/资源余额不小于 0;不显示 `NaN`/`Infinity`/科学计数法;大数不使用错误的千分位或截断 |
| 背包与道具 | 道具数量不超过上限;无重复条目(同 id 两行);不出现空名/空图标条目 |
| 存档与进度 | 断线重连后状态不回退、不丢档;重启后进度一致;跨设备/跨端一致 |
| 结算与并发 | 同一笔订单不重复结算;离线操作重放不双倍生效;重复上报幂等 |
| 弱网与超时 | 断网时给出明确提示而非无限转圈;恢复网络后自动重连或可手动重试;操作超时有反馈 |
| 界面完整性 | 不白屏;文字不截断/不重叠/不溢出容器;按钮不被遮挡;关键按钮可点 |
| 交互响应 | 点击必须有响应(不能无反应);加载不无限转圈;返回键行为合理 |
| 生命周期 | 前后台切换后状态正确;来电/断线中断后能恢复;低内存被杀后可恢复到合理状态 |

### 不变量用例怎么写

不变量用例的 `steps` 通常是一条**操作序列**,`E` 是"序列结束后性质仍成立":

```
用例: 连续消耗金币到接近 0 时余额不变负
- ID: INV-COIN-C01
- 来源: invariant
- 前置: 账号金币为 0
- 步骤:
  - S1: 进入商城
  - S2: 对任意标价道具连续点击购买 10 次
- 期望:
  - E1: 每次购买后金币余额不小于 0
  - E2: 金币不足时给出明确提示(非静默失败)
  - E3: 金币数值不显示为负数
```

## 用例 ID 约定

| 前缀 | 用途 |
|---|---|
| `REQ-<需求号>-C<序>` | 需求派生的用例,如 `REQ-003-C01` |
| `INV-<类别>-C<序>` | 不变量用例,如 `INV-COIN-C01`、`INV-NET-C02` |
| `EXP-<序>` | 探索发现后固化的用例(通常 `judge: replay`) |
| `CONS-<源对>-C<序>` | 源间一致性用例(来源写 `consistency`),如 `CONS-CFG-C01`、`CONS-REQ-C01`;校验的是"两个源说的是不是同一件事",见 [10-upstreams.md](10-upstreams.md) 第六节 |

这张表与 `scripts/validate_cases.py` 的 `CASE_ID_PREFIXES` 是一件事的两处写法,`check_docs.py` 会对账;改前缀只改代码那一处,再回来补这一行。

## 覆盖策略:一个需求子句至少一条,但要按风险加权

覆盖率闸门只要求 ≥1,但生成时应按优先级铺开:

| 子句类型 | 建议覆盖 |
|---|---|
| 涉及货币、支付、结算、存档 | 正常路径 + 边界值 + 并发/重复 + 弱网中断,**必须全覆盖** |
| 涉及进度、等级、解锁 | 正常路径 + 边界值 |
| 纯展示、文案 | 正常路径 + UI 完整性不变量 |
| 性能、兼容 | 交给云真机/性能测试,不做功能用例 |

**金额与结算类子句的期望要写成精确值或明确公式**,不许写"合理增加"这类模糊表述——模糊期望到阶段 3 无法转换。

## 人复核聚焦点(写进复核单)

生成完用例后跑 `review_sheet.py` 出复核单。复核人只看四件事:

1. **哪条需求没覆盖** —— 复核单直接标 `⚠ 无对应用例`
2. **哪条期望的来源不合法** —— 有没有 `expect_source` 标成需求但实际是你自己想的要求
3. **哪条期望无法判定** —— 有没有"友好""合理""正常"这类不可判定的词
4. **有没有把现有行为写成期望** —— 看到"期望:扣 50 金币"这种具体数字时,问一句:这个数是需求里写的,还是你看屏幕看到的?

第 4 条是复核的关键,也是唯一需要人的判断力才能拦住的问题。**复核单会在每条期望后标注来源,让人一眼看出哪些是需求背书的硬要求、哪些是不变量推出的软要求。**

## 输出

`specs/<feature>.md`,格式见 `assets/case-template.md`。一个文件可放多条用例,`PRE-N / S-N / E-N` 编号在单条用例内唯一。

> **派生用例 JSON 不用从零手写**:`scripts/scaffold_cases.py` 能把自然语言用例转成骨架 —— ID/来源/类型/优先级/判定模式/req_refs 一次填好,每条 `E-N` 都生成一条判定项占位,**从不覆盖已有文件**。骨架是 `draft` 且带 `skeleton: true`,步骤与断言要人填,填完复核通过才能进执行阶段。
