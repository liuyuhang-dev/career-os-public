## 三、核心配置

### 3.1 数数平台 API Token（推荐）

**不需要账号密码** 使用数数平台 Open API + Token 方式，更安全。

**生成 Token 步骤：**

1. 登录数数平台服务器（私有化部署环境）
2. 切换到 ta 用户：`su - ta`
3. 生成项目密钥：
   ```bash
   # 方式1：生成项目专用密钥（推荐）
   ta-tool generate_api_secret -appid YOUR_APPID
   
   # 方式2：生成 root 密钥（适用所有项目）
   ta-tool generate_root_secret
   ```
**API 调用方式：**
```bash
# 通过 SQL 查询异常数据
curl -X POST 'http://$HOST:8992/querySql?token=$API_SECRET' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  -d 'sql=SELECT * FROM v_event_0 WHERE "$part_date"='2026-04-13' LIMIT 100'
```

**查询异常数据的 SQL 示例：**
```sql
-- 查询今日异常触发数
SELECT 
  "#event_name" as exception_type,
  "exception_message",
  COUNT(DISTINCT "#user_id") as trigger_users
FROM v_event_0
WHERE "$part_date" = '2026-04-13'
  AND "#event_name" LIKE '%Exception%'
GROUP BY "#event_name", "exception_message"
ORDER BY trigger_users DESC
LIMIT 20
```

**配置信息：**
```markdown
## 数数平台 API
- **API地址**: http://ta2:8992
- **Token**: your_api_token_here
- **APPID**: YOUR_APPID
```

**优势：**
- ✅ 无需账号密码，更安全
- ✅ Token 可按项目生成，权限隔离
- ✅ Token 可随时撤销，安全可控
- ✅ 支持设置 IP 白名单访问限制

## 四、告警规则

| 规则 | 条件 | 通知方式 |
|-----|------|---------|
| 紧急告警 | 单条异常触发 > 20次 | @所有人 |
| 新增异常 | 出现历史未记录的异常类型 | 普通通知 |
| 波动告警 | 触发数增长 > 50%（且绝对值≥5） | 普通通知 |

**白名单机制：**
某些测试环境特有的异常可加入白名单，不触发告警：
```
异常监控白名单：
- KeyNotFoundException (NotificationSwitch)：测试端特有
```

## 五、钉钉通知代码示例

```python
import hmac
import hashlib
import base64
import time
import urllib.request
import json

def send_dingtalk_notification(webhook, secret, title, content):
    """发送钉钉通知（带加签）"""
    
    # 生成签名
    timestamp = str(round(time.time() * 1000))
    string_to_sign = f'{timestamp}\n{secret}'
    hmac_code = hmac.new(
        secret.encode('utf-8'),
        string_to_sign.encode('utf-8'),
        digestmod=hashlib.sha256
    ).digest()
    sign = urllib.parse.quote_plus(base64.b64encode(hmac_code))
    
    # 完整URL
    full_url = f"{webhook}&timestamp={timestamp}&sign={sign}"
    
    # 消息内容
    message = {
        "msgtype": "markdown",
        "markdown": {
            "title": title,
            "text": content
        }
    }
    
    # 发送请求
    data = json.dumps(message).encode('utf-8')
    req = urllib.request.Request(
        full_url,
        data=data,
        headers={'Content-Type': 'application/json'}
    )
    response = urllib.request.urlopen(req)
    return response.read().decode('utf-8')

# 使用示例
send_dingtalk_notification(
    webhook="https://oapi.dingtalk.com/robot/send?access_token=xxx",
    secret="SECxxx",
    title="【异常监控】iOS新增异常",
    content="## iOS 1.3.5 发现新增异常\n\n异常类型：Facebook登录异常\n触发数：3次"
)
```

## 八、常见问题

**Q1：Token 泄露了怎么办？**
A：重新执行 `ta-tool generate_api_secret -appid YOUR_APPID`，旧的 Token 会立即失效

**Q2：如何区分测试环境和正式环境？**
A：为不同环境生成不同的 Token，Token 只能访问对应项目

**Q3：通知太多怎么办？**
A：调整告警阈值，或使用白名单过滤掉不关心的异常类型

**Q4：如何查看历史趋势？**
A：查看 `history.json` 中的 `trigger_users` 字段，可以看到每日触发数变化

**Q5：API 有调用频率限制吗？**
A：数数平台对 API 调用频率有限制，建议每小时调用一次即可满足监控需求

## 九、异常归类与智能分析

### 9.1 异常归类逻辑

**问题背景：** 同一个异常在不同设备上可能产生不同的报错信息（设备ID、路径、时间戳等差异），导致误判为多个独立异常。

**归类策略：**

```python
import re
from collections import defaultdict

def extract_exception_signature(exception_message, stack_trace):
    """提取异常签名，用于归类"""
    
    # 1. 提取异常类型（如 NullReferenceException）
    exception_type = re.search(r'(\w+Exception|\w+Error)', exception_message)
    exception_type = exception_type.group(1) if exception_type else "Unknown"
    
    # 2. 提取核心堆栈（去掉设备差异）
    # 去掉：设备ID、时间戳、完整路径、内存地址
    core_stack = re.sub(r'/var/mobile/[^/]+/', '/[DEVICE]/', stack_trace)
    core_stack = re.sub(r'0x[0-9a-f]+', '0x[ADDR]', core_stack)
    core_stack = re.sub(r'\d{4}-\d{2}-\d{2}.*?\d{2}:\d{2}:\d{2}', '[TIME]', core_stack)
    
    # 3. 生成签名
    signature = f"{exception_type}|{hash(core_stack) % 10000}"
    return signature

def group_exceptions(exception_list):
    """归类异常"""
    groups = defaultdict(list)
    
    for exc in exception_list:
        signature = extract_exception_signature(
            exc['exception_message'],
            exc.get('stack_trace', '')
        )
        groups[signature].append(exc)
    
    return groups
```

**归类示例：**
```
原始异常（3条）：
1. "PurchaseHub failed on device iPhone13, path /var/mobile/xxx, time 2026-04-13 10:00"
2. "PurchaseHub failed on device iPhone14, path /var/mobile/yyy, time 2026-04-13 11:00"  
3. "PurchaseHub failed on device iPad, path /var/mobile/zzz, time 2026-04-13 12:00"

归类后（1组）：
签名: "PurchaseHubError|5827"
- 设备变体：iPhone13, iPhone14, iPad
- 合计触发数：3次
```

### 9.2 客观分析原则

**禁止事项：**
- ❌ 猜测异常原因（"可能是配置问题"、"可能是网络问题"）
- ❌ 给出无依据的建议（"建议检查代码"、"建议优化逻辑"）
- ❌ 添加主观判断（"这个问题很严重"、"影响用户体验"）

**必须基于事实：**
- ✅ 陈述触发数变化（"从3次增长到5次，增长67%"）
- ✅ 说明异常类型（"属于 NullReferenceException 类型"）
- ✅ 指出异常位置（"位于 GameManager.cs 第42行"）
- ✅ 对比历史数据（"该异常首次出现于04-11"）

**分析模板：**
```
【异常名称】PurchaseHub初始化失败
【触发数】今日5次（昨日3次，增长67%）
【异常类型】NullReferenceException
【堆栈位置】PurchaseHub.cs:Init() 第156行
【首次出现】2026-04-11
【设备分布】iPhone(2), iPad(2), Android(1)
【版本分布】1.3.5(4), 1.3.4(1)

说明：该异常触发数增长但绝对值较低，持续观察。
```

## 十、优化建议

1. **异常归类**：按异常签名归类，避免同一问题重复告警
2. **客观分析**：基于数据说话，不猜测原因
3. **增加趋势图**：定期生成异常趋势图，发送到钉钉群
4. **多渠道通知**：支持飞书、企业微信等
