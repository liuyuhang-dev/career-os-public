# 场景交付状态看板：从 Git 改动反推每个场景做到哪一步

> 一个只读工具：不改工作区、不要求提交信息规范，按 Git 里的文件改动和 Unity YAML diff，推断场景当前处于哪个制作阶段，并生成看板与钉钉日报。

## 问题

场景交付链条长：外包/内包制作 → 资源入库 → 动效做动作 → 动效做特效 → 材质返修 → 策划配点 → 验收。每个环节的人不同，进度只存在于群里和口头确认里。

想做一个进度看板，卡在三件事：

1. **Git 里没有"已完成"这个提交。** 验收是口头/群里的动作，不会留下 commit。
2. **提交信息不可信。** 标题经常是"锅""宏""场景11"，不能拿来分类。
3. **工作区很脏。** 几百个未提交改动，不能把本地状态卷进来。

## 设计

### 核心思路：用改动类型，而不是提交信息

一个场景目录下改了什么，比提交标题可靠得多：

| 改动信号 | 推断阶段 |
|---|---|
| 一次新增大量 Spine/Timeline/场景/预制体 | 资源入库（整场景导入） |
| Timeline 修改，或 diff 里出现动画绑定字段 | 动效/动作 |
| `SceneXX/Effect/` 下的 prefab、粒子资源变化 | 特效 |
| Spine/图集被修改（不是新增） | 资源返修 |
| 主要是材质、层级、SortingOrder、颜色 | 材质/资源调整 |
| 纯坐标/显隐改动 | 点位配置 |
| 动作之后只剩微小改动（无动画/Spine/特效，Timeline ≤2，文件 ≤5） | 验收完成/微调 |

对"像点位/混合"的最近几次提交，再跑 `git show --unified=0` 读 Unity YAML 的 `propertyPath`，区分是动画绑定、坐标、材质还是粒子。

### 三条边界

1. **只看远端引用。** `git fetch --prune` 后读 `origin/feature/develop`，不 pull、不碰工作区，本地未提交改动不影响结果。
2. **人工确认单独存。** Git 看不到口头验收，所以用 `manual_status.json` 登记"某场景某天谁确认完成"；看板把它单列成"已完成（人工确认）"，并保留最后一次提交作为证据。
3. **推送只推一次。** 人工确认的完成状态推送成功后写 `push_state.json`，后续不重复推；改了登记内容才重推。

### 输出

- 命令行表格：末次提交、距今、状态（活跃/近期/静默）、近 7 天提交数、作者数、当前阶段、最近在做什么。
- JSON：给周报和其他脚本用。
- 静态甘特图：纯 HTML + `gantt_data.js`，双击打开；排期与负责人放 `gantt_schedule.json`，Git 状态按 `git_key` 叠到场景上。
- 钉钉日报：概览版和详细版；详细版读 `delivery_risk.json`，给出当天风险和需要盯的事项。
- 外部交付（还没入库的 zip/mp4）登记在 `scene_notes.json`，避免"Git 里没有 = 没做"。

## 几个关键决策

**1. 不用 AI 读提交信息。**
提交信息噪声太大，分类规则要可解释、可复核。文件路径和 Unity diff 是结构化信号，规则写死以后，任何人都能看懂为什么判成这个阶段。

**2. 不把"最近提交时间"当完成度。**
一次整场景导入会加几百个文件，提交习惯也会让次数失真。所以看板把"末次提交""距今""阶段"分开列，不合成一个分数。

**3. 人工确认不覆盖推断。**
`manual_status.json` 只影响展示和分组，不篡改 diff 推断；这样"人说的"和"代码里发生的"始终能对照。

**4. 先做只读，再谈自动化。**
工具不写仓库、不改工单、不发消息给制作同学，只生成看板和日报。降低被抵触的概率，也避免误判直接变成催促。

## 结果

- 每天的站会从"逐个问场景进度"变成"看看板 + 核对静默场景"。
- 验收完成但没正式记录的场景，有了"最后一次有效动作 + 人工确认"两条证据。
- 周报直接用 JSON 生成，不再手工整理。

## 边界与误判

- "验收完成/静默"只代表微调后没有新提交，不等于已交付上线。
- 合并提交没有文件列表，只计提交数，不参与阶段判断。
- 二进制资源没有文本 diff，只能按新增/修改和路径判断。
- 特效可能放在公共目录，脚本只统计场景目录下的 `Effect/` 和 `eff_` 资源；显示 0 不代表没做。
- 作者角色表是手工维护的，未登记的作者只按文件/diff 判断。

## 如果重来

1. **先和制作同学对齐"阶段"的定义**，再写规则。第一版把"资源返修"和"动效修改"混在一起，看板上看不出返修积压。
2. **人工确认应该更早做。** 一开始只信 Git，导致"已验收但没提交"的场景被标成静默，差点误报。
3. **甘特图不要一开始做。** 表格 + JSON 已经能回答问题，甘特图是后来为了给非技术同学看才加的。
