## 2. 六个技术概念，用 PM 语言解释

### 2.1 逻辑层 / 表现层分离（这是整个项目的地基）

#### 先说什么叫"抽到 Rust"

**"抽"不是翻译，是搬家。**

传统 Unity 项目里，游戏规则和界面是长在一起的。比如你点一张牌：

```
Unity 的 C# 脚本里写着：
  OnCardClick(这张牌) {
      if (是万能牌) { 按万能牌规则算 }      ← 规则
      if (combo 达成) { 加分、播特效 }        ← 规则 + 表现
      刷新界面();  播动画();  播音效();       ← 表现
  }
```

规则、UI、动画、音效全在一个函数里。**你想单独测"combo 判定对不对"，必须把整个游戏跑起来、点到那张牌、看画面。**

"抽到 Rust"就是把上面那段里的**规则部分**剪出来，搬到另一个工程里单独写：

```
Rust 逻辑层（纯计算，不碰界面）：
  输入：当前牌局状态 + 玩家操作（点了哪张牌）
  处理：按规则算新状态（牌是否有效、combo 是否达成、金币加多少）
  输出：新状态 + 一串"发生了什么"的事件（例如 [Combo达成, 金币+50]）

Unity 表现层（只负责好看）：
  把玩家的点击传给逻辑层 → 拿到事件列表 → 播动画、放音效、刷新界面
```

**关键差别**：逻辑层不知道有屏幕，也不知道有音效。它只会算。

这就是"逻辑层 / 表现层分离"。Bevy（Rust 的游戏引擎）在这个项目里只负责逻辑层那一半，Unity 负责表现层那一半。

#### Rust 是什么

**一句话**：一门编译型的系统编程语言，2015 年发布，由 Mozilla 主导。特点是**性能接近 C++，但编译器会在编译阶段就把内存错误挡掉**。

它和常见语言的区别：

| 语言 | 怎么运行 | 特点 |
| --- | --- | --- |
| C#（Unity 常用） | 编译成中间码，运行时由 .NET/IL2CPP 执行 | 开发快，但依赖运行时，跨端要各自打包 |
| Python | 解释执行 | 写得快，跑得慢，不适合逐帧逻辑 |
| C++ | 编译成机器码 | 快，但内存管理全靠人，容易崩 |
| **Rust** | **编译成机器码或 WASM** | **快 + 编译期防内存错误 + 无垃圾回收（GC）** |

**为什么游戏逻辑适合 Rust**：
- **确定性**：没有 GC 的"随机卡顿"，逐帧逻辑行为可预测
- **安全**：编译器挡住空指针、数据竞争这类会让游戏崩的问题
- **可编译成 WASM**：这是下面"热更"和"多端一致"的前提

**代价**：学习曲线陡、开发慢、招人贵。所以通常只把"规则"放进去，不把"画面"放进去。

#### 为什么可热更

先理解包体和逻辑的关系：

- **传统做法**：逻辑编译进 APK/IPA 里。改一条规则 → 重新打包 → 提审 → 用户更新。iOS 审核通常几天，救不了线上事故。
- **本项目**：逻辑是独立的 `.wasm` 文件，可以在**运行时**从服务器下载并加载。

```
用户启动游戏
   ↓
客户端检查逻辑层版本
   ↓
发现服务器有新版本 .wasm
   ↓
下载 → 校验签名 → 加载新逻辑
   ↓
规则生效，不需要重新发版
```

**本质**：逻辑从"编译进包体的二进制"变成了"可以替换的数据文件"。

⚠️ **但要说准确**：这不是"想改就改"。实际受三个约束：
1. **平台政策**：iOS / Google Play 对"改变产品核心功能的热更"有明确限制，通常只能修 bug、调数值，不能加新玩法
2. **接口兼容**：新的 `.wasm` 必须和客户端的调用接口对得上，所以要管接口版本
3. **失败兜底**：下载失败、校验失败要有回滚，否则用户直接进不去游戏

**面试别说"我们可以随便热更"**，要说：
> "逻辑层具备热更能力，改数值和修 bug 不用发版；但受平台政策限制，新玩法还是要走正常发版。"

#### 为什么多端一致

核心只有一句：**同一份代码，编译出同一个文件，各端加载同一个文件。**

```
        Rust 逻辑代码（只有一份）
                 ↓ 编译
            logic.wasm（只有一份）
        ↙        ↓         ↘
   Android     iOS       服务端/模拟器
```

对比一下传统做法的问题：

- 客户端用 C# 写一套规则
- 服务端用 Java/Go 再写一套规则（因为服务端跑不了 Unity）
- **两套代码，两份实现，就一定会有细微差异**

很多游戏线上出的事故——"客户端显示赢了，服务端判输"、"安卓能过、iOS 过不了"——根源就是规则被实现了两遍。

**本项目的做法**：客户端和服务端加载同一个 `.wasm`，规则物理上只有一份，想不一致都难。

**注意用词**：多端一致指的是**规则一致**，不是画面一致。画面本来就是各端各自渲染的。

#### 为什么测试能脱离客户端跑

因为逻辑层是**纯计算**，它不需要：

- 不需要 Unity 引擎（不渲染）
- 不需要显卡
- 不需要真机
- 不需要人点

只要有一个"能执行 WASM 的宿主"就行——一台服务器、一个 Node 进程、一个 Rust 测试程序都可以。

```
传统方式测一条规则：
  开 Unity（几十秒）→ 进游戏 → 点到那一关 → 点到那张牌 → 看结果 → 截图
  一个人一天跑不了几百次

本项目测一条规则：
  写一个牌局初始状态 → 调 play_card() → 断言输出
  一台服务器一晚上可以跑几万局
```

**这就是 LL-TEST 机器人能存在的原因**：它不需要"玩游戏"，它只需要"调用函数然后检查结果"。

而 PL-TEST 机器人为什么还要 Unity？因为**表现层必须看画面**——动画对不对、层级有没有穿模，这些只能渲染出来才知道。所以两个测试机器人分工不同，不是一个多余。

#### 一张表总结

| 维度 | 传统 Unity 写法 | 本项目（逻辑抽到 Rust/WASM） |
| --- | --- | --- |
| 规则在哪 | 散在 C# 脚本里，和 UI 混在一起 | 集中在 Rust 逻辑层 |
| 改规则 | 重新打包 + 提审 | 可热更（受平台政策约束） |
| 多端 | 各端各写/各编，容易不一致 | 同一份 wasm，规则天然一致 |
| 测规则 | 必须开客户端 | 脱离客户端，服务器批量跑 |
| 谁能改 | 会 Unity 的人 | 会 Rust 的人（分工更清晰） |
| 代价 | 上手快 | 开发慢、招人贵、要维护接口版本 |

#### 面试话术（30 秒版）

> "我们把规则从 Unity 的 C# 里抽出来，写成 Rust 编译成 WASM。这样带来三件事：一是规则只有一份，客户端和服务端加载同一个文件，不会出现两端算得不一样；二是逻辑可以热更，改数值不用发版；三是逻辑层不依赖 Unity，测试可以在服务器上批量跑，不用开客户端——这也是我们测试机器人能自动回归的前提。"

#### 面试话术（追问版：如果对方问"那为什么不干脆全用 Rust"）

> "因为表现层离不开 Unity 的渲染和美术管线，重写成本太高。分层的目的不是统一语言，是让规则和画面各自用最合适的工具，同时把测试解放出来。"

### 2.2 Rust 是什么

**一句话**：一门系统级编程语言，性能接近 C++，但内存安全（不会因为忘释放内存而崩）。

**为什么选它**（下面三条是常见选型理由，具体到你们项目以团队口径为准）：
- 要跨端、要编译成 WASM → Rust 的 WASM 支持最好
- 游戏逻辑要求确定性、不能崩 → Rust 没有垃圾回收，行为可预测
- 要长期维护 → 编译器能挡掉大量低级错误

**代价**：开发慢、学习曲线陡、招人贵。

**你要知道的边界**：你不需要会写 Rust，但要知道**"为什么不用 C#"**——因为要跨端 + 要 WASM + 要热更。

### 2.3 WASM 是什么

#### 一句话

**WASM（WebAssembly）不是一门编程语言，是一个"编译目标"**——你把 Rust / C / C++ 写好的代码编译成 `.wasm` 二进制文件，任何装了 WASM 运行时的宿主（Unity、浏览器、Node、服务端）都能加载并执行它。

**最好用的类比：WASM 是"代码的 PDF"。**
PDF 是"不管用什么软件写的文档，任何阅读器都能打开"；WASM 是"不管用什么语言写的代码，任何宿主都能运行"。

#### 它为什么存在

2015 年前后，浏览器只能跑 JavaScript。JS 很灵活，但有两个硬伤：

- **慢**：动态类型，逐行解释/即时编译，做 3D、视频编码、物理模拟不够快
- **语言绑定**：想把 C++ 的成熟库（比如游戏引擎、音视频编解码）搬到网页，只能重写

于是几家浏览器厂商联合做了 WASM：**定义一种二进制字节码格式，让任何语言都能编译过来，在浏览器里接近原生速度运行。**

2017 年主流浏览器全部支持，之后溢出到浏览器之外——Node、服务端、边缘计算、嵌入式、游戏引擎都在用。

#### 它是怎么跑起来的（机制）

```
Rust 源码
   ↓ rustc / LLVM 编译
logic.wasm（二进制字节码，不是机器码）
   ↓ 宿主加载（Unity / 浏览器 / Node / Wasmtime）
WASM 运行时（虚拟机）
   ↓ 逐条执行字节码
结果
```

三个关键点：

1. **它是字节码，不是机器码**。所以同一个 `.wasm` 文件，在 ARM 手机、x86 服务器、浏览器里都能跑——不需要为每个平台重新编译。
2. **它跑在虚拟机里，有沙箱**。模块只能访问自己的一块线性内存，**不能直接读文件、不能上网、不能调系统 API**。要用什么能力，必须由宿主显式"导入"给它。
3. **宿主和模块通过 import/export 通信**。模块导出函数（比如 `play_card`），宿主导入函数（比如 `播动画`）。跨这条边界有开销，所以不适合每帧调用几十万次的重计算。

#### 为什么它在这个项目里"承重"

你把逻辑抽出来只是第一步，**能不能变成可复用的模块，取决于编译成什么**。编译成 WASM 之后，四件事同时成立：

| 能力 | 原理 |
| --- | --- |
| **一份文件多端跑** | 字节码与 CPU 架构无关，Android / iOS / 服务端加载同一个文件 |
| **可热更** | `.wasm` 是独立文件，运行时下载 + 加载即可替换，不用重新打包发版 |
| **热更是安全的** | 沙箱保证下载来的代码只能算数，不能乱动设备——**没有沙箱，热更原生代码是危险的** |
| **可脱离引擎测试** | 只要一个 WASM 运行时就能跑，不需要 Unity、显卡、真机 |

**注意第 3 条**：很多人只讲"热更方便"，但真正让热更可行的前提是**安全边界**。你下载一段别人的代码到用户手机上执行，如果没有沙箱，等于把设备交出去。WASM 的沙箱让这件事变得可接受。

#### 和几个容易混淆的东西对比

| 对比对象 | 区别 |
| --- | --- |
| **JavaScript** | JS 是语言，WASM 是编译目标；WASM 更快、更可预测，但不是用来替代 JS 写业务的 |
| **Java 字节码（JVM）** | 思路像，都是"一次编译到处运行"；但 WASM 更轻、启动更快、沙箱更严格、不绑定语言 |
| **原生 .so / .dll** | 原生库要按平台分别编译（arm64/x86），不能沙箱，热更有风险；WASM 一个文件通吃且安全 |
| **Docker** | Docker 打包的是"整个系统环境"，很重；WASM 打包的是"一段代码"，毫秒级启动 |

#### 它不是万能的（面试要能说出限制）

- **跨边界有开销**：宿主和 WASM 之间传数据要拷贝，频繁调用会慢
- **不能直接碰系统**：要读写文件、联网，必须宿主开接口（这也是安全性的代价）
- **调试工具链不如原生成熟**：出问题定位比纯原生麻烦
- **不适合重渲染**：所以你们把渲染留在 Unity，只把规则放进 WASM

#### 面试话术（30 秒版）

> "WASM 是一个编译目标，不是语言。我们把 Rust 逻辑编译成 `.wasm`，它就变成一个可以在运行时加载的沙箱模块。三个价值：一份文件多端跑、可以热替换、下载来的代码也安全。代价是跨边界调用有开销，所以我们只把规则放进去，不把渲染放进去。"

#### 面试话术（追问版：为什么不直接写 C# 或者用 Lua 热更）

> "C# 编译进包体，改逻辑要发版；Lua 能做热更，但性能和类型安全都不如编译型语言，规则一复杂就容易出隐性 bug。WASM 是折中：既有编译期的类型和内存安全，又能运行时替换。"

### 2.4 Bevy 是什么

**一句话**：Rust 写的游戏引擎，核心是 **ECS**（Entity-Component-System，实体-组件-系统）。

**ECS 用大白话讲**：
- **Entity（实体）**：只是一个 ID，比如"这张牌"
- **Component（组件）**：挂在实体上的数据，比如"花色=红桃""点数=5""位置=x,y"
- **System（系统）**：一段逻辑，只处理"拥有某类组件"的实体，比如"所有带位置组件的实体，每帧移动"

**为什么适合逻辑层**：它只管数据和规则，不管渲染。你们的表现层在 Unity，逻辑层用 Bevy 正好互补。

**你要知道的边界**：Bevy **不是 Unity 的替代品**。Unity 管画面，Bevy 管规则。

---

### 2.5 SurrealDB 是什么

**一句话**：一种"多模型"数据库——既能存文档（像 MongoDB），又能存关系（像 MySQL），还能存图（像 Neo4j），而且可以嵌入到程序里运行。

**在你们项目里的作用**：存知识库——需求、配置、测试规则，供 6 个机器人查询。

**为什么不用 MySQL**：知识库是"文档 + 关系"混合结构，一个库能覆盖，不用维护两套。

**对 PM 的意义**：你说的"1200+ 知识节点"，物理上就存在这里。机器人靠查它来理解需求。

### 2.6 GitLab Issue = 状态机（这条最重要，因为这是你的活）

你们的流程（`部署机器人（并发）.md` 里有据）：

- 机器人每 2 分钟轮询 GitLab 的 open issue
- 按 **label** 决定派发给谁：
  - `BUG` → BUG 机器人
  - `PR` + `审核通过` → PR 机器人
  - `已完成` → 进入测试
  - `测试通过` / `测试未通过` → 回给对应开发机器人
  - `人工` → 停下来等人
- 去重规则：`issueId + 评论时间`
- 结果同步到钉钉群"研发群"

**本质**：**用 Issue 当数据库，用 Label 当状态，用轮询当触发器。**

这就是一套不用写代码的工作流引擎。**这套设计你可以完全认领**——它是流程设计，不是编程。

**面试话术**：
> "我们的任务流不是一个看板，是一个状态机：issue 是任务，label 是状态，机器人按状态取活，遇到 `人工` 标签就停下来等人确认。好处是状态永远只有一个来源，不靠口头同步。"

### 2.7 两个顺带知道的名词

- **iroh**：Rust 的 P2P 网络库。你们用它做机器人健康检查——每 2 分钟看工作区机器人是否在线，不在线就切回 main 分支重启。
- **MCP**：Model Context Protocol，让 AI 调用外部工具的协议。Unity CLI 就是通过它被 AI 调用的。

这两个只需一句话带过，不用深讲。

| **人工闸门（AI 只提议）** | **你** | **完全认领** |
| **测试维度 / 基线 / 规则库** | **你** | **完全认领** |

**记住一句话**：**你认领"流程设计"和"验收标准"，不认领"代码实现"。** 这不是示弱，这是 PM 岗的正确边界。

## 4. 三个能讲深的点（面试主力弹药）

### 4.1 人工闸门：为什么 AI 只能提议

> "AI 生成的任务拆解，如果直接落库，一旦理解错需求，整条流水线会按错的方向跑，返工成本极高。所以我们定了一条：AI 出草稿，人签字才生效。这不是不信任 AI，是**把纠错点放在成本最低的地方**。"

这段讲的是**治理设计**，任何 AI PM 岗都吃这套。

### 4.2 测试机器人存在的前提

> "测试机器人能跑起来，前提是逻辑层能脱离 Unity。如果逻辑和画面绑死，机器人只能截图比对，成本高还不稳。所以架构和流程是一起设计的。"

这段讲的是**架构为流程让路**，显示你有系统思维。

### 4.3 状态机替代口头同步

> "以前进度靠问，现在进度靠 label。issue 只有一种状态，谁都能查。会议从'同步进度'变成'解决阻塞'。"

这段讲的是**流程工具化**，对应所有 JD 里的"机制建设"。

## 5. 被问住时的标准回答（背三句）

1. **"这块具体实现是引擎同学负责的，我关注的是验收标准和流程。"**
2. **"我能讲到架构层面——为什么分层、分层后测试怎么跑；代码细节我不认领。"**

## 9. 一段可以直接背的 60 秒架构介绍

> 该 AI 研发项目 的技术架构是三层：Unity 做表现层，Rust 编译成 WASM 做逻辑层，SurrealDB 做知识库。
> 这样分层的最大好处不是性能，是**逻辑可以脱离客户端单独跑**，所以我们的测试机器人才能无人值守地回归。
> 流程上，我们用 GitLab issue 当任务单，用 label 当状态——BUG、PR、人工、已完成、测试通过，机器人每两分钟按状态取活，遇到"人工"就停下来等人。
> 我负责的是后面这半段：流程设计、状态机、人工闸门和验收标准。技术选型是引擎同学定的。
