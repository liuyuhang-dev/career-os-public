# 游戏测试的标准流程与测试方法

**这份文档回答两件事:** ① 我们这套测试是怎么组织的、每一步凭什么算做完;② 它对应的是业界哪套标准做法,以及用例本身怎么设计。

它和用例集的分工:

| 文件 | 内容 |
|---|---|
| 本文 | 流程、标准对标、用例设计方法、人的位置、怎么开始用 |
| `specs/baseline-suite.md` | 通用基线用例集(39 条,任何版本复用) |
| `specs/version-suite.md` | 专属版本用例集(版本验收 / 回归 / 冒烟 / 发版门禁) |

## 一、这套流程对标的是什么(要跟外面说的时候用这张表)

标准原文以官方出版物为准;下面用的是它们的概念与形状,不是逐条引用。

| 业界标准里的东西 | 我们这套里的名字 | 落在哪 |
|---|---|---|
| 测试过程(ISO/IEC/IEEE 29119 的「过程」部分:组织级 / 管理级 / 动态测试过程) | 压成一条流水线:三道闸门 → 静态交叉 → 复核 → 执行 → 判定 → 提 bug → 对账 | `scripts/pipeline.py` |
| 测试文档(29119 的「文档」部分) | 用例规格(.md)+ 派生用例(.json)+ 复核单 + 报告 + bug 单,五份互相对得上 | `specs/`、`artifacts/` |
| 测试设计技术(29119 的「技术」部分 / ISTQB 的测试设计技术) | 等价类、边界值、判定表、状态迁移、场景法、成对组合、错误推测、探索性测试 | 见第六节 |
| 测试过程活动(ISTQB:计划 → 分析 → 设计 → 实现 → 执行 → 收尾,全程监控与控制) | 六步版本验收流程 + 每阶段的准出条件 | `version-suite.md` |
| 入口 / 出口判据(entry / exit criteria) | 每步的「产出」+ 发版门禁表 + 版本验收单 | `version-suite.md` |
| 风险驱动测试(风险 = 可能性 × 影响) | 关注点台账(每条写「为什么担心」)+ 按变更影响面选集 | `assets/concern-register-template.csv` |
| 测试分层(测试金字塔 / 测试奖杯) | 六层:L1 静态交叉 → 显示层 → 内部一致性 → 采集 → 探索 → 人工 | `baseline-suite.md` |
| 左移(shift-left) | 出包前的 L1 零设备静态交叉;写用例阶段就要求「期望必须有来源」 | `scripts/check_config.py` |
| 缺陷与能力缺口分开 | 判定结果词表:`pass` / `fail` / `blocked` / `skipped` / `pending_*` —— 能力没到位记 `blocked`,**不许记 pass** | `references/6-triage.md` |
| 缺陷闭环(回归资产化) | 每个线上缺陷固化成一条永久回归用例(`EXP-*`) | `version-suite.md` |

**三处我们故意跟"常见做法"不一样:**

1. **不用通过率当唯一指标,改用实际执行率**(门禁里是「执行率 ≥90%」)。通过率在"很多用例根本没跑"时会很好看。
2. **不追求覆盖率百分比,追求可追溯**:每条用例的期望必须能指回一个来源(需求 / 不变量 / 配置 / 源对);指不回去的期望不许写。
3. **不许"没人判"被读成"没问题"**:没有证据 = `blocked`,能力没实现 = `skipped`,两者都带原因进报告。

## 二、主题一:我们的游戏怎么测试、需要跑哪些内容

### 六个层,每个层只承诺它判得了的东西

| 层 | 测什么 | 判定方式 | 用例 |
|---|---|---|---|
| L1 静态交叉(出包前,零设备) | 配置表自洽:悬空引用、主键重复、枚举越界、字段缺失 | 机械脚本 | 出包前静态检查清单 |
| L3-a 显示层 | 关键路径、UI 完整性、资源与文案、开关可见性 | 封闭视觉断言 | BOOT / CORE / UI / NUM / ART / TEXT / SYS / FLAG 等 |
| L3-b 内部一致性 | 货币、背包、存档、结算、幂等、弱网、更新、账号 | 状态上报 | COIN / BAG / SAVE / IDEM / NET / HOTFIX / ACCT 等 |
| 采集 | 崩溃 / ANR、启动耗时、FPS、内存增长 | 机械比对(logcat / perf) | CRASH / PERF / MEM |
| 探索 | 长尾缺陷:流程断裂、卡死、异常弹窗 | 只报异常候选,不判通过 | EXP-SYS-C01 |
| 人工 | 手感、美术质量、品牌一致性、合规清单 | 人工确认 | ART-C03 / MKT-C01 / COMPLY |

**为什么这样分:** 判不了的**明确标人工**,能力缺失的**显式 blocked**,不拿视觉假装覆盖内部一致性。这张表就是「跑哪些内容」的答案。

### 什么时候跑什么

| 时机 | 跑什么 | 时长量级 | 准出 |
|---|---|---|---|
| 每个候选构建 | 冒烟集(9 项) | ≈20 分钟 | 全绿才允许进全量回归 |
| 每个发版 | 全量基线 + 版本差异用例 | 1–2 小时 | 见发版门禁表 |
| 引擎 / SDK / 宿主升级 | 全量基线 × 机型矩阵 | 按矩阵规模 | 无崩溃、无 P0 |
| 上线后持续 | 探索 + 线上反馈回流固化 | 长时 | 发现率与误报率达标 |

### 开跑前逐项确认(环境与前置)

测试账号与测试商品固定(虚拟支付)· 固定入口可用 · 状态上报通道就绪 · 每台设备建立坐标档案 · 性能基线已采一次。

## 三、主题二:美术、策划、程序、市场怎么覆盖

| 角色 | 他们最怕的缺陷 | 怎么判 | 只能人工的部分 |
|---|---|---|---|
| 美术 | 资源缺失、贴图错乱、文字截断、图标张冠李戴 | 视觉封闭断言 + 像素回归(带遮罩阈值) | 画面质量、风格统一、品牌元素一致性 |
| 策划 | 数值显示错、配置没生效、文案错、需求做偏、**埋点数据不可信** | 视觉断言 + 配置 × 运行时交叉 | 难度曲线、趣味性、引导体验 |
| 程序 | 崩溃、卡死、内存泄漏、弱网失效、丢档、重复入账、**热更坏了不可玩** | 采集 + 状态上报 + 故障注入 | 崩溃根因定位(采到栈之后的代码定位) |
| 市场 | 素材与游戏不符、分享/广告奖励出错、包体加载失败、礼包码被薅、**上架过审被卡** | 源间核对 + 幂等断言 | 素材与落地页逐条核对、合规清单逐项核对 |

**四个角色不是四套测试**,是同一条流水线上的四种视角:美术→显示层与像素回归,策划→数值与配置交叉,程序→采集与内部一致性,市场→商业化链路与外部承诺一致性。人工不是被移除,而是被收敛到「只能人工」那一列。

## 四、主题三:版本更新的内容如何验收、如何测试

### 六步,每步都有产出

| # | 步骤 | 动作 | 产出 | 准出 |
|---|---|---|---|---|
| 1 | 变更盘点 | 逐条读变更清单,标出受影响模块 | 影响面清单 | 「无法定位影响面」的变更也被列出来 |
| 2 | 生成版本用例 | 每条版本需求拆成 `REQ-VER-*` | `specs/` 增量 | 每条需求子句 ≥1 条用例 |
| 3 | 用例复核 | 人逐条批准 / 驳回 | 复核单,`state=approved` | **唯一的人工用例关卡** |
| 4 | 冒烟 | 在候选包上跑冒烟集 | 冒烟结论 | 全绿;不过不许进全量 |
| 5 | 全量回归 | 全量基线 + 版本用例 + 按影响面加选 | 运行结果与证据 | 执行率 ≥90% |
| 6 | 判定与门禁 | 判定、提 bug、对照门禁表 | 报告 + 放行建议 | **放行由人签署** |

### 版本差异用例的生成规则

版本新增 / 修改内容的用例**只能从该版本需求文档派生**,并带 `req_refs` 指回需求。**版本需求文档就位前这一步不做** —— 没有需求就写不出合法期望,凭观察写出来的「期望」会把现有 bug 固化成期望。文件里给的是填充模板和反例对照。

### 发版门禁(建议阈值,需团队确认后写死)

冒烟集全绿 · P0/P1 全绿 · **实际执行率 ≥90%** · 新增崩溃 0 · 启动耗时 ≤ 基线 120% · skipped/blocked 全部有原因 · **放行决策人工签署**。

## 五、主题四:如何回归以前的功能、如何冒烟

### 回归集是什么

**回归集 = 全量基线 + 版本级用例 + 历史缺陷固化用例(`EXP-*`)+ 探索发现固化用例。**
兜底规则:**每个线上缺陷都要变成一条永久回归用例**;缺陷库只增不减是不允许的。

### 按变更选集(控制回归时长)

改登录跑 BOOT/LOGIN/SAVE/NET/ACCT;改商城支付跑 COIN/IDEM-C01/C02/BAG/CFG;改 UI 资源跑 UI/ART-C01/ART-C02/NUM/TEXT;改分包热更跑 PKG/HOTFIX/VER-C02;改埋点跑 CONS-TRACK;合规相关跑全量(过审是整包的);**影响面无法定位 → 默认全量**。

### 冒烟纪律

冒烟**只引用基线用例、不重复定义**(避免两处维护漂移)。冒烟不过不许进全量;冒烟发现的 P0 直接停测转修复;入口不可达先修环境链路,**不把环境问题记成产品问题**。

### 回归集自己的维护(这一节最容易被省掉,也最容易烂)

| 事项 | 规则 |
|---|---|
| 用例寿命 | 每条用例有主人与最近一次执行时间;连续 N 个版本没跑的要被点名,而不是静静烂掉 |
| 不稳定用例(flaky) | 同一条用例多轮结论不一致 → **先修判定,不许直接改成通过**;修不动就降级为人工并写明 |
| 长期 skipped | 每个 `skipped` 带原因与负责人;长期 `skipped` 视为未覆盖,进放行判断 |
| 时长预算 | 全量回归有预算上限(如 2 小时);超了就按影响面分层,而不是偷偷少跑 |
| 固化节奏 | 每个线上缺陷、每次探索发现,下一轮开始前变成用例 |

## 六、用例设计方法(标准方法里最实用的一块)

每条配一个游戏里的真实例子。

| 方法 | 一句话 | 例子 |
|---|---|---|
| 等价类划分 | 把输入分成"行为应该一样"的几类,每类取一个 | 金币额度:够 / 刚好 / 不够,三类各一条 |
| 边界值分析 | 错的通常在边界上 | 余额 0、余额 1、正好等于价格、比价格少 1 |
| 判定表 | 多个条件组合时,列出该组合下的期望 | 支付:响应丢失 × 客户端重试 × 服务端幂等 → 只扣一次、只发一次 |
| 状态迁移 | 把对象的状态与允许的迁移画出来,测非法迁移 | 会话 `connected → reconnecting → connected`;`pendingOps` 非空时不许判"已收敛" |
| 场景法 | 按用户走完一条完整链路 | 启动 → 一局 → 结算 → 返回,断链即失败 |
| 成对组合(正交) | 全组合太多时,保证每两个因子的组合都出现过 | 机型 × 分辨率 × 网络 × 渠道:不打全组合,按机型矩阵铺 |
| 错误推测 | 凭经验猜哪里会烂 | 礼包码被薅、重复领取、改系统时间刷体力、断网时疯狂点购买 |
| 探索性测试 | 带着问题去乱走,产出候选清单 | `EXP-SYS-C01`:30 分钟 / 300 次操作,报异常候选,不判通过 |
| **不变量** | 不管怎么操作都必须成立的性质,游戏测试里最好用 | 余额不为负、背包无重复条目、存档不回退、重放不双倍入账 |
| **源间一致性** | 两个源描述同一件事时必须自洽 | 配置表 × 运行时、埋点定义表 × 事件流、投放素材 × 落地页、道具表 × 图标资源 |

**什么时候用哪个:**

| 手上有什么 | 先用什么 |
|---|---|
| 一份需求文档 | 场景法 + 判定表 + 等价类/边界值 |
| 一张配置表 | 源间一致性(L1 静态交叉)+ 配置 × 运行时 |
| 一条"绝不能发生"的底线 | 不变量 |
| 一个多因子环境(机型/渠道/网络) | 成对组合 + 机型矩阵 |
| 一个没人知道会出什么的新系统 | 探索性测试 → 发现固化成回归用例 |
| 一个线上缺陷 | 错误推测反推场景 → 写成不变量或一致性用例 |

## 七、"人"的位置:三处不许自动化

1. **期望的来源** —— 期望不能来自观察(看屏幕上是多少就写多少,会把现有 bug 固化成期望)。
2. **用例复核批准** —— 唯一必须人工逐条过的关卡(`state=approved` 之前执行一律 `blocked`)。
3. **放行签署** —— 自动化到「报告可信、证据齐全」为止;能不能发是人的决定,要留签署人与日期。

**只能人工的清单**不是被放弃的部分,是被**收敛**的部分:手感、观感、品牌一致性、素材与落地页逐条核对、合规条款核对。它们都进报告,只是判定者是人。

## 八、怎么开始用(第一天 / 第一周 / 第一个版本)

- **第一天**:项目提供配置表 → 跑通 L1 静态交叉(零设备);冻结机型矩阵名单;准备测试账号与测试商品(虚拟支付);每台设备建坐标档案。
- **第一周**:跑通冒烟集 9 项,出第一份报告;把性能基线采一次(首版人工采,之后自动比对)。
- **第一个版本**:走完六步验收流程;把门禁表里的"建议阈值"按团队实际改成写死的阈值;第一份版本验收单存档。
- **之后每个版本**:线上缺陷与探索发现各固化成一条用例;回归集开始自己长大。

**当前的前置缺口**(这些不补齐,相关的层只能返回 `blocked`,而不会假装通过):判定轮未实现(截图停在 `pending_judgment`,现阶段由人看截图确认)· 客户端状态上报未接入(弱网/幂等/存档类没有判定依据)· iOS 通道未验证(`skipped`)· 机型矩阵名单未冻结 · 合规清单需发行方提供。

## 九、术语表(对外交流时用同一批词)

| 词 | 含义 |
|---|---|
| 用例规格(spec) | 自然语言用例文件(`specs/*.md`),人读人改的源 |
| 派生用例(case) | 机器可执行的那份(`03-cases/*.json`),由规格派生并经复核 |
| 判定项(check) | 一条期望对应的一个可判定问题(`E1` → 一条判定项) |
| 判定模式 | `vision-closed`(视觉封闭断言)/ `state-report`(状态上报)/ `replay`(回放)/ `explore`(探索) |
| 期望来源 | `requirement` / `invariant` / `config` / `consistency` —— 期望必须能指回其一 |
| 源对 | 一致性用例要比对的两个源(`A × B`) |
| 执行率 | 真正跑了的用例占比(与通过率是两个数) |
| 放行门禁 | 发版前必须全过的若干条,人工签署生效 |
| 固化用例 | 由线上缺陷或探索发现转成的永久回归用例(`EXP-*`) |
| 不变量 | 不管怎么操作都必须成立的性质 |

## 十、诚实的边界

这套东西的价值在于**它不会说谎**:判不了的说判不了,没证据的说没证据,没跑的说没跑。代价是**在能力补齐之前报告会显得"不够绿"** —— 那是真实状态,不是流程失败。

要让它真正跑起来,按顺序补三件:状态上报通道 → 判定轮 → 真机执行器接入。三件里缺任何一件,对应层的用例都会如实返回 `blocked`,不会伪装成通过。
