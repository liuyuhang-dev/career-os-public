# 15 · 边界与异常的完备性保证

**策划说"你都考虑到了"的前提不是报告好看,而是真的没漏。**
报告写得再漂亮,漏掉一个上限截断,他照样会在群里问"这个怎么没测"。
所以这一层要解决的是**机制问题**:怎么保证边界与异常是**推出来的**,而不是**想起来的**。

---

## 一、靠"想"一定漏,靠"乘"才不漏

一张需求文档里的每一条子句,都要去乘一张**维度表**(`assets/check-dimensions.csv`,默认 12 个维度):

```
需求子句 × 维度 = 完备性矩阵
```

每个格子只有三种合法状态:

| 状态 | 要求 |
|---|---|
| **适用** | 必须给出**产出**(一条可判的关注点,进登记册) |
| **不适用** | 必须写明**为什么**(比如"本条是单局结算,不存在没有数据的情形") |
| **未判断** | **不允许** —— 检查器会点名,这就是漏 |

```bash
# 1) 生成矩阵(子句 × 维度,规则只给"建议适用",结论由 AI/人定)
python3 "$SKILL_DIR/scripts/concerns.py" \
  --intake requirements:test-artifacts/<f>/01-requirements.json --feature <模块> \
  --matrix-out test-artifacts/<f>/matrix.csv

# 2) 逐格填(AI 干,人复核来源与优先级)

# 3) 完备性检查:适用没产出 / 不适用没原因 / 还没判断 —— 全部点名
python3 "$SKILL_DIR/scripts/concerns.py" --matrix-check test-artifacts/<f>/matrix.csv

# 4) 产出转成登记册(矩阵是"扫一遍",登记册是"台账")
python3 "$SKILL_DIR/scripts/concerns.py" \
  --matrix-to-register test-artifacts/<f>/matrix.csv > test-artifacts/<f>/concerns.csv
```

## 二、12 个维度(策划脑子里那几类)

| # | 维度 | 标准问法(节选) |
|---|---|---|
| D1 | 正向:按需求做到 | 正常路径上真的做到了吗(界面/文案/数值与需求一致) |
| D2 | **数值边界** | 0 / 1 / 最小 / 最大 / 上限 / 超上限 分别什么表现?上限截断吗?会负数或小数吗 |
| D3 | 空与缺失 | 数据为空(没记录/没奖励/没订单)时界面与流程怎么表现 |
| D4 | **重复与幂等** | 重复点击、请求重试、回调重投、断线重放会不会重复生效 |
| D5 | **中断与恢复** | 做到一半断网/切后台/被杀进程/来电,恢复后不丢不重不回退吗 |
| D6 | 时序与竞态 | 快速连点、并发、响应乱序、超时重试会出问题吗 |
| D7 | 权限与合规 | 未授权/拒绝授权/权限被关/协议未同意时的表现 |
| D8 | 状态迁移 | 首次 / 已存在 / 已过期 / 已完成 各状态对不对?会不会卡中间态 |
| D9 | 跨端与跨设备 | 换设备、多端同登、低端机与不同分辨率下是否成立 |
| D10 | 资源与配置 | 配置缺失、配置与需求不一致、热更中断时的表现 |
| D11 | 时间与周期 | 跨天/跨周刷新瞬间、活动结束瞬间、服务器与本地时间不一致 |
| D12 | 数据一致性 | 本地缓存与服务器不一致、部分成功、回滚时用户看到哪一份 |

**这张表就是"策划的脑子"的结构化版本**:D2/D4/D5 是他说"边界值和异常你都想过了"的那几类。
每个维度的完整问法与例子在 `assets/check-dimensions.csv`。

**维度是数据,加一行就多一个维度** —— 不用改代码、不用改 JSON:

```bash
# 直接编辑(推荐)。列:id,名称,标准问法,触发条件,示例,标签,全局,备注
#   触发条件 = 命中这些关键词时才建议适用(顿号/逗号分隔);全局 = 是 表示每条子句都过
#   例:加一个"多语言"维度 -> D13,多语言,最长语言下文案会不会超框?,语言、文案、翻译,俄语超框,文案,否,新增
python3 "$SKILL_DIR/scripts/concerns.py" --dump-dimensions-json   # 导出给别的工具/技能读的 JSON
```

`check-dimensions.json` 是**派生产物**:别的技能(如 axiom-testdesign)读它,
改了 CSV 忘了重导会被 `check_docs.py` 点名(两边不一致就是"两份判据")。

## 三、为什么这样策划会放心(而不是觉得我们在凑数)

1. **维度是他认得的**:上限截断、重复领取、断线重连、跨天刷新 —— 他自己就是这么想的。
   他看到的是"你们把我想的每一类都列了",而不是"你们凑了一堆用例"。
2. **不适用也要给理由**:比如"D11 时间与周期:需求写的是单局上限,不涉及跨天" ——
   **这条理由本身就是信任的来源**:说明我们不是漏了,是判断过。
3. **格子数得出来**:36 格、适用 24、不适用 12、未判断 0 —— 策划可以数。
   比"覆盖率 92%"这种数字可信得多。
4. **它跟结论连得上**:有产出的格子 → 登记册 → 结论页 → 给他的答复(测了没/有没有 bug)。

## 三·五、第二张表:常识别表(与需求无关的那一半)

上面那张矩阵是**"按你写的展开"**;还有一半是**你没写、但这是常识**:

> 金币不能为负、体力不能为负、道具不超上限、同一操作不重复生效、
> 存档不回退、显示不出 NaN、点击必有响应、倒计时不倒流、操作 ID 唯一、不崩不白不卡。

需求文档里未必写这些(合成文档里就没写"体力不能为负"),但策划心里有 ——
**把它们单独列出来并逐条给结论,才是真的放心**(说明不只是在抄需求)。

```bash
# 从需求文本里认出实体(金币/体力/物品/结算/存档/操作ID…)-> 套上对应常识不变量
python3 "$SKILL_DIR/scripts/concerns.py"   --intake requirements:test-artifacts/<f>/01-requirements.json --feature <模块>   --common-sense-out test-artifacts/<f>/common-sense.csv
# 纪律与矩阵完全一致:每条要么给出断言(产出),要么写明不适用与原因
python3 "$SKILL_DIR/scripts/concerns.py" --matrix-check test-artifacts/<f>/common-sense.csv
python3 "$SKILL_DIR/scripts/concerns.py"   --matrix-to-register test-artifacts/<f>/common-sense.csv   # 并入登记册

```

规则表在 `assets/common-sense.json`(**21 条**,分四类):

| 类别 | 条目 |
| --- | --- |
| 数值与资产 | 不得为负 / 不超上限 / 概率与权重合法(0..1、同组之和不超 1、保底不跳变) |
| 数量与守恒 | 消耗产出对得上(不凭空增减) / 物品不重复计入 / 标识符唯一可追 |
| 重复与中断 | 操作不重复生效(点重/重试/重投/重放) / 失败不留痕(无半成品与副作用) / 存档不回退 / 表现层幂等 |
| 界面与体验 | 显示不出 NaN 与占位符 / 显示值等于权威状态 / 点击必有响应 / 空态与边界态有表现 / 文案完整不超框 / 时间不倒流且改时间不能获益 / 长跑不退化(内存帧率) / 等待有超时上限 / 互斥与禁用态真的挡住 / 全局不崩不白不卡 |

每条带**建议断言写法**与"为什么这是常识"。三条纪律:

1. **不硬塞**:需求里没出现的实体不会冒出来。
2. **也不静默丢掉**:没命中的照样成行,写「不适用 + 为什么」(这份需求里没出现这类对象)。
   否则表看起来干净,实际是少了几行 —— 覆盖形状必须完整。
3. **匹配要看正文也要看备注**(玩家可见反馈):"界面显示 / 动画 / 文案 / 空态"这些词常常
   只写在玩家可见反馈里,只看正文会整类漏掉(实测漏过 CS-06 显示异常那一整类)。

## 四、完备性是相对的,而且可以变强

**不要声称"穷尽了所有可能"** —— 那是吹。能声称的是:**"按这张 12 维表逐格过了,没有空格子"**。

维度表本身可以扩,而且扩的动作是机械的、有收益的:

1. 线上出了新类型的缺陷(比如"跨时区导致的每日刷新错乱") → 回补一个新维度(D13 时区);
2. 重跑矩阵 → **新增的格子会被自动标出来** → 那些就是"以前没考虑到的";
3. 逐格处理(适用就给产出,不适用就写原因)。

所以这张表**每出一次事故或舆情就变强一次**,而不是靠人的记忆力。

## 五、例子:R-3.1 的 12 格

见 `examples/matrix-filled-sample.csv`(三条子句共 36 格,全部填完):

| 维度 | 结论 | 产出 / 不适用原因 |
|---|---|---|
| D1 正向 | 适用 | 结算后金币增量 = 击杀数×10(击杀 8 → +80) |
| D2 数值边界 | 适用 | 上限 500:击杀 60 时是 500 不是 600;击杀 0 时增量为 0;不出现负数/小数 |
| D3 空与缺失 | **不适用** | 单局结算不存在"没有数据"的情形(击杀数必为 0 及以上) |
| D4 重复与幂等 | 适用 | 重复点结算不重复发放(已有用例,现 fail → BUG-001/002/003) |
| D5 中断与恢复 | 适用 | 结算超时/断线:金币不增不扣,重连后以服务端为准 |
| D6 时序与竞态 | 适用 | 结算动画中再点结算 / 立刻开下一局:奖励不串局 |
| D7 权限与合规 | **不适用** | 结算不涉及授权与隐私 |
| D8 状态迁移 | 适用 | 未结束/已结束/已结算 三态下结算入口的表现 |
| D9 跨端与跨设备 | **不适用** | 单局结算与设备无关(跨端一致性由存档类需求覆盖) |
| D10 资源与配置 | 适用 | 上限值与配置表 settle_coin_cap 一致;配置缺失时的行为 |
| D11 时间与周期 | **不适用** | 需求写的是"单局"上限,不涉及跨天刷新 |
| D12 数据一致性 | 适用 | 上报 coinDelta 与界面显示一致(界面 80、入账 40 = 缺陷) |

**对比展开前的粗粒度版本**(只有"D1 正向"那一条),现在策划能看到:
上限截断、击杀 0、重复点击、结算中断、竞态串局、状态三态、配置一致、上报一致 ——
**这就是"你都考虑到了"的样子;而它是乘出来的,不是想出来的。**
