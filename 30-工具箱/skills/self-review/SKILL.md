# Self Review — 有证据的自评

## 这个 skill 解决什么

自评最容易写成两种废稿：罗列做了什么（只有活动没有结果），或形容词堆砌（"积极主动、认真负责、有主人翁意识"）。评审者要的是可核对的事实：你做了什么、产生了什么可验证的变化、其中哪些是你独立完成的、和考核标准怎么对应。

写自评的目标不是"显得忙"，是让评审者在打分时不需要猜。

## 三条规矩

1. **证据只能来自用户给的事实。** 数字、项目名、时间、影响范围，缺了就问，不许补。一条编造的数字被追问一次，整份自评的可信度归零，后面写得再好也没用。
2. **区分"我做的"和"团队做的"。** 每一条写清角色（主导 / 负责 / 参与 / 支持）。边界含糊不是谦虚，评审者会自己往低打，而且你没法反驳。
3. **弱点要写，但要带处理方案。** 只写优点的自评不可信；写"沟通有待加强"却不给动作，等于承认一年没改进。

## 工作流

1. **收集原料。** 让用户提供：周报 / 项目清单 / OKR / 上次自评 / 领导反馈 / 晋升标准。没有就让用户口述 5–10 件事，一件一句话，不用组织语言。
2. **建证据表。** 每件事拆成：行动 → 结果（带数字）→ 我的角色 → 证据出处。缺的格子标 `待补`，一次性问完，不要写一句问一次。
3. **选主线，3–5 条。** 按「业务影响 × 与考核维度的关联度」排序。不要平均用力——八条平庸的条目会稀释掉两条真正强的。
4. **压成 STAR 条目。** 情境一句，行动两句（含关键决策和取舍），结果一句（数字 + 对比基线）。基线比绝对值重要："错误率 0.3%" 不如 "错误率从 1.2% 降到 0.3%"。
5. **对齐考核维度。** 若用户给了绩效标准或职级要求，把条目映射过去；没有覆盖的维度明确写"本周期无相关项目"，比硬凑一条更可信。
6. **写改进项 1–2 条。** 每条给：现象 → 原因 → 下周期动作 → 如何验证。动作要小到今天就能开始做。
7. **自检后交付。** 按下面的清单过一遍再给用户。

## 证据条目格式

```text
【事项】结算链路对账重构
【情境】原链路每月人工对账 3 人日，错账率 1.2%，财务每月提一次工单
【行动】主导设计对账规则引擎；推动财务确认 12 条边界规则；分两期灰度，第一期只覆盖 B 端
【结果】人工对账降至 0.5 人日/月，错账率 0.3%；上线后 4 个月零资损
【我的角色】技术负责人（带 3 人），规则设计独立完成，跨部门推动由我发起
【证据】项目周报 2026-03；监控看板；财务确认邮件
```

## 输出结构

1. **一句话定位**：本周期我最重要的贡献是什么（一句，不堆词）。
2. **核心贡献 3–5 条**：上面的条目格式，每条一个小标题。
3. **职责内工作**：一段话带过常规职责，不逐条展开。
4. **不足与改进**：1–2 条，带动作和验证方式。
5. **下周期重点**：2–3 条，与上面改进项呼应。
6. **待补充清单**：还缺哪些数据、需要用户去查什么。

## 检查清单

- 每个数字都有出处，或明确标了"用户口述，未核实"
- 每条结果都能回答"所以呢"——对业务意味着什么
- 没有形容词单独成句
- 角色边界写清，团队成果不冒领
- 不足项有动作和验证方式
- 全文没有出现用户没说过的事实
- 长度与考核份量匹配（普通绩效 1 页，晋升材料可 2–3 页）

## 反模式

- 把周报按时间顺序抄一遍 → 评审者看不出重点
- 用"参与了"包装核心贡献 → 自贬
- 只写结果不写关键决策 → 看不出你的判断力，和"运气好"无法区分
- 改进项写成"加强学习" → 无动作、无验证、等于没写
