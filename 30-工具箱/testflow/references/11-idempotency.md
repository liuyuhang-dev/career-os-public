# 11 · 幂等与重复执行类缺陷

以「重复支付」为典型代表。这类缺陷黑盒测试基本覆盖不了,但它也不是只能靠人肉 code review——本文说明框架怎么处理它,以及边界在哪。

---

## 一、先说清楚为什么黑盒测不到

不是"点两次按钮"就能测出来。真实的重复支付来自这些场景:

| 场景 | 机制 |
|---|---|
| **响应丢失导致重试** | 请求发出 → 服务端处理成功 → 响应在回程丢失 → 客户端超时 → 重发 → 服务端处理了两次 |
| **渠道回调重复投递** | 支付渠道(微信/抖音)回调超时会重试,同一笔订单的回调被投递多次 |
| **本地队列重放** | 超时/离线期间的待处理订单排队,恢复后重放,与先前的成功请求叠加 |
| **进程被杀后重启** | 未确认状态的订单在重启后被重新提交 |
| **用户重复提交** | 唯一一个黑盒真正能撞到的场景,但它**恰恰是最少见的** |

**界面上的表现往往完全正常。** 重复发货可能表现为"道具多了"(还算看得见),而"扣款两次但只发一次货"在客户端界面上根本不可见——需要看服务端账目和对账数据。

而且这些场景都要求**特定时序**:要在"请求已发出、响应未收到"的那个窗口里制造中断。黑盒测试靠随机操作撞到这个窗口的概率极低。

---

## 二、「点两次按钮」是伪覆盖,必须禁止

这是最重要的一条警告。

连续点击两次购买按钮,看起来像是在测重复支付,实际上:

- 大多数客户端都有按钮防抖/置灰,第二次点击根本不会发出请求
- 即使发出了,它走的是"两次独立下单",不是"同一笔订单重复入账"
- 它**永远不会**触发回调重投、响应丢失重试、队列重放这三种真实场景

**所以它会给团队造成"重复支付已覆盖"的虚假信心。这比不测更糟。**

框架里应该明确禁止:用例若以"连续点击 N 次"作为重复支付的验证手段,校验器发警告,复核时必须驳回。

## 三、三层解法

| 层 | 做什么 | 能发现 | 依赖 |
|---|---|---|---|
| **L2 静态** | **幂等防护缺失扫描** —— 扫描支付/发货/结算链路,找该有防护但没写的地方 | 缺少幂等键、缺少状态守卫、缺少回调去重 | 源码(不需运行) |
| **L3 运行时** | **精确时序故障注入** + **幂等不变量判定** | 防护存在但失效、防护有漏洞 | 真机 + 状态上报 |
| **服务端** | 回调重投、重复入账的对账验证 | 服务端那一半 | 服务端数据 |

**关键认识:重复支付的根因是"结构性缺失"——该有幂等的地方没写。所以最有效的检测不是运行测试,而是静态地找出这些缺失。** 这恰好是"代码作为上游"的合法用法(代码提供"测哪里/查哪里",不提供期望)。

---

## 四、L2:幂等防护缺失扫描

这是"人肉 code review"的自动化版本,而且可做——因为防护的存在与否是**结构性**的,不是语义推测。

### 扫描目标:找出有副作用的链路

先定位所有**会产生不可逆副作用**的入口:

- 支付下单、支付确认、支付发货
- 道具/货币发放
- 结算入账
- 存档写入
- 排行榜提交
- 活动奖励领取

### 对每个入口检查四类防护

| 防护 | 检查什么 | 缺失后果 |
|---|---|---|
| **幂等键** | 请求是否携带唯一订单号/请求 id,并在服务端或本地有唯一约束 | 同一请求被处理两次 |
| **状态守卫** | 状态流转是否有前置状态校验(如"只有待支付才能转为已支付") | 已完成的订单被再次推进 |
| **回调去重** | 外部回调处理是否先查"这笔已处理过吗" | 渠道重投导致重复发货 |
| **重放去重** | 本地待处理队列重放时,是否检查该操作已成功 | 离线队列与成功请求叠加 |

### 扫描产出

不是"用例",而是两份清单:

```
防护缺失清单
  文件: ShopManager.cs:214  入口: BuyItem
  缺失: 状态守卫 —— 未校验订单当前状态即发起扣款
  证据: 第 214-240 行无 status 判断,直接调用 Pay()
  置信度: 待人工确认

覆盖地图(支付链路)
  S1 下单 → S2 拉起支付 → S3 支付回调 → S4 发货入账 → S5 状态落库
  每条边的失败/重试路径: [列出]
  可注入点: S2 后丢响应、S3 重投、S4 前杀进程
```

**每条都要能定位到文件与行号**,供人抽查——因为 AI 读代码会声称"这里没有防护"而实际有(或在别处有)。产出必须标注为"待验证"。

## 五、L3:精确时序故障注入

框架已有的 `network` 块太粗(只有 latency/loss/disconnect_after_ms),测重复支付需要**按动作定位的时序注入**。

### 新增 fault 动作语义

```json
{"action": "fault", "kind": "drop_response", "after_step": "S2",
 "delay_ms": 100, "window_ms": 2000}
{"action": "fault", "kind": "kill_after_step", "after_step": "S3"}
{"action": "fault", "kind": "offline_during_step", "around_step": "S4", "duration_ms": 3000}
{"action": "fault", "kind": "replay_callback", "target": "PAY_CALLBACK",
 "times": 3, "note": "需服务端或代理配合,客户端注入不了"}
```

与运行时状态的对应关系:

| 真实场景 | 注入方式 | 客户端能否独立注入 |
|---|---|---|
| 响应丢失导致重试 | `drop_response`:在请求发出后、响应到达前切断下行 | **能** |
| 进程被杀后重启 | `kill_after_step` + 重启后观察 | **能** |
| 本地队列重放 | `offline_during_step` 制造待处理队列 | **能** |
| 渠道回调重投 | `replay_callback` | **不能,需服务端/代理** |
| 用户重复提交 | 普通点击(价值最低) | 能,但覆盖不到真问题 |

**四种能测的、一种测不了的。** 服务端回调重投这一条必须在服务端验证,真机测试覆盖不到——这是诚实的边界,要写进报告而不是假装覆盖了。

## 六、幂等不变量目录

判定必须靠这些不变量,不能靠界面。全部需要 `state-report` 支持。

| 不变量 | 上报字段建议 | 说明 |
|---|---|---|
| 同一订单只存在一条记录 | `orders[]` 按 `orderId` 唯一 | 服务端唯一约束的客户端可见面 |
| 同一订单只发货一次 | `deliveries[]` 按 `orderId` 唯一 | |
| 扣款次数等于 1 | `order.chargeCount == 1` | 最直接 |
| 道具/货币增量等于单次预期值 | `player.coinDelta`、`bag[].count` 增量 | **注意不是"大于 0",是"精确等于单次值"** |
| 订单状态单调不回退 | `order.status` 只能沿合法方向流转 | 状态守卫是否生效 |
| 待处理队列最终清空 | `pendingOps == []` | 与 `assert_convergence` 配合 |
| 回调处理计数与业务动作计数一致 | `callback.processed` vs `deliveries.length` | 能发现"回调收了两次只发一次货" |

**「增量精确等于单次值」比「增量大于 0」强得多。** 后者对重复支付完全无感——发了两次货,增量是 2 倍,仍然大于 0。

精度用 `eq` 算子即可表达。而"订单表按 orderId 唯一""背包无重复条目"这类唯一性,需要 `unique_by` 算子(已在框架中实现:path 指向列表,value 给字段名)。**关键是要有人想到写这条不变量,并把它挂在正确的时序注入后面。**

## 七、一个完整的重复支付用例长什么样

```
# 用例: 支付响应丢失后的重试不得导致重复扣款与重复发货

- ID: INV-IDEM-C01
- 来源: invariant
- 类型: device-android
- 优先级: P0
- 判定模式: state-report

## 前置条件
- PRE-1: 账号金币 0,背包无道具 A
- PRE-2: 使用固定测试商品(价格 100 金币,发放道具 A × 1)

## 操作步骤
- S1: 进入商城,点击购买商品
- S2: 在支付请求发出后 100ms 切断下行网络,持续 2000ms(模拟响应丢失)
- S3: 恢复网络,等待客户端重试与状态收敛
- S4: 读取状态上报
- S5: 重启客户端,再次读取状态上报

## 期望结果
- E1: 上报的 order.chargeCount 等于 1,不得为 2
- E2: 上报的 player.coinDelta 精确等于 -100(单次扣款),不是 -200
- E3: 上报的 bag 中道具 A 的数量精确等于 1,不是 2
- E4: 上报的 orders 中按 orderId 唯一,不存在同一订单两条记录
- E5: 重启后 E1-E4 仍成立(防止重放)
```

对应声明块:

```json
"network": { "profile": "flaky", "reconnect": true, "assert_convergence": true },
"determinism": { "seed": 20260917, "fixed_timestep_ms": 16 }
```

注意 E4 这条唯一性断言用的是 `unique_by` 算子:path `orders`,op `unique_by`,value `orderId`。

## 八、能不能"避免"这类缺陷?

分两种含义回答。

### 能避免漏测 —— 能,靠上面三层

静态扫描发现缺失、故障注入验证防护、不变量判定结果。三层配合能系统覆盖,而不是靠随机撞。

### 能避免缺陷发生 —— 部分能,但要前移到开发阶段

既然根因是结构性缺失,那最有效的时点是**写代码的时候**,不是测试的时候。建议把上面那张四类防护检查表变成**开发自检清单**,在 MR 里过一遍:

- 这个入口有副作用吗?→ 有幂等键吗?
- 涉及状态流转吗?→ 有前置状态守卫吗?
- 接收外部回调吗?→ 有去重吗?
- 有本地队列吗?→ 重放时检查已成功了吗?

**这比全量 code review 便宜得多,而且可以部分自动化**(模式匹配找有没有幂等键参数、有没有去重查询、有没有状态判断)。

框架能参与的是:把这份清单做成可执行的静态检查,挂到 CI 上,在合并前报告"这个新增的副作用入口没有幂等防护"。**这才是真正的"避免",而不是"测出来"。**

## 九、边界(不要承诺做不到的)

| 做不到 | 原因 |
|---|---|
| 服务端回调重投的真机覆盖 | 客户端注入不了回调,需服务端或代理 |
| 服务端重复入账的确认 | 客户端看不到服务端账目,需要服务端数据或对账接口 |
| 真实支付渠道的端到端验证 | 无沙箱自动支付路径 |
| 高并发下的竞态(真并发) | 真机只有单客户端,造不出真并发;需要服务端压测 |
| 保证防护"绝对正确" | 静态扫描只能发现"缺失",发现不了"防护写错了"——后者需要故障注入实测 |

**最后一条特别要注意**:静态扫描说"这里有幂等键",不等于"这个幂等键有效"。所以 L2 和 L3 必须配合——静态找缺失,动态验有效。任何一层单独用都会漏。
